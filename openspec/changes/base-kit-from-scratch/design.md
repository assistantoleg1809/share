# Design

## Context

Расширение ship-kit v2 (1.0.0, 7 скиллов, стадийная модель, yaml-реестр)
e2e-проверено, но как лицо комплекта слишком сложно (proposal — Why).
Подготовленный change `simplify-to-base-kit` предполагал механическую
чистку; пользователь выбрал «путь б» — три скилла пишутся с нуля по
решётке суперпауэрс («методология + файловый контракт, без движка и без
конфигурации», исследование `research/superpowers-skills/`, 2026-11-14).
Этот change поглощает и заменяет `simplify-to-base-kit`. Зафиксированные
пользователем решения 2026-11-14: состав task/pr/ci, реестра в базе
нет, конвейер — в `examples/conveyor/` (второе расширение отклонено),
OpenSpec-корень — в корень репо, 76 удалений `dev/**` финальны, версия
2.0.0. Имена task/pr/ci — выбор пользователя 2026-11-14 из пяти
предложенных связок; ранее отвергнуты analyst/courier/operator (жарлон
позиций) и dev/pr/runcicd («нейминг вызывает резь»). Инструмент
спекирования в поставке не упоминается — discovery в рантайме, смена
инструмента не требует правок комплекта (решение «без вшивания»,
2026-11-14). Рабочая копия: v2-тексты analyst/courier/operator — источник
проверенных формулировок, но не основа для правки.

## Goals / Non-Goals

**Goals:**

- Три SKILL.md с нуля, каждое ≤ ~150 строк ядра: поведение — в ядре,
  тяжёлое (kind-файлы CI) — в support-файлах по требованию.
- База понятна из одних description: «возьми задачу» / «отправь на
  ревью» / «запусти сборку», без словаря конвейера.
- v2 целиком и читабельно в `examples/conveyor/`, включая выжившие
  tests/e2e; возможность «оживить» копированием в `.qwen/skills`.
- Проверка базы — методология writing-skills (RED-baseline без скилла →
  GREEN со скиллом, golden-снимки контрактов), не стенд движка.

**Non-Goals:**

- Ревью-сабагент по SHA-диапазону в `pr` (второй эшелон — отдельный
  change после двух недель живого использования базы).
- Поддержка примера как продукта: не версионируем, не адаптируем под
  чужие проекты, не чиним его прогоны.
- Автопереходы между фазами, счётчики/бюджеты/WAIT, конфигурация любого
  вида — не возвращаются в базу.
- Изменение истории git и архивных артефактов v2.

## Decisions

1. **Писать с нуля, не чистить v2-тексты.** v2-скиллы несут привычки
   шаг-протокола: ask-таблицы позиций, привязка гейтов к карточной
   криптографии, оговорки про реестр. Механическая чистка сохранила бы
   форму (отклонённый путь simplify-to-base-kit). Переписывание
   начинается с чистого контракта фазы; дословно из v2 переносятся
   только проверенные блоки (Шаг-0 MCP-проверка с блоком ошибки, запрет
   целевых веток, контракт-строки отчётов).
2. **Скилл = фаза; границы: task / pr / ci.** task: контекст → спека
   (openspec, опционально) → реализация TDD → коммиты. pr: ветка →
   карточка «пуш+PR» → цикл замечаний. ci: карточка запуска →
   запуск → ожидание → лог → секция диагностики. Диагноз и фикс
   «профессий» doctor/detective/mechanic распределяются: чтение лога и
   категория — секция `ci` (kind-файлы build.md/deploy.md
   переезжают из doctor и перерабатываются), правка по диагнозу — режим
   fix у `task`. Режим fix различает связанность (решение пользователя
   2026-11-14): ошибка внутри диффа задачи — правка в её ветке, тем же
   PR; посторонняя ошибка (инфра/конфиг CI/чужой код — первопричина вне
   диффа задачи, обычно эволюционирует независимо) — отдельная
   техническая ветка, срезанная от базовой, и отдельный PR; посторонние
   правки файлы `openspec/` не трогают вовсе. Отклонено: четвёртый
   скилл-диагност (нарушает решение о базе-3 и возвращает микрошаги).
3. **Лёгкий/полный путь task — по заданию.** Аналог храповика
   brainstorming (spike/bounded/architectural): фикс-правка и мелкая
   задача идут лёгким путём (контекст + правка + коммит); полный путь —
   спецификация изменения — когда задание просит спеку или правка
   затрагивает поведение спеки. Инструмент спекирования не вшивается
   (решение пользователя 2026-11-14 «без вшивания»): определяется в
   рантайме из скиллов сессии по description (оформление спеки до кода),
   найдено несколько — один вопрос, ни одного — мини-дизайн в чате;
   реализация идёт по чек-листу изменения, не по структуре каталогов.
   Тот же принцип, что нейтральность к бренду CI. Неясно — один вопрос
   человеку. Порог не фиксируется числом.
4. **Гейты — три правила, без состояний.** Карточка-превью → явное «да»
   → действие; отказ = стоп без перебора; дословное «подтверждаю …» в
   задании = pre-approved с указанием источника. Отброшено v2-правило
   наследования по идентичной карточке: семантическое сравнение payload
   в прозе непроверяемо; вместо него flaky-повтор — переспрос одной
   строкой, максимум один подряд.
5. **Состояние — plan.md минимальной схемы.** Чек-лист фаз (попытки —
   числом в строке `- [ ] build · 2/3`), текущая фаза, журнал, открытые
   вопросы. Нет секций бюджета/гейтов/аргументов с источниками.
   Возобновление = прочитать план + свериться с реальностью (git, статусы
   PR/джоб). issues.md — как в v2: провал = отдельная задача, чинит
   другой вызов.
6. **Дисциплины встроены в ядра, отдельного скилла-диспетчера нет.**
   Секция верификации (~5 строк: дословные свежие строки перед
   `OK: true`) и минимальность правки — императивные строки каждого
   ядра. В отличие от суперпауэрс, базе нечем подгружать дисциплины
   извне (нет using-superpowers), поэтому дублирование трёх строк в трёх
   скиллах дешевле слоя диспетчеризации.
7. **Конвенции вместо конфигурации.** Единственные пути: вызов
   `/ship-kit:<имя> <КЛЮЧ> …, mcp-<имя>=<alias>, …`;
   `skill-runs/<КЛЮЧ>/{plan.md,issues.md}` (рекомендация `.gitignore` —
   в docs). Формат передачи алиасов — пары `ключ=значение` в тексте
   задания; скилл разбирает их на Шаге-0. Любые списки и файлы данных
   комплекта и примера — md, не yaml (решение пользователя 2026-11-14:
   ии-агенты читают связный текст и таблицы лучше yaml-структур).
   Спек-инструмент — discovery в рантайме по списку скиллов сессии;
   строка-объявление в QWEN.md проекта не требуется (подсказка проекта —
   обычный контекст, не конфигурация). Список скиллов сессии — уже
   доступный контекст, не «поиск»: запрет поиска действует для внешних
   систем (MCP/CI).
8. **Тесты базы — отложены (решение пользователя 2026-11-14 «без
   тестов пока»).** Методология зафиксирована на будущее: (1)
   статический контракт (frontmatter, ядро ≤150 строк, секции); (2)
   golden-снимки контракт-строк; (3) RED-baseline/GREEN-прогоны на
   моках (моки переезжают в examples/conveyor/e2e, прогон оттуда).
   Проверки этого изменения — статические: validate --strict,
   grep-чистота поставки, структура, JSON-манифест; агентные прогоны
   вернутся после живого использования вместе с ревью-сабагентом
   (Non-Goal).
9. **examples/conveyor — снимок, не продукт.** Скиллы run/doctor/
   registry/adapt-kit (тексты v2), манифест позиций и схема реестра —
   оба в md (конвертация из yaml при переносе: yaml-блоки →
   md-таблицы/списки; упоминания yaml/formatVersion в текстах примера
   переписываются; yaml-валидатор `check_registry.mjs`/`yamlite.mjs` и
   yaml-фикстуры не переезжают, `run_checks.sh` — без yaml-уровня), v2-документ, снимок
   мейн-спек conveyor/registry/executors, выжившие tests/e2e из dev/,
   README (когда конвейер нужен, имена базы
   ship-kit:task/pr/ci, «оживление» копированием в `.qwen/skills`,
   миграция с v1.0.0, «соответствие на момент коммита»). Ссылки примера
   на имена базы переписываются в этом же change.
10. **Порядок применения.** (1) OpenSpec-корень → корень репо (change
    переезжает вместе с корнем); (2) удаление поглощённого change
    `simplify-to-base-kit`; (3) скиллы с нуля (task, pr, ci +
    kind-файлы); (4) QWEN.md, docs/ship-kit.md, манифест 2.0.0; (5)
    вынос v2 в examples/conveyor + README + снимок спек (до удаления
    мейн-спек); (6) ликвидация dev/ (удаления + переезд 13 файлов);
    (7) проверки (validate --strict, структура, grep);
    (8) коммит; (9) обновление dev-копии `~/.qwen/extensions/ship-kit`.
    Откат — `git revert` коммита: база и пример возвращаются атомарно.
11. **Порядок прогона — из задания, материализуется в план (решение
    пользователя 2026-11-14; пересмотр первоначального файла-профиля).
    Проблема: внешний набор скиллов в промпте + ship-kit — гейт
    создания PR ожидался после конкретного шага, а модель входила в
    фазу доставки после произвольного (#2 или #5). База детерминирует
    гейт внутри себя (вход в `pr`, ровно один раз, до необратимого),
    но не позицию фазы среди внешних скиллов. Файл-механизм отклонён:
    конфигурация до первого прогона, рассинхрон при смене набора, а
    схема уже есть в самом задании. Механизм: Шаг-0 `task` собирает
    чек-лист (скиллы в порядке перечисления + слоты фаз: названная
    позиция, иначе хвост доставки), показывает одним блоком, одно
    подтверждение; далее порядок живёт в plan.md — токен возобновления.
    Макрос `ship-kit.workflows.md` (несколько по типам задач)
    разворачивается в перечень до подтверждения. Отклонены: файл как
    механизм; 4-й скилл-оркестратор (= `run` из v2); полный нативный
    набор скиллов конвейера (4 из 7 скиллов дублировали бы
    установленные методологии вроде superpowers; боль v2
    возвращается).

## Risks / Trade-offs

- [Переписывание потеряет проверенные формулировки v2] → блоки
  Шаг-0/границ веток/контракт-строк переносить дословно из v2-текстов;
  каждая перенесённая секция сверяется grep'ом.
- [Лаконичные тексты снизят комплаенс скиллов] → дисциплины остаются
  императивными строками (MUST-форма), проверка — живым использованием
  (агентные прогоны отложены, Decision 8); ядро не ужимается ради
  цифры 150, если строка несёт поведение.
- [Секция диагностики ci разбухнет] → детали трактовки — только в
  kind-файлах; ядро держит контракт (вход/выход/границы).
- [Пример разъедется с базой при её эволюции] → README фиксирует
  «соответствие на момент коммита»; пример не продукт.
- [Коллеги на v1.0.0 зовут analyst/courier/operator] → README примера:
  переустановить расширение, новые имена, вызов без реестра.
- [Конвертация реестра в md отводит пример от «дословного снимка v2»] →
  README примера фиксирует: реестр конвертирован по решению пользователя,
  остальное — снимок v2 как есть.
- [Полный конвейер перестаёт быть «одним установом»] → осознанный
  размен (решение пользователя); README объясняет «оживление».

## Migration Plan

См. Decision 10 (порядок). Миграция установленных копий: uninstall →
install из репо (`--consent`), имена скиллов меняются на task/pr/ci,
реестр больше не читается никем. Промежуточных версий не выпускается.

## Open Questions

Нет: состав, имена, границы фаз, судьба dev/ и версия зафиксированы
пользователем; порог лёгкого/полного пути task решается текстом скилла
при написании (Decision 3) и не влияет на спеки и разбиение задач.

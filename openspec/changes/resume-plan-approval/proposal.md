# Proposal — resume-plan-approval

## Why

Между фазами прогона человек вручную печатает полные имена скиллов набора
(`/openspec-apply-change` и т.п.), чаще всего в новой сессии без
автодополнения ввода. Это главный источник трения комплекта: продолжение
прогона ощутимо дольше, чем та же работа без ship-kit. Токен возобновления
«продолжи <КЛЮЧ>» уже спроектирован, но не доведён до рук: его нет в
триггерах description скиллов (новая сессия не обязана сопоставить фразу с
комплектом) и нет в отчётах (готовой фразы для копирования отчёт не даёт).

## What Changes

- **«продолжи <КЛЮЧ>» — канонический вход возобновления прогона**:
  триггер добавляется в description `task`; узкие resume-фразы `pr`
  (ожидание MERGED) и `ci` (статус джобы) остаются как есть.
- **Алгоритм возобновления «сначала сам, потом вопрос»**: `task` читает
  план, сверяется с git, находит следующий незакрытый слот. Шаг однозначен
  → показывает **остаток плана одним блоком** и получает **одно
  подтверждение** (вопрос закрытыми опциями, правила гейтов), после чего
  ведёт слоты сам до конца плана. Сомнение (несколько незакрытых слотов,
  расхождение плана с git, ключ не найден) → один вопрос закрытыми
  опциями.
- **Имена внешних скиллов человек не печатает**: слоты плана вызывает сам
  `task` инструментом вызова скиллов; в карточке остатка имена видны, но
  набирать их не нужно.
- **Пауза-ревью после слота спеки**: после закрытия слота `spec` цепочка
  останавливается вопросом закрытыми опциями (проверить спеку → продолжить
  / доработать / стоп) — проверка спеки человеком не пропускается.
- **План живой**: посторонний тех-фикс дописывается в план слотом
  `pr: тех-PR`, повторная сборка — попыткой `ci ×N`; дописывание
  показывается на ближайшей карточке или вопросе, отдельной команды
  («собери») не требуется.
- **Строка `ДАЛЬШЕ: продолжи <КЛЮЧ>`** — в конце отчёта каждой фазы
  (`task`/`pr`/`ci`), пока план не закрыт: одна строка для копирования в
  новую сессию вместо имени скилла.
- **Скилл слота не загружен в сессии** — честная пометка и один вопрос:
  пропустить слот (помечается в плане) / остановить прогон; молчаливых
  пропусков нет.
- Манифест 2.6.0 → 2.7.0, секция рецептов в `docs/upgrade.md`.

## Capabilities

### New Capabilities

- нет — поведение целиком расширяет существующую capability.

### Modified Capabilities

- `base-skills`:
  - **«Три скилла-фазы с говорящими именами»** — description `task` обязан
    нести триггер продолжения прогона; `task` — канонический вход
    возобновления.
  - **«Состояние прогона — plan.md и issues.md»** — токен возобновления
    обрастает алгоритмом: определение следующего шага, подтверждение
    остатка плана одним блоком, вызов внешних слотов сам, пауза-ревью
    слота `spec`, живой план (дописывание слотов/попыток), строка
    `ДАЛЬШЕ:` в отчётах фаз.

## Impact

- `extensions/ship-kit/skills/task/SKILL.md` — триггер в description,
  Шаг-0 (алгоритм возобновления), завершение фазы (пауза-ревью, строка
  ДАЛЬШЕ), формат отчёта.
- `extensions/ship-kit/skills/pr/SKILL.md`,
  `extensions/ship-kit/skills/ci/SKILL.md` — строка `ДАЛЬШЕ:` в формате
  отчёта; связь «продолжи <КЛЮЧ>» вне собственного ожидания → вход через
  `task`.
- `extensions/ship-kit/QWEN.md` — инвариант «Один вызов = одна фаза»
  уточняется: переход между вызовами делает человек одной короткой фразой;
  внутри утверждённого плана фазы идут цепочкой. «Состояние прогона» —
  краткий алгоритм возобновления.
- `extensions/ship-kit/docs/ship-kit.md` — п.1 и п.6.
- `extensions/ship-kit/docs/upgrade.md` + `qwen-extension.json` (2.7.0).
- `examples/` не правятся: конвейер-пример — отдельный снимок со своей
  методикой.

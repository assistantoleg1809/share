# executors — способность «позиции и исполнители конвейера»

## Purpose

Словарь позиций (манифест комплекта), исполнители на позициях (дефолты
комплекта и подмена в проекте), режимы doctor и правила «спрашивать
человека»; как исполнители получают MCP и аргументы из записей знания стадий
и как правки репозитория уходят в pull request.

## ADDED Requirements

### Requirement: Манифест позиций

Комплект MUST поставлять манифест позиций (`docs/ship-kit.positions.yaml`):
для каждой позиции — контракт (шаг 0, формат отчёта, ask-правила) и версия
контракта; дефолтные наборы позиций по kind стадии. Комплект исполнителей не
подбирает сам (trust discovery-only) — только явная запись в `executors:`
проекта; SKILL.md исполнителей пишутся под контракт манифеста.

#### Scenario: состав словаря

- **WHEN** читается манифест комплекта
- **THEN** позиции: analyst (спека + правки кода), courier (ветка/PR/замечания), operator (запуск/ожидание джоб), detective (диагноз — служебная, вызывает run), mechanic (не-код фикс)

#### Scenario: подмена исполнителя в проекте

- **WHEN** проект пишет `mechanic: superpowers:refactoring` в `executors:`
- **THEN** стадии не меняются; валидатор даёт предупреждение «контракт проверяется e2e»; прогоны используют подменённого исполнителя на позиции mechanic

### Requirement: Скиллы-исполнители комплекта (Профессии, 7)

Комплект MUST поставлять исполнителей: **analyst** (контекст Jira/Confluence/
mmap + оформление изменения OpenSpec + правки кода), **courier** (ветка,
коммиты, PR, цикл замечаний), **operator** (запуск/ожидание джоб), **doctor**
с режимами `diagnose` (только чтение: категория, rootCause, fixable,
fixHint, knownIssues, confidence) и `fix` (TDD-фикс, 🔒 карточка пуша, push);
режим задаёт вызывающий, doctor сам не переключает. `run`, `registry`,
`adapt-kit` — без переименования.

#### Scenario: диагноз и фикс одним doctor

- **WHEN** build упала, run вызывает doctor (режим diagnose), затем fixBuild вызывает исполнителя mechanic (дефолт doctor в режиме fix)
- **THEN** диагноз не передаётся аргументом между скиллами; режим fix читает `repairRef` и сверяет первопричину логом упавшей джобы

### Requirement: Исполнители получают MCP и джобы из записи своей стадии

Исполнители MUST получать свои MCP и аргументы запуска из записи знания
своей стадии (передаёт вызывающий): позиции стадии — `knowledgeRef`,
`doctor: diagnose` — `diagnosisRef`, `doctor: fix` — `repairRef`; ссылка
отсутствует или null — читается `knowledgeRef` стадии. Исполнители реестр не
читают и серверы сами не выбирают (шаг 0, блок ошибки при недоступном MCP).

#### Scenario: диагностика с runbook

- **WHEN** build упала и run вызывает doctor (режим diagnose)
- **THEN** doctor получает MCP из `diagnosisRef` (транспорт стадии + sonar/jira/confluence) и читает runbook и тикеты команды, которых нет в записи самой стадии

#### Scenario: фикс сверяет упавшую джобу

- **WHEN** fixBuild вызывает mechanic (doctor, режим fix)
- **THEN** фикс сверяет первопричину логом упавшей джобы из `repairRef` (jobName=calc-app), а не быстрой ci-джобой записи стадии

### Requirement: Ask-правила позиции

SKILL.md каждого исполнителя MUST начинаться таблицей правил: запуск джобы —
ask · всегда; пуш — ask · всегда; создание PR — ask · всегда; flaky-повтор —
inherited, только идентичная карточка; чтение (статус/лог/тикеты) — allow;
всё сверх переданных MCP — deny.

#### Scenario: чтение без вопроса

- **WHEN** operator в режиме ожидания опрашивает статус джобы
- **THEN** чтение выполняется без гейта; в отчёте статус, errorSnippet, logTail

### Requirement: Производный kind для knowledge-пака

Ролям транспорта MUST передаваться kind=build|deploy, производный из kind
стадии: BUILD/FIX_BUILD → build, DEPLOY/FIX_DEPLOY → deploy; командные файлы
knowledge-пака (`build.md`/`deploy.md` в doctor) читаются только своего kind.
Для DO/FIX_DO роли транспорта не вызываются — их падение идёт в issues.md
без диагноза.

#### Scenario: фикс деплоя читает deploy-файл

- **WHEN** fixDeploy вызывает mechanic (doctor, режим fix)
- **THEN** doctor читает командный файл деплоя, а не сборки

### Requirement: PR только через владельца позиции

Правки репозитория MUST уходить в PR только через исполнителя позиции
`pullRequestOwner` стадии (обычно courier): 🔒 карточка «пуш+PR», замечания —
пушем в тот же PR, новый PR — только на новый фикс после упавшей джобы и
только при реальной правке репозитория. Прямого пуша без PR нет; пуш — только
в рабочие ветки `<X>/<КЛЮЧ>`, целевые ветки (`defaultBranch`, база PR)
запрещены.

#### Scenario: фикс сборки через PR-2

- **WHEN** fixBuild внёс правку по диагнозу
- **THEN** courier создаёт PR-2 в рабочую ветку после 🔒 карточки; замечания правятся пушем в тот же PR-2

#### Scenario: стадия без правок репозитория

- **WHEN** стадия build/deploy исполняется (`pullRequestOwner: null`)
- **THEN** PR не создаётся; решение падения — фикс-стадия или починка джобы

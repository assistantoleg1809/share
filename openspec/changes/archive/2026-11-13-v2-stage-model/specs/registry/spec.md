# registry — способность «ведение yaml-реестра проектов»

## Purpose

Единственная точка ведения реестра `ship-kit.projects.yaml`: проекты, стадии,
записи знания, серверы и исполнители — и правила, по которым реестр считается
корректным.

## ADDED Requirements

### Requirement: Единая точка ведения yaml-реестра

Реестр MUST вестись только скиллом `registry`: `ship-kit.projects.yaml` в
корне проекта либо центральный `~/.qwen/ship-kit/projects.yaml`. Скиллы-роли
реестр не читают — значения им передают аргументами вызывающий (`run`) или
человек; отсутствие alias в записях проекта = «в этом проекте этого MCP нет».

#### Scenario: добавление проекта

- **WHEN** пользователь просит «добавь проект в реестр» и называет значения
- **THEN** registry создаёт проект с обязательными полями (projectKey, jiraProjectKey, repoSshUrl, artifactId), стадиями и записями знания; отсутствующие значения спрашивает, не выдумывает

#### Scenario: сверка серверов

- **WHEN** в endpoint указан `serverId`
- **THEN** registry сверяет его с `settings.json → mcpServers`; не найден — сообщает пользователю и не пишет значение молча

### Requirement: Валидация реестра при ведении

При каждом изменении registry MUST проверять правила 1–14 (design.md §11):
ссылочная целостность, роли ссылок по kind, транспорт
`diagnosisRef`/`repairRef`, модели `runnerKind`, стенды, полнота фикс-стадий,
`pipelineOrder`, покрытие исполнителей записи, `servers:`, `executors:` и
`positions` против манифеста позиций.

#### Scenario: висячая ссылка стадии

- **WHEN** у fixBuild указан `fixesStageId: buld` (опечатка)
- **THEN** registry отказывается сохранять и показывает ошибку ссылки

#### Scenario: диагност без транспорта стадии

- **WHEN** запись `diagnosisRef` стадии deploy не содержит `MCP_DEPLOY` или называет другую джобу
- **THEN** registry отклоняет изменение: лог упавшего деплоя нечем читать

#### Scenario: исполнителя нет в манифесте

- **WHEN** в `executors:` указана позиция, которой нет в манифесте комплекта
- **THEN** registry отклоняет изменение; внешний скилл на существующей позиции допускается с предупреждением «контракт проверяется e2e»

### Requirement: Версионирование и миграции формата реестра

Реестр MUST начинаться с `formatVersion`. При расхождении с поддерживаемой
комплектом версией registry MUST предлагать управляемую миграцию (цепочка
миграций из комплекта, дифф, применение только после подтверждения
пользователя) либо останавливаться без правок файла, если реестр новее
комплекта.

#### Scenario: реестр старее комплекта

- **WHEN** yaml-реестр имеет `formatVersion` ниже поддерживаемой комплектом
- **THEN** registry показывает цепочку миграций и дифф; применяет только после подтверждения пользователя; миграция идемпотентна

#### Scenario: реестр новее комплекта

- **WHEN** `formatVersion` выше поддерживаемой комплектом
- **THEN** registry останавливается с сообщением «обновите комплект», файл не правится

### Requirement: Секция servers

serverId MUST описываться в верхнеуровневой `servers:` (id → назначение);
адреса, URL и токены в реестре не хранятся — подключение остаётся в
`settings.json → mcpServers` за пользователем.

#### Scenario: смена адреса сервера

- **WHEN** у CI-сервера сменился адрес
- **THEN** правится только `settings.json`; yaml-реестр не меняется (serverId неизменен), записи и стадии не трогаются

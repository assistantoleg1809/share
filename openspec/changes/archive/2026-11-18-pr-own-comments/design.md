# Design

## Context

Живые прогоны базы выявили две проблемы (пользователь, 2026-11-18):
слабая модель пытается спросить разрешение на ожидание мержа (спека это
уже запрещает — текст скилла недостаточно императивен), и в PR нельзя
различить комментарии агента и человека, когда оба идут под одной
учёткой — поле «автор» одинаково у всех.

## Goals / Non-Goals

**Goals:**

- Детерминированное различение своих/чужих комментариев без отдельной
  учётки и без конфигурации проекта.
- Формулировка ожидания мержа, которую слабая модель читает однозначно.

**Non-Goals:**

- Отдельная учётка-бот для агента (вне контроля комплекта и проекта).
- Изменение контракта MCP репозитория (add_comment как есть).
- Различение «человек-владелец» vs «другие ревьюеры» — все без маркера
  одинаково чужие.

## Decisions

1. **Маркер — дословная строка `[ship-kit]` в конце комментария.**
   Литерал слабая модель воспроизводит надёжнее шаблона; концовка
   строки не смешивается с содержимым ответа. Альтернативы: префикс
   (мешает читать первое предложение), HTML-комментарий
   `<!-- ship-kit -->` (не виден человеку в веб-UI, исчезает при
   цитировании), эмодзи (нестабильная кодировка). Маркер виден людям —
   честная маркировка авторства.
2. **id-журнал — вторая линия.** id своих комментариев пишутся в журнал
   `skill-runs/<КЛЮЧ>/plan.md`: точная проверка, переживает потерю
   маркера при цитировании/редактировании. Арбитр при расхождении —
   id-журнал (человек может пошутить маркером; id подделать не может).
   Альтернатива «только id без маркера» отвергнута: журнал теряется
   при новой сессии без плана.
3. **Свои = с маркером ∨ в id-журнале; всё остальное — чужое.** fix
   отвечает только на чужие; check считает только чужие unresolved.
   Свои unresolved — не замечание (иначе цикл зациклится на себе).
4. **Ожидание — императив в двух местах.** Шаг 5 implement+pr и
   «Завершение фазы» получают явное «разрешение на ожидание не
   спрашивается — ни вопросом, ни карточкой; первый опрос сразу после
   создания PR». Дубль фразы в двух секциях дешевле недоинтерпретации
   слабой моделью.

## Risks / Trade-offs

- [Человек подпишет свой комментарий маркером] → арбитр — id-журнал:
  комментарий с маркером, но не в журнале, при расхождении трактуется
  как свой только при отсутствии чужих признаков; практика редкая.
- [Другой бот тоже ставит `[ship-kit]`] → вне правдоподобия в контуре
  одного проекта; id-журнал различает.
- [Маркер не виден в UI некоторых форджей при рендере] → строка
  видима как текст везде, где комментарии — текст.

## Migration Plan

Текстовые правки pr/SKILL.md + одна фраза в docs; синк при архивации;
переустановка копии. Старые прогоны без маркера: их комментарии без
маркера и id в журнале отсутствуют — трактовка «чужие» безопасна
(агент не отвечает на свои прошлые ответы, но они и не unresolved).

# Design

## Context

См. proposal.md — Why. Ограничения, определяющие подход: (1) инвариант
«имя инструмента спекирования не в файлах комплекта»; (2) «ничего не
искать» — никакого сканирования ФС/серверов, только список скиллов
сессии, который платформа показывает скиллу (name + description, без
чтения файлов с диска); (3) лесенка «задание > конвенция проекта >
вопрос» уже канонизирована для аргументов — слоты обязаны вписаться в
ту же форму; (4) дисциплина версий (version-drift): change, меняющий
Шаг-0, бампает манифест и пишет рецепт в `docs/upgrade.md`.

## Goals / Non-Goals

**Goals:**

- Детерминированное разрешение исполнителя спекирования: литеральная
  метка вместо семантического угадывания по description.
- Один каскад разрешения слота той же формы, что лесенка аргументов.
- Контракт слотов, расширяемый без поломки старых/новых версий
  комплекта и проектов.

**Non-Goals:**

- Манифест-файл фаз (идея 3, не выбрана): макрос
  `ship-kit.workflows.md` и «Порядок прогона с внешними скиллами» не
  меняются — перечисление заданием уже вершина каскада.
- Расширенная диагностика (идея 5, не выбрана): fuzzy-подсказки имён,
  статическая предвалидация чек-листа — отдельных требований нет.
- Новые слоты кроме `spec`: словарь открыт, но каждый новый слот
  вводится своим change с правилом слота; здесь канонизируется только
  `spec`.
- Изменение `pr`/`ci`: слотовый поиск им не нужен, каскад описан на
  уровне комплекта.

## Decisions

1. **Метка живёт в description, не в frontmatter и не в теле SKILL.md.**
   Список скиллов сессии, доступный скиллу-фазе, содержит только
   name + description; frontmatter и тело читаются лишь при вызове
   скилла — метка там невидима без чтения файлов с диска, что
   противоречит «ничего не искать» и зависит от уровней установки
   (user/project/extension). Description виден каскаду бесплатно.
   Альтернатива (чтение SKILL.md кандидатов с диска) отвергнута:
   пути установки нестабильны, платформа уже отдала список.
2. **Формат метки — литеральный токен `slot:<имя>`, без пробелов,
   несколько через запятую** (`slot:spec,review`). Дословный поиск
   подстроки; никакой семантики. ASCII-токен выбран, чтобы метка была
   одинаковой в русских и английских описаниях; префикс `slot:`
   достаточно редкий, чтобы не совпасть случайно с чужим текстом.
3. **Семантическое угадывание удаляется, а не остаётся fallback'ом.**
   Цель выбора человека — «убрать угадывание»: оставленный fallback
   вернул бы недетерминизм и сделал бы метку необязательной. Цена —
   миграция (см. Migration Plan): проект без метки после 2.2.0
   получает честную деградацию «мини-дизайн», а рецепт закрывает
   добавление метки или назначение слота конвенцией.
4. **Каскад повторяет лесенку аргументов.** Задание (назвал
   инструмент/назначение) > конвенция проекта > метки сессии >
   правило слота. Шаг конвенции принимает три формы: исполнитель
   (звать), набор кандидатов без выбора одного (один вопрос с опциями
   из перечисленного — частый случай по слову человека 2026-11-20:
   файл проектов перечисляет скиллы, не называя конкретный), ничего
   (дальше к меткам). Набор в конвенции сильнее меток: метки не
   сканируются, вопрос идёт по перечисленным. Форма уже доказана в
   «Работа без конфигурации» — один алгоритм на все разрешения, две
   сегодняшние тропы (угадывание спеки / перечень внешних) сходятся к
   ней: перечень заданием — это и есть вершина каскада, менять её не
   нужно.
5. **Неизвестные слоты игнорируются** (паттерн Zed «старая версия
   игнорирует незнакомое поле»): проект может ставить метки слотов,
   которых эта версия комплекта не знает, и наоборот — новая версия
   словаря не ломает старые проекты.
6. **Dogfood:** метка `slot:spec` ставится в description
   `.agents/skills/openspec-propose/SKILL.md` этого репо — после
   применения change сам репо живёт по новому контракту.

## Risks / Trade-offs

- [Проект не поставил метку → после 2.2.0 спека тихо уходит в
  мини-дизайн] → деградация честная и замечаемая (отчёт отмечает
  отсутствие исполнителя); рецепт 2.2.0 в `docs/upgrade.md` + детектор
  дрейфа сообщит о смене версии; конвенция может назначить слот без
  метки.
- [Ложное совпадение литерала `slot:` в чужом описании] → несколько
  меток дают вопрос, а не угадывание; токен редкий, регистр и запятая
  зафиксированы.
- [Словарь разрастётся ad-hoc] → расширение словаря — только change'ом
  комплекта с правилом слота; конвенция проекта может назначать
  существующие слоты, но не вводить новые.
- [description скилла перегружается служебной меткой] → метка — одна
  короткая строка; description исполнителя — проектный файл, ограничение
  «только когда использовать» на него не действует (оно — на description
  скиллов комплекта).

## Migration Plan

Правки: `extensions/ship-kit/skills/task/SKILL.md` (Шаг 0.3 —
слот-каскад), `QWEN.md` («Спецификация»), `docs/ship-kit.md` (п.4 +
словарь слотов), `docs/upgrade.md` (секция 2.2.0: поставить метку
`slot:spec` в description спек-скилла или назначить слот конвенцией),
манифест 2.1.0 → 2.2.0, метка в `.agents/skills/openspec-propose`.
Синк дельты в `openspec/specs/base-skills/spec.md` при архивации;
установленная копия переустанавливается. Отката не требуется: старое
поведение (угадывание) возвращается удалением меток и сменой версии
назад — но проекты, поставившие метки, продолжают работать и на старом
комплекте (неизвестное игнорируется).

# Spec Delta

## ADDED Requirements

### Requirement: Скиллы комплекта видимы модели

Скиллы комплекта (`ship-kit-task/-pr/-ci`) MUST оставаться
доступными модели: `disable-model-invocation` MUST NOT выставляться.
Модель вызывает фазы из цепочки утверждённого плана и по триггерам
возобновления; человек — напрямую `/ship-kit-<фаза> <КЛЮЧ>, …`.
Description каждой фазы MUST нести триггеры «когда использовать»; у
`ship-kit-task` — также «продолжи <КЛЮЧ>» (канонический вход
возобновления).

#### Scenario: модель ведёт цепочку плана

- **WHEN** слот task закрыт, следующий незакрытый слот утверждённого плана — pr
- **THEN** вызванный скилл вызывает ship-kit-pr сам (инструментом вызова скиллов); человек имя фазы не печатает

#### Scenario: человек вызывает фазу напрямую

- **WHEN** человек пишет `/ship-kit-ci дай лог PRJ-42` вне плана
- **THEN** ci запускается и выполняет одиночный шаг без цепочки

#### Scenario: резюм фразой

- **WHEN** в новой сессии человек пишет «продолжи PRJ-42»
- **THEN** фраза сопоставляется с ship-kit-task по триггеру из description; task ведёт алгоритм возобновления

### Requirement: Частичная установка и вход любой фазы

Каталог `skills/ship-kit-<фаза>/` MUST быть самодостаточен (SKILL.md
+ `reference.md` инвариантов; ci — с kind-файлами) и устанавливаться
копией без остальных фаз. План прогона MUST строиться из
установленных фаз — наличие фазы определяется по списку скиллов
сессии; неустановленная фаза — пометка «фаза не установлена» в плане
и отчёте, без вопроса. Любая установленная фаза — входная точка:
первый вызов фазы по ключу создаёт план-файл.

#### Scenario: установлен только task

- **WHEN** в списке скиллов сессии из комплекта только `ship-kit-task`
- **THEN** план строится из одного слота task; фазы pr и ci помечены «фаза не установлена» в плане и отчёте; прогон завершается после task без вопросов о пропуске

#### Scenario: вход через pr

- **WHEN** человек вызывает `/ship-kit-pr PRJ-42`, плана с ключом нет, `ship-kit-pr` установлен
- **THEN** pr создаёт план-файл прогона, помечает слоты невыставленных фаз и ведёт свою фазу доставки

#### Scenario: установленный сосед видим

- **WHEN** `ship-kit-ci` установлен
- **THEN** он присутствует в списке скиллов сессии: Шаг-0 видит фазу, и цепочка плана включает слот ci

### Requirement: Директория прогона — каскад с временным дефолтом

Директория прогона MUST разрешаться каскадом: задание назвало
директорию → конвенция проекта → дефолт — временная
`.qwen/tmp/ship-kit/<КЛЮЧ>/` проекта. Определённая директория
использует уровень проекта — `<директория>/<ПРОЕКТ>/<КЛЮЧ>/`; дефолт
уровня не имеет — `.qwen` уже проектный. `<ПРОЕКТ>` — из конвенции,
иначе имя каталога репозитория. Каждый запуск скилла MUST
материализовать план-файл: найти по ключу или создать; провалы —
задачами в `issues.md` рядом.

#### Scenario: директория не определена

- **WHEN** задание и конвенция директорию прогона не называли, человек вызвал `/ship-kit-task PRJ-42`
- **THEN** план создаётся в `.qwen/tmp/ship-kit/PRJ-42/plan.md` — временная директория проектной `.qwen`; рабочее репо прогона не загрязняется

#### Scenario: директория определена конвенцией

- **WHEN** конвенция проекта называет `runs/` корнем прогонов
- **THEN** план живёт в `runs/<ПРОЕКТ>/<КЛЮЧ>/plan.md`, issues.md рядом; уровень проекта сохраняется

#### Scenario: прогон привязан к проекту

- **WHEN** два проекта имеют прогон с одинаковым ключом X-1, директории не определены
- **THEN** прогоны лежат раздельно — `.qwen/tmp/ship-kit/X-1/` в .qwen каждого проекта; при общей определённой директории — `<директория>/<проект1>/X-1/` и `<директория>/<проект2>/X-1/`

### Requirement: Чек-лист и журнал план-файла

План-файл MUST нести чек-лист фаз (счётчик попыток — числом в строке),
текущую фазу и журнал; каждая запись журнала MUST начинаться с даты и
времени — `ГГГГ-ММ-ДД ЧЧ:ММ` (локальное время машины), затем событие;
записи без даты и времени MUST NOT писаться.

#### Scenario: запись журнала с даты и времени

- **WHEN** фаза фиксирует событие в журнал плана (создание плана, гейт, PR, запуск джобы, id своего комментария)
- **THEN** строка записи начинается с даты и времени `ГГГГ-ММ-ДД ЧЧ:ММ`, затем событие; записей без префикса не пишется

### Requirement: Токен возобновления и статусы из MCP

План-файл MUST быть токеном возобновления: после паузы вызванный
скилл читает план, сверяется с фактическим состоянием (git, статусы
PR/джоб) и продолжает. Статусы PR и джоб MUST браться из свежих
ответов MCP: слова человека — не статус; при расхождении `pr` MUST
спросить: ждать MERGED или собрать на рабочей ветке; сборка на рабочей
ветке — только после явного «да», слот помечается ⚠ (жёлтым), не
зелёным.

#### Scenario: возобновление после паузы

- **WHEN** человек возвращается с «продолжи PRJ-42» (канонический вход `ship-kit-task`)
- **THEN** скилл читает plan.md по каскаду директории, сверяет фактическое состояние и продолжает с зафиксированной фазы, не переспрашивая сделанное

#### Scenario: слова против статуса

- **WHEN** человек говорит «смержил», а свежий get_pr показывает OPEN
- **THEN** pr не закрывает слот зелёным и спрашивает: ждать MERGED или собирать на рабочей ветке; при «да» карточка запуска ci фиксирует рабочую ветку и её источник, слот помечается ⚠

## MODIFIED Requirements

### Requirement: Три скилла-фазы с говорящими именами

Комплект MUST поставлять ровно три скилла: `ship-kit-task` — контекст
задачи и правки кода (спецификация изменения — опциональный путь),
`ship-kit-pr` — рабочая ветка, пуш, PR и цикл замечаний, `ship-kit-ci`
— запуск и ожидание джоб CI с диагностикой падений. Поставка —
самодостаточные каталоги `skills/ship-kit-<фаза>/`, устанавливаемые
независимо копией («Частичная установка и вход любой фазы»); QWEN.md
и манифест расширения в поставке нет, скиллы остаются доступными
модели («Скиллы комплекта видимы модели»). Description каждого
скилла MUST содержать только «когда использовать» с триггерами
вызова, без словаря конвейера. Закрытый слот плана прогона MUST
продолжаться следующим незакрытым слотом **без остановки** (цепочка
авторизована планом; паузы — только 🔒-гейты и вопросы правил; конец
плана — стоп). Одиночный вызов скилла человеком вне плана
выполняется без цепочки. Тексты поставки MUST обращаться к MCP по
ролям, не по именам конкретных продуктов; роли на серверы мапит
конвенция проекта. Канонические роли: **tracker** (трекер задач),
**docs** (вики/runbook), **repo** (репозиторий и PR), **build**
(сборка), **deploy** (деплой), **quality** (качество кода), **vuln**
(уязвимости/сканирование), **chat** (чаты/мессенджеры).

#### Scenario: правка по тикету

- **WHEN** человек вызывает `/ship-kit-task PRJ-42, mcp-tracker=tasks`
- **THEN** task собирает контекст, оформляет изменение (или правит напрямую — по весу задания), коммитит и сразу продолжает следующим слотом плана — `pr` с карточкой «пуш+PR»

#### Scenario: имя продаёт вызов

- **WHEN** человек читает description скилла, не открывая SKILL.md
- **THEN** из description понятно, какой скилл звать: «возьми задачу» → ship-kit-task, «отправь на ревью» → ship-kit-pr, «запусти сборку» → ship-kit-ci

#### Scenario: одиночный вызов вне плана

- **WHEN** человек зовёт один скилл для одиночного шага (например «проверь PR» или «дай лог»)
- **THEN** выполняется только этот вызов, цепочка не тянется

### Requirement: Инструмент спекирования не вшивается

Комплект MUST NOT фиксировать имя или формат инструмента спекирования
ни в одном поставляемом файле (SKILL.md, reference.md, docs); контракт
комплекта — только слот **spec** («Слоты переменных скиллов»). Полный
путь `task` оформляется исполнителем слота `spec`, найденным каскадом
задание > конвенция проекта > метки скиллов сессии; ноль кандидатов —
мини-дизайн в чате, несколько — один вопрос. **Конвенция проекта
сильнее умолчания скилла**: может обязывать спецификацию (полный путь
всегда, лёгкого пути нет), назначать слот или перечислять кандидатов
без выбора одного (набор — один вопрос человеку); задание сильнее
конвенции. Реализация идёт по чек-листу изменения независимо от формата
каталогов исполнителя.

#### Scenario: в проекте установлен спек-скилл

- **WHEN** задание просит спеку и один скилл сессии несёт метку `slot:spec`
- **THEN** task оформляет изменение этим скиллом по его собственным правилам; отчёт упоминает использованный инструмент как факт, не как настройку

#### Scenario: спек-скилла нет

- **WHEN** задание просит спеку, метки `slot:spec` нет ни у одного скилла сессии
- **THEN** task делает мини-дизайн в чате и честно отмечает в отчёте отсутствие исполнителя слота

#### Scenario: смена инструмента спекирования

- **WHEN** в проекте спек-скилл с меткой `slot:spec` заменён другим скиллом с той же меткой
- **THEN** файлы ship-kit не меняются: каскад входит новым исполнителем

#### Scenario: конвенция обязывает спеку

- **WHEN** конвенция проекта требует спецификацию для каждой задачи и назначает слот
- **THEN** task оформляет изменение до кода даже для мелкой правки, без собственного усмотрения; исполнитель — из конвенции

### Requirement: Порядок прогона с внешними скиллами

Комплект MUST NOT задавать порядок внешних скиллов сам. План прогона
создаётся **всегда** при первом вызове любой фазы по ключу
(директория — «Директория прогона — каскад с временным дефолтом»).
Задание перечислило внешние скиллы → вызванный скилл MUST собрать
чек-лист: скиллы в порядке перечисления + слоты фаз комплекта на
названных позициях (не названы — в хвосте доставки; неустановленная
фаза — пометка, слот пропускается), показать одним блоком и получить
одно подтверждение. Не перечислило → план = установленные фазы
комплекта по умолчанию (`task → pr 🔒 → ci 🔒`; неустановленные фазы
выпадают; слот `ci` открывается после MERGED PR), без вопроса.
`ship-kit.workflows.md` — опциональный макрос типовых наборов,
разворачивается в перечень. Гейт создания PR = вход в `pr` на строке
слота.

#### Scenario: задание задаёт позицию гейта

- **WHEN** задание ставит слот `/ship-kit-pr` после трёх внешних скиллов
- **THEN** карточка «пуш+PR» показывается после завершения этих трёх шагов — не раньше и не позже

#### Scenario: порядок не назван

- **WHEN** задание перечислило скиллы без позиций слотов
- **THEN** task предлагает чек-лист одним блоком (скиллы по порядку перечисления, слоты доставки в хвосте) и ждёт одного подтверждения

#### Scenario: внешних скиллов нет

- **WHEN** задание не перечисляет внешних скиллов
- **THEN** план создаётся с дефолтными фазами `task → pr 🔒 → ci 🔒` без вопроса; цепочка идёт без остановки до конца плана (паузы — только гейты)

#### Scenario: типовой набор как макрос

- **WHEN** задание говорит «профиль feature», в `ship-kit.workflows.md` есть макрос
- **THEN** перечень разворачивается из макроса и подтверждается одним блоком, как обычный чек-лист

### Requirement: Архивация прогона и worktree

Завершённый прогон MUST архивироваться по команде человека
(«архивируй прогон <КЛЮЧ>») или по предложению при закрытии плана:
каталог прогона переносится в `<корень прогонов>/archive/<КЛЮЧ>/`,
корень — по каскаду директории прогона: определённая директория —
`archive/` рядом (`<директория>/archive/<ПРОЕКТ>/<КЛЮЧ>/`); дефолт —
временный корень `.qwen/tmp/ship-kit/archive/<КЛЮЧ>/` с честной
пометкой в отчёте «временный». Worktree прогона — имя
`<ПРОЕКТ>-<КЛЮЧ>`, соответствие в plan.md. Выбор человека по
worktree: удалить (гейт, ветки не трогаются) или `git worktree move`
в архив прогона; отказ от удаления архивацию не отменяет.

#### Scenario: архивация с удалением worktree

- **WHEN** план закрыт, человек на вопрос о worktree выбрал «удалить» и подтвердил гейт
- **THEN** каталог прогона перенесён в архив по каскаду (определённая директория — `<директория>/archive/<ПРОЕКТ>/<КЛЮЧ>/`, дефолт — `.qwen/tmp/ship-kit/archive/<КЛЮЧ>/`), worktree удалён (git worktree remove); ветки прогона остались

#### Scenario: worktree перенесён в архив

- **WHEN** человек отказался удалять worktree
- **THEN** архивация прогона продолжается, worktree перенесён внутрь архива прогона (git worktree move), регистрация worktree сохранена

#### Scenario: имена узнаваемы

- **WHEN** прогон создан и использует worktree
- **THEN** имя worktree содержит проект и ключ (`<ПРОЕКТ>-<КЛЮЧ>`), директория прогона — из каскада; принадлежность видна из листинга

### Requirement: Сомнение возобновления — вопрос закрытыми опциями

Если следующий шаг не определяется однозначно — несколько незакрытых
слотов без ясного порядка, план расходится с фактическим состоянием,
прогон с ключом не найден — вызванный скилл MUST задать **один**
вопрос с закрытыми опциями: кандидатами выступают слоты плана,
«назвать другой ключ», «начать новую задачу». Молчаливый выбор и
перебор вариантов без вопроса запрещены.

#### Scenario: несколько незакрытых слотов

- **WHEN** в плане два незакрытых слота и порядок между ними не ясен из плана и git
- **THEN** вызванный скилл задаёт один вопрос закрытыми опциями с кандидатами-слотами; продолжает по выбранной опции

#### Scenario: ключ не найден

- **WHEN** план-файла по каскаду директории прогона не существует
- **THEN** вызванный скилл спрашивает закрытыми опциями: назвать другой ключ или начать новую задачу; молчаливый старт нового прогона не выполняется

## REMOVED Requirements

### Requirement: Состояние прогона — plan.md и issues.md

**Reason**: Правило путей заменено каскадом директории прогона
(задание → конвенция → дефолт `.qwen/tmp/ship-kit/<КЛЮЧ>/`), а
легаси-поддержка не нужна: комплект не публиковался, внешних
прогонов со старыми путями (`runs/<ПРОЕКТ>/<КЛЮЧ>/`,
`skill-runs/<КЛЮЧ>/`) и журналами без дат не существует (решение
человека 2026-11-24). Замена — три требования: «Директория прогона —
каскад с временным дефолтом», «Чек-лист и журнал план-файла», «Токен
возобновления и статусы из MCP».
**Migration**: Нет: прогоны до v3 существовали только на dev-машине
в тест-контуре; путь `runs/` при желании задаётся конвенцией проекта
как обычная определённая директория.

# base-skills Specification

## Purpose

Три скилла-фазы базового комплекта ship-kit — `task` (разработка), `pr`
(доставка), `ci` (сборка/деплой CI) — переписанные с нуля по решётке
«методология + файловый контракт»: без конфигурации проекта, без
прозаического движка, единица работы — фаза.

## Requirements

### Requirement: Три скилла-фазы с говорящими именами

Комплект MUST поставлять ровно три скилла: `task` — контекст задачи и
правки кода (спецификация изменения — опциональный путь), `pr` — рабочая ветка,
пуш, PR и цикл замечаний, `ci` — запуск и ожидание джоб CI с
диагностикой падений. Description каждого скилла MUST содержать только
«когда использовать» с триггерами вызова, без словаря конвейера.
Закрытый слот плана прогона MUST продолжаться следующим незакрытым
слотом **без остановки** (цепочка авторизована планом; паузы — только
🔒-гейты и вопросы правил; конец плана — стоп). Одиночный вызов скилла
человеком вне плана выполняется без цепочки. Тексты поставки MUST
обращаться к MCP по ролям, не по именам конкретных продуктов; роли на
серверы мапит конвенция проекта. Канонические роли: **tracker** (трекер
задач), **docs** (вики/runbook), **repo** (репозиторий и PR), **build**
(сборка), **deploy** (деплой), **quality** (качество кода), **vuln**
(уязвимости/сканирование), **chat** (чаты/мессенджеры).

#### Scenario: правка по тикету

- **WHEN** человек вызывает `/ship-kit:task возьми PRJ-42, mcp-tracker=tasks`
- **THEN** task собирает контекст, оформляет изменение (или правит напрямую — по весу задания), коммитит и сразу продолжает следующим слотом плана — `pr` с карточкой «пуш+PR»

#### Scenario: имя продаёт вызов

- **WHEN** человек читает description скилла, не открывая SKILL.md
- **THEN** из description понятно, какой скилл звать: «возьми задачу» → task, «отправь на ревью» → pr, «запусти сборку» → ci

#### Scenario: одиночный вызов вне плана

- **WHEN** человек зовёт один скилл для одиночного шага (например «проверь PR» или «дай лог»)
- **THEN** выполняется только этот вызов, цепочка не тянется

### Requirement: Инструмент спекирования не вшивается

Комплект MUST NOT фиксировать имя или формат инструмента спекирования
ни в одном поставляемом файле (скиллы, QWEN.md, docs); контракт
комплекта — только слот **spec** («Слоты переменных скиллов»). Полный
путь `task` оформляется исполнителем слота `spec`, найденным каскадом
задание > конвенция проекта > метки скиллов сессии; ноль кандидатов —
мини-дизайн в чате, несколько — один вопрос. **Конвенция проекта
сильнее умолчания скилла**: может обязывать спецификацию (полный путь
всегда, лёгкого пути нет), назначать слот или перечислять кандидатов
без выбора одного (набор — один вопрос человеку); задание сильнее
конвенции. Реализация идёт по чек-листу изменения независимо от формата
каталогов исполнителя.

#### Scenario: в проекте установлен спек-скилл

- **WHEN** задание просит спеку и один скилл сессии несёт метку `slot:spec`
- **THEN** task оформляет изменение этим скиллом по его собственным правилам; отчёт упоминает использованный инструмент как факт, не как настройку

#### Scenario: спек-скилла нет

- **WHEN** задание просит спеку, метки `slot:spec` нет ни у одного скилла сессии
- **THEN** task делает мини-дизайн в чате и честно отмечает в отчёте отсутствие исполнителя слота

#### Scenario: смена инструмента спекирования

- **WHEN** в проекте спек-скилл с меткой `slot:spec` заменён другим скиллом с той же меткой
- **THEN** файлы ship-kit не меняются: каскад входит новым исполнителем

#### Scenario: конвенция обязывает спеку

- **WHEN** конвенция проекта требует спецификацию для каждой задачи и назначает слот
- **THEN** task оформляет изменение до кода даже для мелкой правки, без собственного усмотрения; исполнитель — из конвенции

### Requirement: Порядок прогона с внешними скиллами

Комплект MUST NOT задавать порядок внешних скиллов сам. План прогона
`skill-runs/<КЛЮЧ>/plan.md` создаётся **всегда** при первом вызове фазы
по ключу. Задание перечислило внешние скиллы → `task` MUST собрать
чек-лист: скиллы в порядке перечисления + слоты фаз комплекта на
названных позициях (не названы — в хвосте доставки), показать одним
блоком и получить одно подтверждение. Не перечислило → план = фазы
комплекта по умолчанию (`task → pr 🔒 → ci 🔒`), без вопроса.
`ship-kit.workflows.md` — опциональный макрос типовых наборов,
разворачивается в перечень. Гейт создания PR = вход в `pr` на строке
слота.

#### Scenario: задание задаёт позицию гейта

- **WHEN** задание ставит слот `/ship-kit:pr` после трёх внешних скиллов
- **THEN** карточка «пуш+PR» показывается после завершения этих трёх шагов — не раньше и не позже

#### Scenario: порядок не назван

- **WHEN** задание перечислило скиллы без позиций слотов
- **THEN** task предлагает чек-лист одним блоком (скиллы по порядку перечисления, слоты доставки в хвосте) и ждёт одного подтверждения

#### Scenario: внешних скиллов нет

- **WHEN** задание не перечисляет внешних скиллов
- **THEN** план создаётся с дефолтными фазами `task → pr 🔒 → ci 🔒` без вопроса; цепочка идёт без остановки до конца плана (паузы — только гейты)

#### Scenario: типовой набор как макрос

- **WHEN** задание говорит «профиль feature», в `ship-kit.workflows.md` есть макрос
- **THEN** перечень разворачивается из макроса и подтверждается одним блоком, как обычный чек-лист

### Requirement: Работа без конфигурации проекта

Всё необходимое скиллы получают аргументами вызова: MCP-алиасы, имена
джоб, стенды, ветки. Формат алиаса: `mcp-<роль>=<сервер>`; **одна роль
может иметь несколько MCP** — серверы перечисляются через запятую
(`mcp-tracker=jira1,jira2`): все перечисленные рабочие, чтение идёт по
всем, запись — в названный заданием сервер, не назван — один вопрос.
Аргументы MUST разрешаться лесенкой: **задание > конвенция проекта >
один вопрос человеку**. Конвенция проекта — обычный контекст сессии
(файлы проекта, например файл проектов); комплект MUST NOT требовать её,
фиксировать имя или формат. После конвенции недостающее скилл MUST
запросить у человека. Комплект MUST NOT требовать реестра, манифеста
или иного файла конфигурации. Сканирование серверов и перебор
джоб/путей («поиск») запрещён.

#### Scenario: алиасы переданы вызовом

- **WHEN** вызов содержит `mcp-tracker=jira-corp, mcp-repo=bb`
- **THEN** скилл работает ровно с этими серверами и не читает никаких файлов конфигурации

#### Scenario: одна роль — несколько MCP

- **WHEN** алиас роли перечисляет несколько серверов (`mcp-chat=telegram,whatsapp`)
- **THEN** скилл считает рабочими оба: чтение по всем, запись — куда названо заданием; не названо — один вопрос

#### Scenario: алиасы не названы, конвенция проекта есть

- **WHEN** задание не назвало алиасы, но конвенция проекта их содержит
- **THEN** алиасы берутся из конвенции без вопроса; источник отмечается в отчёте

#### Scenario: не хватает аргумента джобы

- **WHEN** задание просит запустить сборку, имя джобы не названо ни в задании, ни в конвенции
- **THEN** ci спрашивает у человека; перечисление джоб сервера не выполняется

### Requirement: Каскад конвенции — репо-файл мастер, каталог индекс

Когда конвенция проекта представлена несколькими источниками — файлом
проекта в репозитории и центральным каталогом проектов, — разрешение
MUST идти каскадом: **задание > файл проекта в репо (cwd) > центральный
каталог > один вопрос**. Запись проекта руками правится ТОЛЬКО в
репо-файле (мастер); центральный каталог — автособираемый индекс,
ручные правки в нём запрещены, он пересобирается из репо-файлов.
Коллизия одинаковых имён проектов между источниками MUST разрешаться
в пользу репо-файла; дубликат внутри самого каталога — ошибка сборки
индекса, фиксируемая генератором. Имя файла и формат записи комплект
MUST NOT фиксировать.

#### Scenario: сессия внутри репо проекта

- **WHEN** cwd — репозиторий со своим файлом проекта и существует центральный каталог
- **THEN** аргументы берутся из репо-файла без обращения к каталогу; источник отмечается в отчёте

#### Scenario: cwd вне репо, каталог знает проект

- **WHEN** задание назвало проект, cwd — не его репозиторий, central каталог содержит запись
- **THEN** аргументы берутся из записи каталога; источник отмечается в отчёте

#### Scenario: одно имя в двух источниках

- **WHEN** репо-файл и каталог содержат записи одного проекта с разным содержимым
- **THEN** действует репо-файл; расхождение отмечается в отчёте

#### Scenario: дубликат в каталоге

- **WHEN** генератор индекса находит одно имя проекта в двух репо-файлах
- **THEN** сборка индекса завершается ошибкой с именем проекта и путями источников; индекс не обновляется

#### Scenario: правка записи проекта

- **WHEN** нужно изменить конфигурацию проекта
- **THEN** правка делается в репо-файле, индекс пересобирается генератором; ручная правка индекса запрещена

### Requirement: Клон проекта из записи

Разрешённая запись проекта называет адрес репозитория (SSH), а cwd
сессии не является этим репозиторием → `task` MUST склонировать
репозиторий в рабочую папку сессии и вести фазу в клоне; фазы `pr` и
`ci` работают в том же клоне. Авторизация — учётные данные машины
(SSH-ключи), вопросов человеку не вызывает; клон — локальное обратимое
действие, гейтом не оформляется. cwd уже репозиторий записи — клон не
выполняется. Клон не удался (нет доступа, transport-повторы исчерпаны)
— честная ошибка и стоп.

#### Scenario: сессия вне репо проекта

- **WHEN** запись проекта называет git@git.corp:team/calc.git, cwd — рабочая папка сессии
- **THEN** task клонирует репозиторий и работает в клоне; клон отмечается в отчёте

#### Scenario: cwd уже репозиторий записи

- **WHEN** cwd — клон или checkout репозитория из записи проекта
- **THEN** клон не выполняется, работа идёт в cwd

#### Scenario: нет доступа к репозиторию

- **WHEN** SSH-доступ машины к репозиторию отсутствует, транспортные повторы исчерпаны
- **THEN** честная ошибка и стоп; фаза не продолжается в другом месте

### Requirement: Единица работы — фаза

Один вызов MUST проходить фазу целиком по внутреннему чек-листу скилла:
один Шаг-0 (проверка переданных MCP лёгкими вызовами), основная работа,
один контракт отчёта в конце. Промежуточные микрошаги с собственными
отчётами/проверками MCP MUST NOT выделяться.

#### Scenario: task проходит фазу одним вызовом

- **WHEN** задача требует контекст, спеку и реализацию
- **THEN** task выполняет всё в одном вызове и отчитывается один раз в конце

#### Scenario: MCP недоступен на Шаге-0

- **WHEN** лёгкая проверка переданного MCP провалилась
- **THEN** скилл возвращает блок ошибки с симптомом и рекомендациями и останавливается, не начиная основную работу

### Requirement: Гейты необратимого — три правила

Необратимые действия — пуш ветки, создание PR, запуск джобы — MUST
оформляться тремя правилами: (1) карточка-превью (действие, ветка,
параметры) показывается человеку до применения; (2) применение — только
после явного «да»; отказ = стоп без перебора альтернатив; (3) дословное
«подтверждаю …» в задании равносильно подтверждению (pre-approved).
Семантика наследования подтверждений между карточками MUST NOT
использоваться. Когда в сессии доступен инструмент вопроса с закрытыми
опциями, вопрос-гейт (карточка, подтверждение чек-листа плана, переспрос
повтора) MUST задаваться этим инструментом: согласие = выбор утвердительной
опции, отказ = выбор опции отказа; ответ свободным текстом вне опций
подтверждением не считается — ответь на содержание и переспроси один раз
тем же инструментом, затем стоп. Имя инструмента комплектом не фиксируется;
инструмента в сессии нет — действуют правила свободного текста без
изменений.

#### Scenario: карточка и подтверждение

- **WHEN** pr подготовил пуш ветки и создание PR
- **THEN** человеку показывается карточка с веткой, числом коммитов и целевой веткой; пуш выполняется только после явного «да»

#### Scenario: отказ останавливает

- **WHEN** человек ответил на карточку отказом
- **THEN** скилл останавливается с честным итогом и не предлагает альтернативные действия самовольно

#### Scenario: pre-approved дословной фразой

- **WHEN** задание содержит дословное «подтверждаю запуск сборки PRJ-42»
- **THEN** ci запускает джобу без повторного вопроса, отметив источник подтверждения в отчёте

#### Scenario: гейт спрашивается структурным вопросом

- **WHEN** в сессии доступен инструмент вопроса с закрытыми опциями и pr показывает карточку «пуш+PR»
- **THEN** карточка задаётся этим инструментом; выбор утвердительной опции выполняет действие, выбор опции отказа останавливает фазу; свободный текст человека в ответ не трактуется как согласие

#### Scenario: текст вне опций — не подтверждение

- **WHEN** человек ответил текстом вне утвердительной опции (поле свободного ввода), без выбора опции
- **THEN** действие не выполняется: скилл отвечает на содержание ответа и один раз переспрашивает карточку тем же инструментом; повторный не-выбор опции — стоп

#### Scenario: инструмент вопроса недоступен

- **WHEN** сессия идёт без инструмента закрытых опций (headless-прогон, чисто текстовый канал)
- **THEN** гейт работает по правилам свободного текста без изменений

### Requirement: Повтор упавшей джобы

Повтор той же упавшей джобы с теми же параметрами (таймаут/flaky) скилл
MUST предлагать переспросом одной строкой, без новой карточки-разбора;
без подтверждения повтор MUST NOT выполняться. Более одного повора
подряд без изменения подхода MUST NOT выполняться.

#### Scenario: таймаут джобы

- **WHEN** ожидание завершилось таймаутом, параметры неизменны
- **THEN** ci спрашивает одной строкой «повторить те же параметры?» и повторяет только после «да»

### Requirement: Диагностика падений джоб CI внутри ci

При падении джобы ci MUST разбирать лог: первая настоящая ошибка
(причина отделена от последствий), категория, fixable (правится ли
правкой кода/конфига репозитория), fixHint. Детали трактовки по kind
сборки MUST браться из kind-файла (build/deploy) внутри скилла. Диагноз
fixable MUST завершаться handoff-строкой на `task` (fix); не-кодовые
падения MUST фиксироваться задачей в issues.md с эскалацией человеку;
правки репозитория в ci запрещены.

#### Scenario: fixable падение сборки

- **WHEN** сборка упала, диагноз — ошибка компиляции в коде репозитория
- **THEN** отчёт ci содержит категорию, fixable: true, fixHint и handoff-строку на task; правка не выполняется в этом вызове

#### Scenario: инфраструктурное падение деплоя

- **WHEN** деплой упал по категории infra
- **THEN** ci пишет задачу в issues.md и останавливается, предлагая эскалацию человеку

### Requirement: Маршрут фикса по связанности с задачей

Диагноз fixable MUST классифицироваться по связанности с изменением
задачи: связанный фикс (первопричина в диффе ветки задачи) выполняется
в ветке задачи и доставляется пушем в тот же PR; посторонний
(первопричина вне диффа) — в отдельной технической ветке, срезанной от
базовой, отдельным PR. Посторонние правки MUST NOT изменять артефакты
спеки проекта.

#### Scenario: посторонняя поломка сборки

- **WHEN** сборка ветки задачи упала из-за ошибки в CI-скрипте, не входящего в дифф задачи
- **THEN** фикс делается в отдельной технической ветке от базовой, отдельным PR; артефакты спеки не изменяются, бизнес-PR остаётся чистым

#### Scenario: ошибка в коде задачи

- **WHEN** сборка упала на строке, добавленной веткой задачи
- **THEN** фикс идёт в ветку задачи и доставляется пушем в тот же PR

### Requirement: Дисциплина верификации отчётов

Итоговое `OK: true` скилл MUST подкреплять дословными свежими
доказательствами в отчёте (последние строки прогона, статусы, ответы
MCP). Без свежих доказательств скилл MUST NOT заявлять успех.

#### Scenario: успех с доказательствами

- **WHEN** task завершил правку с зелёным локальным прогоном
- **THEN** отчёт содержит дословные последние строки прогона перед `OK: true`

### Requirement: Границы необратимого

Пуш MUST выполняться только в рабочие ветки вида `<X>/<КЛЮЧ>`; целевые
ветки (main/master/develop/release, база PR) MUST NOT пушиться —
несоответствие выявляется до любых действий. Замечания открытого PR
MUST правиться пушем в тот же PR; новый PR — только на новый фикс.
Статусы задач Jira MUST NOT меняться никем из скиллов.

#### Scenario: попытка пуша в целевую ветку

- **WHEN** в карточке пуша ветка совпадает с целевой (main)
- **THEN** скилл отказывает до любых действий с объяснением запрета

#### Scenario: замечание ревью

- **WHEN** на открытый PR пришло замечание
- **THEN** pr отвечает на комментарий и пушит фикс в ту же ветку; новый PR не создаётся

### Requirement: Состояние прогона — plan.md и issues.md

Межвызовное состояние прогона MUST жить в
`runs/<ПРОЕКТ>/<КЛЮЧ>/plan.md`: чек-лист фаз (счётчик попыток — числом
в строке), текущая фаза, журнал, открытые вопросы. Каждая запись
журнала MUST начинаться с даты и времени — `ГГГГ-ММ-ДД ЧЧ:ММ`
(локальное время машины), затем событие; записи без даты и времени
MUST NOT писаться. Легаси-журналы без дат читаются как есть, не
переписываются. `<ПРОЕКТ>` разрешается из конвенции проекта (файл
проектов), иначе — имя каталога репозитория (cwd/клона); имя проекта
комплектом не фиксируется. План создаётся при первом вызове фазы по
ключу — всегда, включая прогоны без внешних скиллов (слоты фаз
комплекта по умолчанию); слот `ci` открывается после MERGED PR.
Возобновление проверяет и легаси `skill-runs/<КЛЮЧ>/` (только чтение,
новые прогоны создаются только в `runs/`). Статусы PR и джоб MUST
браться из свежих ответов MCP: слова человека — не статус; при
расхождении (человек говорит MERGED, MCP показывает OPEN) `pr` MUST
спросить: ждать MERGED или собрать на рабочей ветке; сборка на рабочей
ветке разрешена только после явного «да», и такой слот помечается в
плане **⚠ (жёлтым — успех на неподтверждённой базе)**, не зелёным.
Файл MUST быть токеном возобновления: после паузы скилл читает план,
сверяется с фактическим состоянием (git, статусы PR/джоб) и
продолжает. Провалы MUST фиксироваться задачами в
`runs/<ПРОЕКТ>/<КЛЮЧ>/issues.md`.

#### Scenario: возобновление после паузы

- **WHEN** человек возвращается с «продолжи PRJ-42»
- **THEN** скилл читает plan.md, сверяет фактическое состояние и продолжает с зафиксированной фазы, не переспрашивая сделанное

#### Scenario: слова против статуса

- **WHEN** человек говорит «смержил», а свежий get_pr показывает OPEN
- **THEN** pr не закрывает слот зелёным и спрашивает: ждать MERGED или собирать на рабочей ветке; при «да» карточка запуска ci фиксирует рабочую ветку и её источник, слот помечается ⚠

#### Scenario: прогон привязан к проекту

- **WHEN** два проекта имеют прогон с одинаковым ключом X-1
- **THEN** прогоны лежат раздельно и узнаваемы из листинга: `runs/<проект1>/X-1/` и `runs/<проект2>/X-1/`

#### Scenario: легаси-каталог skill-runs

- **WHEN** план прогона существует только в старом `skill-runs/<КЛЮЧ>/plan.md`
- **THEN** возобновление читает его оттуда; новые записи и новые прогоны создаются только в `runs/<ПРОЕКТ>/<КЛЮЧ>/`

#### Scenario: запись журнала с даты и времени

- **WHEN** фаза фиксирует событие в журнал плана (создание плана, гейт, PR, запуск джобы, id своего комментария)
- **THEN** строка записи начинается с даты и времени `ГГГГ-ММ-ДД ЧЧ:ММ`, затем событие; записей без префикса не пишется

#### Scenario: легаси-журнал без дат

- **WHEN** возобновление читает план, чей журнал вёлся без даты и времени
- **THEN** старые записи читаются как есть, не переписываются; новые записи журнала идут с датой и временем

### Requirement: Транспортные сбои — автоматический повтор

Таймаут, обрыв соединения или сетевая ошибка вызова MCP или git-операции
MUST вызывать автоматический повтор того же вызова — до 2 повторов,
без вопросов человеку и без повторного гейта: действие уже авторизовано,
сбой состояния не изменил. Повторы исчерпаны — честная ошибка и стоп.
Повтор упавшей джобы CI — отдельное правило (переспрос одной строкой),
транспортные повторы его не отменяют.

#### Scenario: таймаут MCP-вызова

- **WHEN** вызов MCP упал по таймауту, состояние не изменилось
- **THEN** скилл повторяет вызов автоматически (до 2 раз) без вопроса; успех — работа продолжается, повторы отмечены в отчёте

#### Scenario: повторы исчерпаны

- **WHEN** вызов падает по транспорту трижды подряд
- **THEN** честная ошибка и стоп; в отчёте дословные ошибки и число попыток

### Requirement: PR — только после успешного пуша

Создание PR MUST следовать за успешным пушем рабочей ветки в remote.
Пуш не выполнен или невозможен (нет remote; отказ сети; транспортные
повторы исчерпаны) → стоп с ошибкой, PR НЕ создаётся — «PR в никуда»
запрещён. Отчёт фиксирует: пуш не выполнен, PR не создан.

#### Scenario: нет remote

- **WHEN** карточка «пуш+PR» подтверждена, но у репозитория нет git-remote и пуш упал
- **THEN** фаза pr останавливается с ошибкой; PR не создаётся; в плане слот остаётся незакрытым

### Requirement: Ожидание мержа PR

`pr` после создания PR текущего прогона (и при возобновлении до
открытия слота `ci`) MUST активно ждать MERGED: опрашивать статус PR
через MCP репозитория с интервалом по лесенке задание > конвенция
проекта > дефолт 10 секунд, без вопроса человеку. Опрос — чтение, гейт
не оформляется. Свежий MERGED из MCP MUST открывать следующий слот
плана (обычно `ci`) без вопроса. DECLINED → стоп с честной ошибкой,
провал — задачей в issues.md прогона.

#### Scenario: мерж наступил

- **WHEN** PR создан, очередной опрос (интервал 10 сек) вернул MERGED
- **THEN** слот `pr` закрывается зелёным, следующий слот плана (`ci`) вызывается без вопроса; в отчёте — дословный статус MERGED и URL PR

#### Scenario: интервал из задания

- **WHEN** задание назвало интервал опроса (`poll=30`)
- **THEN** опрос идёт каждые 30 секунд, дефолт не применяется, вопрос не задаётся

#### Scenario: PR отклонён

- **WHEN** опрос вернул DECLINED
- **THEN** честная ошибка и стоп; провал зафиксирован задачей в `skill-runs/<КЛЮЧ>/issues.md`; цепочка не продолжается

#### Scenario: транспортный сбой опроса

- **WHEN** очередной опрос статуса упал по таймауту
- **THEN** вызов повторяется автоматически (до 2 повторов) без вопроса и гейта; при успехе ожидание продолжается тем же интервалом

#### Scenario: возобновление ожидания

- **WHEN** человек вернулся с «продолжи PRJ-42» (или «дождись мержа PRJ-42»), план стоит на слоте `pr`, PR ещё OPEN
- **THEN** `pr` возобновляет опрос тем же интервалом, не переспрашивая сделанное; после MERGED — обычное продолжение по плану

#### Scenario: разовая проверка без ожидания

- **WHEN** человек вызывает `check` одиночным вызовом вне плана
- **THEN** возвращается текущее состояние PR без цикла ожидания

#### Scenario: ожидание стартует сразу, без вопроса

- **WHEN** PR создан (карточка «пуш+PR» уже подтверждена, PR существует)
- **THEN** первый опрос статуса выполняется сразу, разрешение на ожидание не спрашивается — ни вопросом, ни карточкой

### Requirement: Различение своих и чужих комментариев в PR

Когда агент и человек пишут в один PR под одной учёткой (одно имя
автора у комментариев), `pr` MUST различать своих и чужих маркером:
каждый комментарий агента завершается дословной строкой `[ship-kit]`;
id своих комментариев фиксируются в журнале плана прогона. Цикл
замечаний (fix) и подсчёт unresolved (check) MUST работать только с
чужими комментариями (без маркера): свои unresolved замечаниями не
считаются, ответы на свои комментарии не пишутся.

#### Scenario: подпись своего комментария

- **WHEN** pr отвечает на замечание ревью (add_comment)
- **THEN** комментарий агента завершается дословной строкой `[ship-kit]`, а его id фиксируется в журнале плана прогона

#### Scenario: свой unresolved — не замечание

- **WHEN** в PR есть unresolved-комментарий, завершающийся `[ship-kit]`
- **THEN** `check` не включает его в счёт замечаний, `fix` не отвечает на него и не пушит по нему фикс

#### Scenario: чужой unresolved — замечание

- **WHEN** в PR есть unresolved-комментарий без маркера `[ship-kit]`
- **THEN** это замечание: `check` показывает его в числе замечаний, `fix` отвечает на него и доставляет правку по действующим правилам

### Requirement: Архивация прогона и worktree

Завершённый прогон MUST архивироваться по команде человека
(«архивируй прогон <КЛЮЧ>») или по предложению при закрытии плана:
каталог переносится в `runs/archive/<ПРОЕКТ>/<КЛЮЧ>/`. Worktree
прогона — имя `<ПРОЕКТ>-<КЛЮЧ>`, соответствие в plan.md. Выбор
человека по worktree: удалить (гейт, ветки не трогаются) или
`git worktree move` в архив прогона; отказ от удаления архивацию не
отменяет.

#### Scenario: архивация с удалением worktree

- **WHEN** план закрыт, человек на вопрос о worktree выбрал «удалить» и подтвердил гейт
- **THEN** каталог прогона перенесён в `runs/archive/<ПРОЕКТ>/<КЛЮЧ>/`, worktree удалён (git worktree remove); ветки прогона остались

#### Scenario: worktree перенесён в архив

- **WHEN** человек отказался удалять worktree
- **THEN** архивация прогона продолжается, worktree перенесён внутрь архива прогона (git worktree move), регистрация worktree сохранена

#### Scenario: имена узнаваемы

- **WHEN** прогон создан и использует worktree
- **THEN** оба имени содержат проект и ключ: `runs/<ПРОЕКТ>/<КЛЮЧ>/` и worktree `<ПРОЕКТ>-<КЛЮЧ>` — принадлежность видна из листинга каталогов

### Requirement: Детектор дрейфа версии комплекта

План прогона MUST хранить строку версии комплекта
`ship-kit: <версия>` (источник — поле `version` манифеста
`qwen-extension.json` два уровня выше базового каталога скилла,
относительный путь, без поиска). Шаг-0 `task` MUST сверять строку
плана с манифестом; при расхождении строка обновляется и в отчёт
добавляется одна строка со ссылкой на рецепты `docs/upgrade.md`.
Правки проектных конфигов при дрейфе MUST NOT выполняться; смена
версии — не гейт.

#### Scenario: план создан со строкой версии

- **WHEN** task создаёт план прогона в проекте с доступным манифестом комплекта
- **THEN** план содержит строку `ship-kit: <версия>` с текущей версией манифеста

#### Scenario: комплект обновился между вызовами

- **WHEN** возобновление («продолжи <КЛЮЧ>») читает план со строкой `ship-kit: 2.0.0`, а манифест показывает 2.1.0
- **THEN** строка плана обновляется на 2.1.0, в отчёте одна строка «комплект обновился 2.0.0 → 2.1.0 …» со ссылкой на рецепты docs/upgrade.md; проектные конфиги не тронуты

#### Scenario: манифест недоступен

- **WHEN** базовый каталог скилла не содержит манифест на два уровня выше
- **THEN** строка версии не пишется и не сверяется, в отчёте пометка об отсутствии манифеста; работа продолжается

#### Scenario: легаси-план без строки версии

- **WHEN** Шаг-0 task читает план, созданный до появления строки версии
- **THEN** строка дописывается текущей версией манифеста; дрейф не фиксируется (не с чем сравнивать), сообщение о смене версии не выводится

### Requirement: Слоты переменных скиллов

Вызов переменного скилла MUST разрешаться слотом — нейтральной ролью;
канонический слот — **spec**. Имя исполнителя в файлах комплекта
MUST NOT упоминаться. Исполнитель заявляет слот литеральной меткой
`slot:<имя>` в description SKILL.md; подбор по смыслу описания MUST
NOT применяться. Разрешение — каскадом **задание > конвенция
проекта > метки скиллов сессии**: несколько кандидатов — один вопрос,
ноль — правило слота (spec → мини-дизайн). Неизвестные слоты MUST
игнорироваться.

#### Scenario: одна метка

- **WHEN** в списке скиллов сессии ровно один скилл несёт `slot:spec` в description
- **THEN** слот разрешается этим скиллом без вопроса; отчёт упоминает исполнителя как факт

#### Scenario: несколько меток

- **WHEN** два скилла сессии заявили `slot:spec`
- **THEN** комплект задаёт один вопрос с выбором исполнителя; угадывание и молчаливый выбор не выполняются

#### Scenario: метки нет — семантика не применяется

- **WHEN** ни одно описание скиллов сессии не содержит `slot:spec`, но одно «похоже по смыслу» на инструмент спекирования
- **THEN** смысл описания не трактуется: действует правило слота (мини-дизайн в чате), отсутствие исполнителя честно отмечается в отчёте

#### Scenario: неизвестный слот в метке

- **WHEN** description скилла содержит `slot:tuning`, которого нет в словаре комплекта
- **THEN** метка игнорируется без ошибки, работа продолжается

#### Scenario: конвенция назначает слот

- **WHEN** конвенция проекта назначает слот `spec` конкретному скиллу, а в сессии есть и скилл с меткой
- **THEN** каскад берёт назначение конвенции; метки сессии не сканируются

#### Scenario: конвенция перечисляет набор

- **WHEN** файл проектов перечисляет для слота `spec` несколько скиллов, не выбрав один
- **THEN** комплект задаёт человеку один вопрос с выбором из перечисленных; метки сессии не сканируются — конвенция сильнее

# Спека conveyor

# conveyor Specification

## Purpose

Диспетчер прогона: как скилл `run` ведёт конвейер стадий проекта — обход,
вызов позиций, обработка падений, фикс-циклы, ожидания, остановки и гейты.

## Requirements

### Requirement: Обход конвейера по стадиям

Скилл `run` MUST обходить стадии проекта в порядке `pipelineOrder` из
yaml-реестра. Фикс-стадии в обход не входят: вызываются по падению стадии
(`fixesStageId`) или по замечаниям PR (`triggeredBy`).

#### Scenario: полный прогон

- **WHEN** задание «полный прогон <тег>», проект calc (`pipelineOrder: [do, build, deploy]`)
- **THEN** run проходит do → build → deploy; каждый запуск джобы (включая каждый стенд) — через 🔒 гейт; итог SUCCESS только при зелёных сборке и всех стендах

#### Scenario: возврат после MERGED

- **WHEN** фикс-стадия получила MERGED своего PR
- **THEN** run продолжает обход со стадии `nextStageId` этой фикс-стадии (fixBuild → build; fixDeploy → build — пересборка, затем стенды заново)

#### Scenario: вход fixDo по замечаниям

- **WHEN** у PR-1 стадии do есть нерешённые замечания ревью, а у fixDo `triggeredBy: pullRequestReview`
- **THEN** run вызывает fixDo (позиции analyst, courier); замечания правятся пушем в тот же PR-1; кругов больше `maxFixAttempts` или DECLINED — задача в issues.md, стоп

### Requirement: Вызов позиций по kind стадии

Набор позиций стадии MUST определяться kind по манифесту комплекта (DO →
analyst, courier; BUILD/DEPLOY → operator; FIX_DO → analyst, courier;
FIX_BUILD → analyst, mechanic, courier; FIX_DEPLOY → mechanic, courier);
поле `positions` стадии может только сузить набор. Исполнители позиций
берутся из `executors` проекта (дефолты — скиллы комплекта). У фикс-стадии
после диагноза вызывается одна позиция: категория «код» → analyst, «не-код»
→ mechanic, если она есть у стадии.

#### Scenario: не-код с объявленной mechanic

- **WHEN** build упала, `doctor: diagnose` дал категорию «не-код», fixable, у fixBuild есть позиция mechanic
- **THEN** run вызывает исполнителя позиции mechanic (дефолт ship-kit:doctor в режиме fix): TDD-фикс, 🔒 карточка пуша, PR-2, MERGED → пересборка

#### Scenario: не-код без mechanic

- **WHEN** категория «не-код», а позиции mechanic у фикс-стадии нет
- **THEN** исход notFixable: задача в issues.md, прогон STOPPED

### Requirement: Исходы падения деплоя: WAIT и notFixable

После `doctor: diagnose` падения деплоя run MUST различать: fixable-правка
репозитория → фикс-стадия (PR-3); not-fixable категории infra/devops-known
(чинить вне репозитория) → WAIT — правок репозитория нет, PR не создаётся,
прогон и бюджет заморожены, возобновление «продолжи прогон <тег>» через 🔒
гейт; прочий notFixable → issues.md, STOPPED.

#### Scenario: деплой упал — инфраструктура

- **WHEN** deploy упал на стенде, категория `devops-known`
- **THEN** прогон WAIT («починка джобы»); после «продолжи прогон» — повтор деплоя через 🔒 гейт

### Requirement: Счётчики и loop guard по id стадии

Попытки, retry и строка плана MUST ключоваться id стадии, а не действием;
`maxRuns` — на стадию (деплой — на каждый стенд), `maxRetries` — повтор
flaky/таймаута без нового гейта. Круг фикс-цикла «фикс → PR → MERGED →
перезапуск» = +1 к `maxFixAttempts`; новый PR счётчик не сбрасывает;
исчерпан — STOPPED.

#### Scenario: две сборки с независимыми лимитами

- **WHEN** `pipelineOrder: [do, buildApp, buildLib, deploy]`, buildApp исчерпал `maxRuns`, очередь дошла до buildLib
- **THEN** buildLib запускается со своим независимым счётчиком попыток

#### Scenario: loop guard

- **WHEN** fixBuild прошёл третий круг «фикс → PR-2..N → MERGED → пересборка», а `maxFixAttempts: 2`
- **THEN** run останавливает прогон с задачей в issues.md, новой попытки фикса нет

### Requirement: Гейт-контракт prepare → confirm → apply

Необратимое действие (запуск джобы, пуш, создание PR) MUST выполняться в три
шага: исполнитель готовит карточку (payload: для джобы — kind, джоба, ветка,
стенд, параметры с источниками; для пуша — ветка, коммиты, суть; для PR —
ветка, база, описание) и не применяет; карточка-превью показывается человеку;
применение — отдельный вызов, только подтверждённой карточки. Нет «да» =
ничего не применено (fail-closed), отказ = STOPPED без молчаливых
альтернатив.

#### Scenario: отказ гейта

- **WHEN** человек ответил «нет» на карточку запуска джобы
- **THEN** вызова запуска нет; прогон STOPPED «гейт отклонён»; в плане карточка с исходом declined

### Requirement: Подтверждение привязано к карточке

`pre-approved(источник)` и `inherited(причина)` MUST действовать только для
идентичной карточки: flaky-повтор тех же параметров наследует гейт без
вопроса; изменение хотя бы одного параметра — новая карточка и новый вопрос.

#### Scenario: параметры изменились

- **WHEN** сборка #N была подтверждена, а после фикса запуск идёт с изменённым параметром
- **THEN** наследования нет — новая карточка, новый вопрос человеку

### Requirement: Вето проекта на категории диагноза

Категория из `errorPolicy.unfixableCategories` MUST блокировать запуск
фикс-стадии заранее, даже если диагноз помечает падение fixable.

#### Scenario: sonar под вето

- **WHEN** диагноз категории `sonar`, а `unfixableCategories: [infra, sonar]`
- **THEN** фикс-стадия не вызывается; прогон STOPPED с задачей в issues.md

# Спека registry

# registry Specification

## Purpose

Единственная точка ведения реестра `ship-kit.projects.yaml`: проекты, стадии,
записи знания, серверы и исполнители — и правила, по которым реестр считается
корректным.

## Requirements

### Requirement: Единая точка ведения yaml-реестра

Реестр MUST вестись только скиллом `registry`: `ship-kit.projects.yaml` в
корне проекта либо центральный `~/.qwen/ship-kit/projects.yaml`. Скиллы-роли
реестр не читают — значения им передают аргументами вызывающий (`run`) или
человек; отсутствие alias в записях проекта = «в этом проекте этого MCP нет».

#### Scenario: добавление проекта

- **WHEN** пользователь просит «добавь проект в реестр» и называет значения
- **THEN** registry создаёт проект с обязательными полями (projectKey, jiraProjectKey, repoSshUrl, artifactId), стадиями и записями знания; отсутствующие значения спрашивает, не выдумывает

#### Scenario: сверка серверов

- **WHEN** в endpoint указан `serverId`
- **THEN** registry сверяет его с `settings.json → mcpServers`; не найден — сообщает пользователю и не пишет значение молча

### Requirement: Валидация реестра при ведении

При каждом изменении registry MUST проверять правила 1–14 (design.md §11):
ссылочная целостность, роли ссылок по kind, транспорт
`diagnosisRef`/`repairRef`, модели `runnerKind`, стенды, полнота фикс-стадий,
`pipelineOrder`, покрытие исполнителей записи, `servers:`, `executors:` и
`positions` против манифеста позиций.

#### Scenario: висячая ссылка стадии

- **WHEN** у fixBuild указан `fixesStageId: buld` (опечатка)
- **THEN** registry отказывается сохранять и показывает ошибку ссылки

#### Scenario: диагност без транспорта стадии

- **WHEN** запись `diagnosisRef` стадии deploy не содержит `MCP_DEPLOY` или называет другую джобу
- **THEN** registry отклоняет изменение: лог упавшего деплоя нечем читать

#### Scenario: исполнителя нет в манифесте

- **WHEN** в `executors:` указана позиция, которой нет в манифесте комплекта
- **THEN** registry отклоняет изменение; внешний скилл на существующей позиции допускается с предупреждением «контракт проверяется e2e»

### Requirement: Версионирование и миграции формата реестра

Реестр MUST начинаться с `formatVersion`. При расхождении с поддерживаемой
комплектом версией registry MUST предлагать управляемую миграцию (цепочка
миграций из комплекта, дифф, применение только после подтверждения
пользователя) либо останавливаться без правок файла, если реестр новее
комплекта.

#### Scenario: реестр старее комплекта

- **WHEN** yaml-реестр имеет `formatVersion` ниже поддерживаемой комплектом
- **THEN** registry показывает цепочку миграций и дифф; применяет только после подтверждения пользователя; миграция идемпотентна

#### Scenario: реестр новее комплекта

- **WHEN** `formatVersion` выше поддерживаемой комплектом
- **THEN** registry останавливается с сообщением «обновите комплект», файл не правится

### Requirement: Секция servers

serverId MUST описываться в верхнеуровневой `servers:` (id → назначение);
адреса, URL и токены в реестре не хранятся — подключение остаётся в
`settings.json → mcpServers` за пользователем.

#### Scenario: смена адреса сервера

- **WHEN** у CI-сервера сменился адрес
- **THEN** правится только `settings.json`; yaml-реестр не меняется (serverId неизменен), записи и стадии не трогаются

# Спека executors

# executors Specification

## Purpose

Словарь позиций (манифест комплекта), исполнители на позициях (дефолты
комплекта и подмена в проекте), режимы doctor и правила «спрашивать
человека»; как исполнители получают MCP и аргументы из записей знания стадий
и как правки репозитория уходят в pull request.

## Requirements

### Requirement: Манифест позиций

Комплект MUST поставлять манифест позиций (`docs/ship-kit.positions.yaml`):
для каждой позиции — контракт (шаг 0, формат отчёта, ask-правила) и версия
контракта; дефолтные наборы позиций по kind стадии. Комплект исполнителей не
подбирает сам (trust discovery-only) — только явная запись в `executors:`
проекта; SKILL.md исполнителей пишутся под контракт манифеста.

#### Scenario: состав словаря

- **WHEN** читается манифест комплекта
- **THEN** позиции: analyst (спека + правки кода), courier (ветка/PR/замечания), operator (запуск/ожидание джоб), detective (диагноз — служебная, вызывает run), mechanic (не-код фикс)

#### Scenario: подмена исполнителя в проекте

- **WHEN** проект пишет `mechanic: superpowers:refactoring` в `executors:`
- **THEN** стадии не меняются; валидатор даёт предупреждение «контракт проверяется e2e»; прогоны используют подменённого исполнителя на позиции mechanic

### Requirement: Скиллы-исполнители комплекта (Профессии, 7)

Комплект MUST поставлять исполнителей: **analyst** (контекст Jira/Confluence/
mmap + оформление изменения OpenSpec + правки кода), **courier** (ветка,
коммиты, PR, цикл замечаний), **operator** (запуск/ожидание джоб), **doctor**
с режимами `diagnose` (только чтение: категория, rootCause, fixable,
fixHint, knownIssues, confidence) и `fix` (TDD-фикс, 🔒 карточка пуша, push);
режим задаёт вызывающий, doctor сам не переключает. `run`, `registry`,
`adapt-kit` — без переименования.

#### Scenario: диагноз и фикс одним doctor

- **WHEN** build упала, run вызывает doctor (режим diagnose), затем fixBuild вызывает исполнителя mechanic (дефолт doctor в режиме fix)
- **THEN** диагноз не передаётся аргументом между скиллами; режим fix читает `repairRef` и сверяет первопричину логом упавшей джобы

### Requirement: Исполнители получают MCP и джобы из записи своей стадии

Исполнители MUST получать свои MCP и аргументы запуска из записи знания
своей стадии (передаёт вызывающий): позиции стадии — `knowledgeRef`,
`doctor: diagnose` — `diagnosisRef`, `doctor: fix` — `repairRef`; ссылка
отсутствует или null — читается `knowledgeRef` стадии. Исполнители реестр не
читают и серверы сами не выбирают (шаг 0, блок ошибки при недоступном MCP).

#### Scenario: диагностика с runbook

- **WHEN** build упала и run вызывает doctor (режим diagnose)
- **THEN** doctor получает MCP из `diagnosisRef` (транспорт стадии + sonar/jira/confluence) и читает runbook и тикеты команды, которых нет в записи самой стадии

#### Scenario: фикс сверяет упавшую джобу

- **WHEN** fixBuild вызывает mechanic (doctor, режим fix)
- **THEN** фикс сверяет первопричину логом упавшей джобы из `repairRef` (jobName=calc-app), а не быстрой ci-джобой записи стадии

### Requirement: Ask-правила позиции

SKILL.md каждого исполнителя MUST начинаться таблицей правил: запуск джобы —
ask · всегда; пуш — ask · всегда; создание PR — ask · всегда; flaky-повтор —
inherited, только идентичная карточка; чтение (статус/лог/тикеты) — allow;
всё сверх переданных MCP — deny.

#### Scenario: чтение без вопроса

- **WHEN** operator в режиме ожидания опрашивает статус джобы
- **THEN** чтение выполняется без гейта; в отчёте статус, errorSnippet, logTail

### Requirement: Производный kind для knowledge-пака

Ролям транспорта MUST передаваться kind=build|deploy, производный из kind
стадии: BUILD/FIX_BUILD → build, DEPLOY/FIX_DEPLOY → deploy; командные файлы
knowledge-пака (`build.md`/`deploy.md` в doctor) читаются только своего kind.
Для DO/FIX_DO роли транспорта не вызываются — их падение идёт в issues.md
без диагноза.

#### Scenario: фикс деплоя читает deploy-файл

- **WHEN** fixDeploy вызывает mechanic (doctor, режим fix)
- **THEN** doctor читает командный файл деплоя, а не сборки

### Requirement: PR только через владельца позиции

Правки репозитория MUST уходить в PR только через исполнителя позиции
`pullRequestOwner` стадии (обычно courier): 🔒 карточка «пуш+PR», замечания —
пушем в тот же PR, новый PR — только на новый фикс после упавшей джобы и
только при реальной правке репозитория. Прямого пуша без PR нет; пуш — только
в рабочие ветки `<X>/<КЛЮЧ>`, целевые ветки (`defaultBranch`, база PR)
запрещены.

#### Scenario: фикс сборки через PR-2

- **WHEN** fixBuild внёс правку по диагнозу
- **THEN** courier создаёт PR-2 в рабочую ветку после 🔒 карточки; замечания правятся пушем в тот же PR-2

#### Scenario: стадия без правок репозитория

- **WHEN** стадия build/deploy исполняется (`pullRequestOwner: null`)
- **THEN** PR не создаётся; решение падения — фикс-стадия или починка джобы

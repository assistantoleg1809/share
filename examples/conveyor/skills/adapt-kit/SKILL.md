# Правила доработки комплекта ship-kit

Действуют при любой правке эталона (`extensions/ship-kit`) и в проектных
копиях. Приоритет — скилл-контур. Перед правкой ответь на три вопроса:

1. Я меняю **точку адаптации** или **методику**?
2. Не ломаю ли **инвариант**?
3. Изменение **универсальное или проектное**?

## 1. Точки адаптации — где живут проектные детали

Проектные детали **никогда не вносятся в тела скиллов**. Их законные места:

- **Реестр** `ship-kit.projects.md` (ведение — скилл `registry`): стадии и
  их kind, записи знания (alias → serverId, джобы, стенды), `servers:`,
  `executors:` (подмены исполнителей позиций), лимиты, политики ошибок.
  Схема — [docs/ship-kit.projects.example.md](../docs/ship-kit.projects.example.md).
- **Манифест позиций** `docs/positions.md`: словарь позиций,
  наборы по kind (`kindPositions`), маршрутизация фиксов (`fixRouting`),
  дефолтные исполнители. Историческая связка с `formatVersion++` реестра
  (yaml-эпоха) не применяется: md-формат не версионируется.
- **Аргументы вызова**: kind (build/deploy), номер джобы, ветка, целевая
  ветка, стенд, диагноз предыдущего шага, подтверждение из задания.
- **`settings.json → mcpServers`** проекта (адреса/токены серверов) — за
  пользователем.

Скилл-исполнитель не знает о реестре и манифесте: что ему передали
аргументами, тем и работает.

## 2. Инварианты — нельзя ломать

1. **Один скилл — одна область знания, один вызов — один шаг.** Режимы
   законны (doctor: diagnose|fix; ci: запуск|ожидание; pr:
   implement|check|fix) — режим задаёт вызывающий, скилл сам не
   переключается.
2. **MCP — только из аргументов вызова.** Скилл не выбирает сервер, не
   читает реестр. Alias не передан — «в проекте этого MCP нет»: работать без
   него и отметить в отчёте.
3. **Ничего не искать.** Не сканировать CI, не перечислять джобы, не
   угадывать пути; источники — реестр, args, история успешной джобы, ответ
   пользователя.
4. **Исполнителей не подбирать** (trust discovery-only): только `executors:`
   проекта или дефолты манифеста; комплект ничего не «находит» сам.
5. **Командные файлы kind обязательны и взаимоисключающие** (doctor:
   `build.md`/`deploy.md`, внутри — секции своего режима).
6. **Формат отчёта — контракт.** Отчёт читают человек и `run`; изменил поле —
   синхронно проверь вызывающих.
7. **Явный вызов не тянет цепочку.** «Соседние шаги» — навигация для
   человека; цепочку ведёт только `run`.
8. **Push только в рабочие ветки `<X>/<КЛЮЧ>`**; целевые ветки
   (`defaultBranch`, база PR) запрещены; правки репозитория — только через
   PR (pullRequestOwner, обычно pr); статусы Jira не трогать.
9. **Шаг 0 обязателен**: лёгкая проверка переданного MCP с внятным блоком
   ошибки и остановкой.
10. **Гейт-контракт prepare → confirm → apply**: карточка = payload с
    превью; fail-closed (нет «да» = ничего не произошло); подтверждение
    привязано к карточке — изменение payload = новый вопрос; flaky-повтор
    идентичной карточки наследует гейт. Отказ гейта = стоп прогона.
11. **Loop guard**: круг «фикс → PR → MERGED → перезапуск» = +1 к
    `maxFixAttempts`; новый PR счётчик не сбрасывает.
12. **Счётчики и план ключуются id стадии**, не действием; wait-исходы —
    только через диагноз (WAIT у деплоя = infra/devops-known; прочие —
    issues.md).
13. **Новые скиллы** — по методике writing-skills (baseline-сценарий «без
    скилла» до написания; описание — только условия срабатывания; проверка
    прогоном на glm-5.3-flash).
14. **Смена формата реестра/словаря позиций** — историческая механика
    yaml-эпохи (`formatVersion++` + миграция); в md-формате изменение
    формата — коммит с описанием, без версионирования.

## 3. Универсальный или проектный

Транспорт CI — **контракт трёх операций** (запуск/статус/лог), не бренд:
`runnerKind: JENKINS` (jobFolder+jobName) или `CUSTOM` (jobParameters);
точные имена инструментов — `toolNames` записи. CI-специфика (эскалации,
источники, известные проблемы) — в командных файлах knowledge-пака
(`doctor/build.md`/`deploy.md`), не в телах скиллов.

Проект подходит под универсальные скиллы, если: CI даёт контракт трёх
операций; роли MCP сводятся к закрытому набору alias; операции линейны; пуш
в рабочие ветки разрешён. Иначе — проектный вариант:

1. CI-транспорт без контракта / другая гранулярность — проектная версия
   ci с тем же форматом отчёта + свой knowledge-пак.
2. Другая роль MCP (нет Jira/Confluence) — проектные task/doctor, не
   переименование alias.
3. Особые политики (запрет push, коммиты ботом) — проектные pr/doctor.
4. Особый исполнитель позиции — не правка комплекта: `executors:` в реестре
   проекта (+ предупреждение валидатора, контракт проверяется e2e).

Правила сосуществования: универсальные скиллы из проекта не правятся;
проектный скилл — новый каталог с префиксом проекта/транспорта; фича идёт в
эталон, только если полезна ≥2 проектам и без проектных деталей.

## 4. Порядок доработки

1. Реши уровень: эталон или проектный (сомневаешься — проектный).
2. Эталон: правка скилла/манифеста → синхронизация вызывающих формата
   отчёта → docs → статические проверки `tests/run_checks.sh` примера
   зелёные → e2e-проверка (glm-5.3-flash) → коммит.
3. Формат реестра или словарь позиций изменились → правка схемы-примера
   одним коммитом (миграции yaml-эпохи не применяются).

# registry — ведение md-реестра проектов

Единственная точка изменений `ship-kit.projects.md`: проекты, стадии,
записи знания, `servers:`, `executors:`, лимиты, миграции формата. Скиллы-
исполнители реестр не читают — его читает вызывающий (человек или `run`),
чтобы передавать alias→сервер и джобы аргументами.

## Где файл

Цепочка поиска (первый найденный — рабочий):

1. `ship-kit.projects.md` в корне проекта;
2. `~/.qwen/ship-kit/projects.md` (центральный, на несколько проектов).

Файла нет — спроси, где создавать, и создай по схеме
[docs/ship-kit.projects.example.md](../docs/ship-kit.projects.example.md).

## Шаг 0 — формат файла (обязателен)

Файл в md-формате. Историческая механика версионирования yaml-эпохи
(`formatVersion` + цепочка миграций) не применяется: md-реестр не
версионируется, изменения видны в git-истории файла. Найден устаревший
yaml-файл — предложи конвертацию по схеме примера, применяй только
после явного подтверждения пользователя.

## Протокол

1. Найди файл по цепочке; покажи, какой выбран.
2. Прочитай целиком. Структура: `defaultProject`,
   `servers:` (serverId → описание), `executors:` (позиция → скилл),
   `projects[]` (ключи проекта, `pipelineOrder`, `stages[]`, `knowledge[]`).
3. Внеси изменение (значения не выдумывай: сервер, джоба, КЭ, лимит — спроси,
   если их не назвали; не удаляй без явной команды).
4. Проверь схему и правила валидации (список ниже). Ошибка — не сохраняй,
   покажи; предупреждение — сохрани и покажи.
5. Сверь каждый `serverId` с `settings.json → mcpServers` проекта (или
   центрального). Не существует — скажи пользователю, не пиши значение молча.
6. `executors:` — позиция только из манифеста
   [docs/positions.md](../docs/positions.md)
   (task / pr / ci / detective / mechanic). Скилл не из
   комплекта (`ship-kit:*`) — сохрани с предупреждением «контракт позиции
   проверяется e2e».
7. Отчитайся диффом (до/после) и списком проверенных ключей.

## Правила валидации (1–14)

1. Ссылки `knowledgeRef`/`diagnosisRef`/`repairRef`/`nextStageId`/
   `fixesStageId` существуют; id стадий и записей уникальны в проекте.
2. `diagnosisRef` — только у BUILD/DEPLOY; `repairRef` — только у
   FIX_BUILD/FIX_DEPLOY; null/отсутствие = `knowledgeRef`.
3. `diagnosisRef`: транспортный alias стадии с теми же `jobFolder`/`jobName`
   (и `environments` для деплоя) — расхождение = ошибка (лог нечем читать /
   не та джоба).
4. `repairRef`: ровно один транспортный alias; сверхтранспортные —
   предупреждение; отличие джобы от `knowledgeRef` — допустимо (замысел).
5. Запись покрывает всех исполнителей своей стадии (позиции × alias).
6. `runnerKind: JENKINS` → `jobFolder`+`jobName`; `CUSTOM` → `jobParameters`,
   `jobFolder`/`jobName` запрещены.
7. `environments` — непустой список из DEV, ST, IFT, PSI в каноническом
   порядке; `environmentJobNames` — только при `environments`, ключи из него.
8. Фикс-стадия: обязательны `fixesStageId` и `nextStageId`; `triggeredBy` —
   только у FIX_DO (`pullRequestReview` | `humanDirective`).
9. `pipelineOrder`: элементы существуют и не FIX_*; не-фикс стадия вне
   `pipelineOrder` — предупреждение; дефолт `[do, build, deploy]` ∩
   существующие.
10. BUILD/DEPLOY стадии без фикс-стадии с `fixesStageId=<id>` —
    предупреждение (любое fixable-падение = notFixable).
11. `pullRequestOwner` — позиция (обычно pr) или отсутствие; правящий
    репозиторий исполнитель есть, а owner не задан — предупреждение.
12. `servers:`: serverId из endpoints не описан — ошибка; описанный
    serverId не используется — предупреждение. Лимиты — целые ≥ 1;
    категории `errorPolicy` — из taxonomy (code, tests, sonar, infra, config,
    dependency, flaky, devops-known, other).
13. `executors:`: позиция существует в манифесте; внешний скилл —
    предупреждение «контракт проверяется e2e».
14. `positions` стадии — подмножество дефолтного набора kind из манифеста;
    FIX_* без позиции для своей категории — предупреждение.

## Ограничения

- Не трогать `settings.json → mcpServers` — конфигурация серверов за
  пользователем; реестр хранит только serverId.
- Адреса, URL, токены в реестр не писать.
- MCP не используется вовсе — это работа с файлом (MCP-серверы не вызывай).

## Формат отчёта

Файл (какой из цепочки); дифф;
проверенные ключи; предупреждения схемы, если были.

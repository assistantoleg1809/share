## 2. Точки отказа слабой модели

Систематический фон (из S4): слабая модель (glm-5.3-flash) в прогоне green777 искала артефакт «всегда-загруженный контекст сессии», а не инструментом (e2e-run.md:22–25) — «правила в скиллах нет», «сверка не выполнялась». Усиление из S1: запрет подбора по смыслу в комплекте не сформулирован — «слово «подбор» не встречается вовсе» (известная проблема 1); вся слот-механика выбора — один блок task/SKILL.md:83–102 (известная проблема 4).

**Звено 1. Условие входа (когда спека вообще нужна).**
- *Механизм ошибки:* триггер «правка меняет поведение из спеки» (task/SKILL.md:83) — интерпретационный, не дословный маркер; для него норма в отчёте S2 не процитирована (а-1). Слабая модель решает «по настроению»: либо пропускает спеку там, где путь требует, либо тянет спеку на каждую мелочь.
- *Симптом:* строка `SPEC: пусто — не требовалась` (task/SKILL.md:144) при фактически требовавшейся спеке — либо лишний запуск спек-исполнителя.
- *Чем грозит:* неполный путь (потерян артефакт спеки) либо лишние гейты/вопросы; обе ошибки плохо диагностируются постфактум, т.к. критерий входа размыт.

**Звено 2. Приоритеты каскада: задание > конвенция > метки сессии.**
- *Механизм ошибки:* норма требует остановки скана на верхнем уровне («метки сессии не сканируются» при назначении/перечне конвенцией — спека 736, 741). Слабая модель сканирует всё подряд: найдя метку, игнорирует названную конвенцией/заданием; либо, не сумев прочитать конвенцию (не вызвала инструмент чтения — паттерн e2e-run.md:22–25), молча падает на уровень меток.
- *Симптом:* исполнитель выбран не из того источника; «лишний» вопрос о нескольких кандидатах там, где конвенция уже назвала одного/набор.
- *Чем грозит:* нарушение MUST-приоритета (спека 107–110); пользователь получает вопрос, на который ответ уже был в конвенции, — эрозия доверия к автоматике.

**Звено 3. Дословный поиск метки `slot:spec`.**
- *Механизм ошибки:* (i) перенос задокументированного паттерна — поиск `slot:spec` в всегда-загруженном контексте/памяти сессии вместо списка скиллов сессии (e2e-run.md:22–25); (ii) при «не найдено» — компенсация подбором по смыслу, поскольку запрет не сформулирован в комплекте (S1, проблема 1): модель видит описание без метки, «похожее» на спек-инструмент, и берёт его — ровно сценарий спеки 725–726, запрещающий «смысл описания не трактуется».
- *Симптом:* «метка не найдена» при живом носителе (или наоборот ложный кандидат без метки); пометка вида «сверка не выполнялась» как в green777.
- *Чем грозит:* ноль кандидатов при реально существующем (лишний мини-дизайн/вопрос) либо самозваный исполнитель, которого словарь не назначал; нарушение литеральной семантики метки (спека 704–706).

**Звено 4. 1 / несколько / 0 кандидатов.**
- *Механизм ошибки:* при нескольких — угадывание или молчаливый выбор (спека 721: «угадывание и молчаливый выбор не выполняются»); при одном — избыточный вопрос (норма 716 — «без вопроса»); при нуле — вместо мини-дизайна с пометкой (task/SKILL.md:89) попытка «кого-нибудь найти»; встретив неизвестную метку — спотыкание вместо «игнорируется без ошибки» (спека 731).
- *Симптом:* вопрос человеку при единственном кандидате; выбор второго кандидата без вопроса; зависание/ошибка на посторонней метке.
- *Чем грозит:* нарушение закрытых сценариев спеки 713–731; молчаливый выбор — самый опасный: решение принято без человека и без следа.

**Звено 5. Вызов исполнителя слота.**
- *Механизм ошибки:* формула «вызывай инструментом вызова скиллов, человек имена не печатает» (task/SKILL.md:74) локализована в task; в pr/SKILL.md и ci/SKILL.md прямого указания на инструмент вызова следующего слота нет (S1, проблема 2). Слабая модель на переходе из pr/ci просит человека напечатать имя или «запускает» слот текстом без вызова. Дополнительно: состав передаваемых данных для спек-исполнителя описан одной фразой «Реализация — по чек-листу изменения» (task/SKILL.md:90), а протокол вызова (аргументы, передача задания) в спеке не найден (S2, секция «Б», «не найдено»); формального описания передачи при обычном переходе task→pr→ci в комплекте тоже нет (S1, проблема 3).
- *Симптом:* цепочка останавливается с вопросом «какой скилл вызвать»; исполнитель получает неполный контекст (нет задания/чек-листа).
- *Чем грозит:* остановка авторизованной цепочки (норма «без остановки», спека 23–26); реализация не по чек-листу изменения (нарушение task/SKILL.md:90 и спеки 110–111).

**Звено 6. Пауза-ревью после слота spec.**
- *Механизм ошибки:* норма — «цепочка не заходит в следующий слот сама» (спека 890) и «проверка спеки человеком не пропускается автоматически» (882–885). Слабая модель, закрыв spec и имея план, продолжает «по плану без остановки» — обобщает правило непрерывной цепочки (task/reference.md:11–12) на гейт, который является исключением.
- *Симптом:* следующий слот начинается сразу после закрытия spec без вопроса «продолжить / доработать / стоп» (task/SKILL.md:154–155).
- *Чем грозит:* человек не увидел спеку до её реализации; непроверенная спека заходит в код/доставку — самый дорогой по последствиям отказ, и он же невидим: прогон может остаться GREEN.

**Звено 7. Фиксация в отчёте (`SPEC: …`).**
- *Механизм ошибки:* строка `SPEC: <инструмент | chat-design | пусто — не требовалась>` (task/SKILL.md:144) требует enum-дисциплины; слабая модель опускает строку, пишет произвольный текст либо называет инструмент как «настройку» (норма 116 — «как факт, не как настройка»).
- *Симптом:* в отчёте нет строки SPEC, или в ней имя инструмента подано как конфигурация комплекта.
- *Чем грозит:* недостоверный отчёт (нарушение контрактной дисциплины дословных доказательств — review.md:263, п. 7.3 «Когда допускается `OK: true`?»); невозможность аудита: какой исполнитель закрывал слот — неопределимо.

## 3. Рекомендации по устранению потенциальных ошибок (особенно на слабых моделях)

**R1. Закрепить запрет подбора по смыслу — task/SKILL.md:88.**

Слабой модели прямой запрет нужен рядом с инструкцией поиска — паттерн green777 показал, что модель полагается на «всегда-загруженный контекст», а правила там нет (e2e-run.md:22–25).

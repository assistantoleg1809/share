# Правила доработки агентов и workflows

Действуют при любой правке агентов и workflows: в универсальном эталоне
(репозиторий `share`) и в проектных копиях комплекта. Перед правкой ответь на
три вопроса:

1. Я меняю **точку адаптации** или **логику**? — раздел 1.
2. Не ломаю ли **инвариант** эталона? — раздел 2.
3. Изменение **универсальное или проектное**? — разделы 3–5.

Справка по комплекту: [docs/agents-and-workflows.md](../../../docs/agents-and-workflows.md)
(состав, матрица доступа агентов, чек-лист адаптации §7, e2e-стенд).

## 1. Точки адаптации — единственное, что меняется под проект

Проектные детали никогда не вносятся в логику агентов и скрипты workflow.
Их законные места: args вызова (`job`, `branch`, `modelFast`, `modelExpert`),
`settings.json → mcpServers`, задача Jira / реестр проектов (`jenkinsJob`).

При адаптации копии эталона допустимо менять ТОЛЬКО:

1. **id MCP-серверов** в `disallowedTools` (deny-list) агентов — под
   фактические id проекта. Deny-list защищает только от перечисленного:
   появился новый сервер в проекте — внеси его в deny-list всем агентам,
   которым он не нужен, иначе агенты его унаследуют.
2. **Имена инструментов запуска** в allowlist-агентах `build-trigger.md` и
   `deploy-trigger.md` (`mcp__jenkins__trigger_build` → точное имя из `/mcp`).
   Allowlist строгий: не названный инструмент агент не получит вовсе.
3. **Записи `mcpServers`** в `.qwen/settings.json` (моки стенда → реальные
   серверы). Файлы агентов и workflows при этом не меняются — они ходят к
   серверам по id.
4. **Канал уведомлений** воркера (afplay → корпоративный канал), если звук на
   машине сессии невозможен.

Имена джоб, пути к проектам, URL, ключи задач, имена веток — НЕ точки
адаптации: их место — args и реестр, не файлы эталона.

Всё, что выходит за этот список, — не адаптация, а доработка: иди в разделы 3–5
и решай, куда она попадает (эталон или проектный форк).

## 2. Инварианты — нельзя ломать ни в эталоне, ни в копии

1. **Шаг 0.** Агент с MCP перед работой проверяет сервер лёгким вызовом;
   недоступен — блок `❌ MCP <server> недоступен` с рекомендациями и стоп.
   Клиент не перезапускает MCP — внятная ошибка обязательна.
2. **Роль = одна операция.** trigger — ровно одна попытка; status — ожидание;
   triage — только чтение, без shell; fix — TDD «красный → правка → зелёный»,
   commit, push; reviewer — только чтение. Роль не расширяется «по дороге».
3. **Отчёт — контракт.** Формат отчёта агента читает workflow (schema).
   Изменил поле — синхронно поправь schema у всех consumer'ов.
   `build-autofix.js` и `deploy-autofix.js` — структурные близнецы (песочница
   запрещает import): правки схем/хелперов/цикла вносить в оба и сверять diff.
4. **Push-политика.** build-fix, deploy-fix, implementer пушат только в рабочие
   ветки, никогда в main/master; их шаг 0 это проверяет.
5. **Интерполяция в shell-промпты** строк из отчётов агентов — только через
   валидаторы формы (`SAFE_WORKTREE` / `SAFE_BRANCH` / `SAFE_KEY`). Новая точка
   интерполяции = новый валидатор, никаких «здесь точно безопасно».
6. **Лимиты времени.** ~10 минут на агента, wall-clock на прогон: ожидание —
   цепочка наблюдателей с sleep, не один долгий агент.
7. **Детерминизм workflow.** `args` может прийти строкой — нормализация
   `const A = typeof args === 'string' ? JSON.parse(args) : args` в каждом
   скрипте. Без import и таймеров — resume обязан быть предсказуем. Воркер:
   один шаг на тик, состояние — валидируемый `state.json`, терминальные фазы
   закрываются в историю, ошибка задачи не останавливает воркер.
8. **Статусы Jira и комментарии в Jira** агенты не меняют никогда — только
   чтение. Расширение — отдельное явное решение, не попутная правка.
9. **e2e-стенд.** Правка эталона валидируется прогоном на стенде (моки `mcp/`,
   bare-репозиторий) до коммита; находки — в `e2e/e2e-run.md`.

## 3. Критерии: проект подходит под универсальный комплект

Комплект берётся без форка, если выполняются ВСЕ пункты:

1. **CI — Jenkins.** Сборка (и для deploy-линейки — деплой) — джобы Jenkins,
   доступные через MCP: запуск, статус, лог. Имена джоб передаются args или
   берутся из задачи/реестра (`jenkinsJob`).
2. **MCP-идентификаторы сводятся к эталонным без смены ролей.** Серверы
   называются `jenkins`, `jira`, `confluence`, `sonar`, `bitbucket`, `mmap` —
   или id меняется по разделу 1. Появляется новая РОЛЬ сервера (не имя) —
   проектный вариант.
3. **Набор операций линеен и достаточен.** Запуск = один вызов инструмента,
   статус = поллинг, без многошаговых сайд-эффектов при запуске джобы.
4. **Полный цикл воркера — опционально.** `/autonomous-worker` требует Jira
   (задачи) + Bitbucket (PR). Их нет — берём только `/build-autofix` /
   `/deploy-autofix`, воркер не трогаем.
5. **Локальная проверка возможна.** Фикс-агент может воспроизвести падение
   локально (тесты/компиляция запускаются на машине агента).
6. **Push в рабочие ветки разрешён**, PR-флоу поддерживается.
7. **Матрицы доступа достаточно.** Проекту не нужно от агента больше, чем даёт
   матрица (docs §2); статусы Jira переводит человек.

Не выполнен хотя бы один пункт → проектный вариант (раздел 4).

## 4. Когда создавать проектных агентов/workflows

Создавай отдельные проектные агенты/workflows, НЕ правя универсальные, если:

1. **Другой CI-транспорт.** GitLab CI, GitHub Actions, TeamCity, ручной деплой —
   линейка `<ci>-trigger/status/triage/fix` пишется заново по структуре эталона
   (роль = одна операция, шаг 0, форматы отчётов).
2. **Другая роль сервера.** Нет Jira (Linear, YouTrack), нет Confluence —
   triage завязан на пятёрку серверов семантически: это проектный triage,
   а не переименование id.
3. **Другая гранулярность инструментов.** Нет отдельного `trigger_deploy`
   (деплой = параметр сборки) или запуск требует цепочки вызовов — проектные
   trigger-агенты; форматы отчётов сохрани, чтобы workflow не переписывать.
4. **Особые политики.** Push запрещён, коммиты только через бота, обязательные
   подписи/проверки — проектный fix-агент и/или свой workflow.
5. **Другой словарь статусов.** PR-статусы не MERGED/DECLINED, иные фазы —
   сначала попытайся замапить на эталонные; не мапится — форк workflow.
6. **Новые ступени конвейера.** Автотесты после деплоя, миграции БД, промоутинг
   окружений — новый проектный workflow, компонующий универсальных агентов
   там, где возможно.

Правила сосуществования:

- Универсальные файлы из проекта не правятся. Проектное = новый файл с
  префиксом транспорта или проекта (`glci-trigger.md`, `PRJ-build-fix.md`).
- Копия, получившая правки сверх раздела 1, обязана пометить это в шапке
  файла («форк от `<файл>` эталона, `<дата>`, причина») — иначе обновления
  эталона перестают переноситься безопасно.
- Проектный workflow сначала компонует универсальных агентов (`agentType`);
   код копирует только при расхождении семантики, с пометкой источника.
- Фича из проекта попадает в эталон, только если полезна ≥2 проектам и не
  тянет проектных деталей. Тогда: оба близнеца + матрица + чек-лист §7 +
  e2e-прогон + правка docs — одним коммитом.

## 5. Порядок доработки

1. Реши уровень: **эталон** (полезно любому проекту с этим контуром, без
   проектных деталей) или **проект** (разделы 3–4). Сомневаешься — делай
   проектный: универсальность доказывается вторым проектом, не предполагается.
2. Эталон: правка → синхронизация близнецов → схемы consumer'ов → docs
   (матрица, чек-лист §7, разделы) → e2e-стенд → коммит.
3. Проектная копия: только точки раздела 1; потребовалось больше — форк с
   пометкой в шапке или предложение переноса в эталон.
4. Обновление эталона переносится в проекты точечно по чек-листу §7
   (docs/agents-and-workflows.md); после переноса — smoke-проверка шага 0
   (агенты с MCP делают лёгкий вызов и возвращают ok).

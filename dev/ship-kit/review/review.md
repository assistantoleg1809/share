# ship-kit — ревью-опросник (приёмка текстов)

Приёмка и ревью комплекта вопросами с эталонами ответов; живое
поведение проверяет тест-стенд `../stand/` (инструкция —
`stand/INSTRUCTION.md`, один прогон на glm-5.3-flash). Эталон —
единственный правильный ответ; источник эталонов — мейн-спека
`openspec/specs/base-skills/spec.md` (имя требования в скобках) и
тексты `skills/`.

**Как пользоваться.** Ревьюер — человек или агент. Вопрос задаётся
к текстам скиллов («что сделает скилл, если…») или к живому прогону
(поведение сверяется с эталоном). Любое расхождение с эталоном —
провал пункта: фикс — отдельной задачей, пункт не «засчитывается
почти». Отвечать по тексту SKILL.md фазы, не по памяти.

## 1. Поставка и вызов

**1.1. Как ставится комплект и можно ли не всеми фазами?**
Эталон: копия выбранных каталогов `skills/ship-kit-<фаза>/` в
`~/.qwen/skills/` или `.qwen/skills/` проекта; частично можно; план
прогона строится только из установленных фаз.
(«Частичная установка и вход любой фазы»)

**1.2. Видит ли модель фазы комплекта в списке скиллов сессии?**
Эталон: да — `disable-model-invocation` не выставляется; модель
вызывает фазы из цепочки утверждённого плана и по триггерам
возобновления; человек — напрямую `/ship-kit-<фаза> <КЛЮЧ>, …`.
(«Скиллы комплекта видимы модели»)

**1.3. Что в плане, если из комплекта установлен только task?**
Эталон: слоты pr/ci помечаются «фаза не установлена» в плане и
отчёте, исключаются из плана, вопрос человеку не задаётся.
(«Частичная установка и вход любой фазы»)

**1.4. Человек вызывает `/ship-kit-pr PRJ-42` первым, плана нет.**
Эталон: pr создаёт план-файл прогона (любая установленная фаза —
входная точка), помечает слоты невыставленных фаз, ведёт свою фазу.
(«Частичная установка и вход любой фазы»)

## 2. План прогона

**2.1. Куда пишется план, если директорию никто не называл?**
Эталон: `.qwen/tmp/ship-kit/<КЛЮЧ>/plan.md` — временная директория
проектной `.qwen`; репо не загрязняется.
(«Директория прогона — каскад с временным дефолтом»)

**2.2. Конвенция проекта назвала корнем `runs/`.**
Эталон: `runs/<ПРОЕКТ>/<КЛЮЧ>/plan.md`, issues.md рядом; уровень
проекта сохраняется.
(«Директория прогона — каскад с временным дефолтом»)

**2.3. Два проекта с одинаковым ключом X-1, директории не заданы.**
Эталон: прогоны раздельны — `.qwen/tmp/ship-kit/X-1/` в .qwen
каждого проекта.
(«Директория прогона — каскад с временным дефолтом»)

**2.4. Формат записи журнала плана?**
Эталон: каждая запись начинается с `ГГГГ-ММ-ДД ЧЧ:ММ` (локальное
время), затем событие; записей без даты не пишется; счётчик попыток
— числом в строке слота.
(«Чек-лист и журнал план-файла»)

**2.5. План лежит в старом `skill-runs/<КЛЮЧ>/`. Прочитает ли скилл?**
Эталон: нет — легаси не поддерживается; план ищется только по
каскаду директории.
(«Директория прогона — каскад с временным дефолтом», решение
2026-11-24)

**2.6. Где архив завершённого прогона и судьба worktree?**
Эталон: `<корень>/archive/<КЛЮЧ>/` (корень — тот же каскад; дефолт
`.qwen/tmp/ship-kit/archive/` — временный, с пометкой в отчёте);
worktree `<ПРОЕКТ>-<КЛЮЧ>` — выбор человека: удалить (гейт) или
`git worktree move` в архив.
(«Архивация прогона и worktree»)

## 3. task

**3.1. Задание перечислило внешние скиллы. Порядок прогона?**
Эталон: чек-лист одним блоком — скиллы по порядку перечисления +
слоты фаз комплекта на названных позициях (не названы — в хвосте
доставки; неустановленные — пометка), одно подтверждение.
(«Порядок прогона с внешними скиллами»)

**3.2. «Профиль openspec» назван, файла `ship-kit.workflows.md` нет.**
Эталон: честная пометка + один вопрос закрытыми опциями: назвать
слоты напрямую / продолжить без профиля; молчаливого дефолта нет.
(«Профиль без макроса — вопрос, а не дефолт»)

**3.3. «продолжи PRJ-42» в новой сессии — что происходит?**
Эталон: фраза матчится с ship-kit-task по триггеру description;
скилл читает план по каскаду, сверяется с фактическим состоянием
(git, статусы PR/джоб), остаток плана одним блоком + одно
подтверждение, после «да» ведёт слоты сам.
(«Вход возобновления — фраза продолжения», «Утверждение остатка
плана при возобновлении»)

**3.4. В плане два незакрытых слота без ясного порядка.**
Эталон: один вопрос закрытыми опциями (слоты / другой ключ / новая
задача); молчаливый выбор запрещён.
(«Сомнение возобновления — вопрос закрытыми опциями»)

**3.5. Скилл внешнего слота не установлен в сессии.**
Эталон: пометка в отчёте + один вопрос «пропустить / стоп»;
молчаливый пропуск запрещён.
(«Скилл слота не загружен в сессии»)

**3.6. Кто исполняет спеку и как выбирается?**
Эталон: слот `spec` каскадом: задание > конвенция (обязывает /
назначает / перечисляет кандидатов — тогда один вопрос) > метка
`slot:spec` в descriptions скиллов сессии (дословный поиск, несколько
— один вопрос); ноль — мини-дизайн в чате с пометкой.
(«Инструмент спекирования не вшивается»)

**3.7. Что происходит сразу после закрытия слота spec?**
Эталон: пауза-ревью — вопрос закрытыми опциями «продолжить /
доработать / стоп»; следующий слот — только после «продолжить».
(«Пауза-ревью слота спеки»)

**3.8. Как определяется тип задачи и что при пустом наборе?**
Эталон: `business`/`technical` каскадом — маркер в задании > тикет >
правило конвенции > дефолт business; набор — метки `slot:<тип>` либо
список конвенции; пустой: technical — без скиллов молча, business —
один вопрос. Смешанная — расщепление в плане.
(«Типы задач и наборы»)

**3.9. CI упал по посторонней причине. Маршрут фикса?**
Эталон: тех-ветка от базовой, отдельный тех-PR, артефакты спеки не
трогать.
(«Маршрут фикса по связанности с задачей»)

**3.10. Может ли task запушить ветку?**
Эталон: нет — пуш только через ship-kit-pr; task коммитит.
(«Три скилла-фазы с говорящими именами»)

## 4. pr

**4.1. Что в карточке «пуш+PR» и почему она одна?**
Эталон: ветка, число коммитов, целевая ветка, суть PR — одна карточка
на оба действия; целевые ветки (main/master/develop/release, база PR)
— NEVER для пуша, несоответствие — отказ до действий.
(«Гейты необратимого — три правила», «PR — только после успешного
пуша»)

**4.2. Пуш упал после «да». Создаётся ли PR?**
Эталон: нет — стоп с ошибкой («PR в никуда» запрещён).
(«PR — только после успешного пуша»)

**4.3. Когда начинается ожидание MERGED и как?**
Эталон: сразу после создания PR, разрешение не спрашивается; опрос
get_pr с интервалом `poll=<сек>` > конвенция > 10 сек; опрос —
чтение; MERGED (дословно) → следующий слот; DECLINED → стоп, провал
в issues.md.
(«Ожидание мержа PR»)

**4.4. Человек говорит «смержил», свежий get_pr — OPEN.**
Эталон: не закрывает слот зелёным; один вопрос: ждать MERGED или
собрать на рабочей ветке; сборка на рабочей ветке — только после
явного «да», слот помечается ⚠ (жёлтым).
(«Токен возобновления и статусы из MCP»)

**4.5. Как различаются свои и чужие комментарии?**
Эталон: по id-журналу план-файла (id каждого своего комментария — в
журнал с датой-временем); замечания и unresolved — только чужие;
игнорируемые авторы (задание `ignore-authors=` + конвенция,
объединение, дословное совпадение) не считаются; подписей в PR нет.
(«Различение своих и чужих комментариев в PR», «Игнорируемые авторы
комментариев»)

**4.6. Что в карточке фикса и порядок после «да»?**
Эталон: одна карточка на цикл — черновики ответов на каждый чужой
комментарий, ветка, коммиты, закрываемые замечания; после «да»:
ответы (add_comment, id в журнал) → пуш в ту же ветку (упал — стоп,
resolve не отмечается) → resolve закрытых. Новый PR — только на новый
фикс.
(«Карточка фикса — подтверждение ответов и пуша»)

## 5. ci

**5.1. Что в карточке запуска?**
Эталон: kind (build/deploy), джоба, ветка и её источник (MERGED-база
или рабочая), стенд, параметры — с источником каждого (задание →
конвенция → прошлая успешная → человек); сборка на рабочей ветке —
только после «да», успех помечается ⚠.
(«Гейты необратимого — три правила», «Диагностика падений джоб CI
внутри ci»)

**5.2. Имени джобы нет нигде. Что делает скилл?**
Эталон: спрашивает; перечисление джоб и сканирование сервера
запрещены.
(«Работа без конфигурации проекта»)

**5.3. Таймаут/flaky в логе.**
Эталон: предложение повтора тех же параметров одной строкой; максимум
один повтор подряд, дальше — диагностика.
(«Повтор упавшей джобы»)

**5.4. Как ставится диагноз падения?**
Эталон: kind из задания/имени джобы → свой командный файл
(build.md/deploy.md); первая настоящая ошибка; категория, rootCause,
fixable, fixHint, knownIssues, связанность (в диффе ветки задачи или
вне); мало данных — confidence low.
(«Диагностика падений джоб CI внутри ci»)

**5.5. Диагноз: fixable, причина вне диффа задачи.**
Эталон: HANDOFF ship-kit-task — тех-ветка от базовой, отдельный PR,
артефакты спеки не трогать; не-код — задача в issues.md + эскалация
человеку; перезапуск — новая карточка запуска.
(«Маршрут фикса по связанности с задачей»)

**5.6. После «да» на карточку запуска — что делает скилл?**
Эталон: ждёт исхода джобы, опрашивая статус лёгким вызовом; первый
опрос — сразу после запуска, интервал: задание `poll=<сек>` >
конвенция > дефолт 600 сек; вопрос «ждать ли?» не задаётся (ожидание
входит в слот, карточкой не оформляется); долгая джоба — отчёты
этапами.
(«Ожидание джобы CI»)

## 6. Гейты и остановки

**6.1. Перечень необратимых действий?**
Эталон: пуш ветки, создание PR, запуск джобы, отправка ответов на
комментарии PR.
(«Гейты необратимого — три правила»)

**6.2. Ответ на карточку: «ну да, наверное».**
Эталон: не подтверждение — совпадение со списком только частью фразы
не считается (ответ читается целиком); переспрос один раз, затем стоп
без действия.
(«Гейты необратимого — три правила»)

**6.3. Инструмент закрытых опций есть; человек ответил текстом вне
опций.**
Эталон: не подтверждение — ответить на содержание и переспросить один
раз тем же инструментом; повторный не-выбор — стоп.
(«Гейты необратимого — три правила»)

**6.4. Задание содержит дословное «подтверждаю запуск сборки PRJ-42».**
Эталон: pre-approved — запуск без повторного вопроса, источник
подтверждения отмечается в отчёте.
(«Гейты необратимого — три правила»)

**6.5. Какие остановки допустимы в работе скиллов?**
Эталон: только (1) 🔒-карточки необратимого, (2) вопросы-выборы
человека (спека-ревью, сомнения, профили, пустые наборы, flaky,
архивация), (3) честные ошибки/конец плана (MCP недоступен, пуш
упал, DECLINED). Иных остановок нет: фазы идут по плану без
остановки, цепочка ведётся моделью.
(«Единица работы — фаза», «Три скилла-фазы с говорящими именами»)

## 7. Цепочка и отчёты

**7.1. Слот task закрыт, следующий — pr. Кто вызывает pr?**
Эталон: модель сама, инструментом вызова скиллов — человек имя фазы
не печатает; паузы — только 🔒 и вопросы.
(«Скиллы комплекта видимы модели», «Три скилла-фазы с говорящими
именами»)

**7.2. Чем заканчивается отчёт фазы при незакрытом плане?**
Эталон: строкой `ДАЛЬШЕ: продолжи <КЛЮЧ>`; план закрыт — строки нет,
дальше предложение архивации.
(«Строка продолжения в отчёте фазы»)

**7.3. Когда допускается `OK: true`?**
Эталон: только с дословными свежими строками прогона/статусов этого
вызова.
(«Дисциплина верификации отчётов»)

**7.4. Транспортный таймаут MCP-вызова.**
Эталон: авто-повтор того же вызова до 2, без вопросов и повторного
гейта; исчерпаны — честная ошибка и стоп.
(«Транспортные сбои — автоматический повтор»)

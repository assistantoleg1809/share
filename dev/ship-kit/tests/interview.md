# Интервью скиллов ship-kit v2 — дешёвая проверка понимания (без полного прогона)

Один вопрос = один вызов модели: промпт содержит вопрос + «отвечай по
установленным скиллам ship-kit» — префикс со скиллами ложится в кеш, ответ
короткий. Проверяет извлечение правил из текста скиллов; руки (инструменты,
гейты-карточки) этим не проверяются — для них живые прогоны s1–s5.

Прогон (модель — только glm-5.3-flash), из корня `extensions/ship-kit`:

```bash
qwen --model glm-5.3-flash -p "<вопрос из списка, дословно> Отвечай по установленным скиллам ship-kit (run/registry/analyst/courier/operator/doctor), кратко: цепочка скиллов с режимами и итоговый исход."
```

Оценка: ответ совпал с «ожиданием» по ключевым точкам (цепочка, режимы,
исход) — GREEN; расхождение — фиксировать в e2e-runs.md и решать, чей баг:
текста скилла или модели.

## Вопросы и эталоны

1. **Кейс «ошибка на девопсе».** Деплой calc упал на DEV, диагноз: категория
   `devops-known`, fixable=false. Какие скиллы вызовутся и в каком порядке?
   Какой итоговый исход прогона?
   *Ожидание:* operator (ожидание) → doctor:diagnose → правок репо нет, PR
   нет → **WAIT** («починка джобы», бюджет заморожен); после «продолжи
   прогон» — operator с новой 🔒 карточкой. analyst/courier не вызываются.

2. **Кейс «нужен человек».** Диагноз деплоя: not-fixable, категория не
   инфраструктурная. Исход?
   *Ожидание:* **STOPPED + задача в issues.md** (не WAIT: ждать нечего);
   продолжение — отдельной явной командой. Отдельный подслучай: отказ на
   карточку гейта → мгновенный STOPPED «гейт отклонён», doctor не вызывается.

3. **Кейс «фикс в другой инфраструктуре».** Деплой упал, чинить надо в чужой
   инфре, сейчас это делает человек. Что сейчас? Как автоматизировать потом
   без правки комплекта?
   *Ожидание:* сейчас — WAIT + задача в issues.md («чинит человек в инфре X»)
   → «продолжи прогон». Потом — два пути без правок скиллов: (а) инфра
   заводится отдельным проектом в реестре со своим конвейером; (б) свой скилл
   на позицию mechanic через `executors:` (+предупреждение «контракт e2e»).

4. **Кейс «не хватает диагностики».** doctor:diagnose вернул
   confidence: low. Что делает run?
   *Ожидание:* WAIT(диагностика) + вопрос человеку; человек подключает
   сервер в settings.json, **registry** дописывает alias/endpoint в запись
   diagnosisRef; doctor:diagnose повторяется с расширенной записью.

5. **Кейс «девопс подсказал в тикете».** Деплой упал, в Jira-тикете DevOps
   написано, как исправить конфиг репозитория. Цепочка до SUCCESS?
   *Ожидание:* operator (ожидание) → doctor:diagnose (категория config,
   fixable, fixHint из тикета) → fixDeploy: позиция **mechanic** =
   doctor:fix (правка, красный→зелёный, коммит, 🔒 карточка пуша, push) →
   courier: PR-3 → MERGED → nextStageId=build → operator (пересборка) →
   operator (стенды заново с начала) → SUCCESS.

6. **Кейс «пришли новые бизнес-требования», деплой идёт.** Как остановить и
   что дальше?
   *Ожидание:* отказ на 🔒 карточку следующего стенда → **STOPPED «гейт
   отклонён»** (или просто не отвечать — WAIT(гейт), бюджет заморожен).
   «Переделать всё» — не падение и не фикс: новая задача → **новый тег →
   новый прогон** с do. Слитые PR не откатываются агентом.

7. **Кейс «ошибка в спеке», сборка зелёная, деплой идёт, PR-1 уже MERGED.**
   Что делать?
   *Ожидание:* остановка отказом карточки стенда; переделка — fixDo по
   `triggeredBy: humanDirective` (PR уже слит): analyst переделывает спеку и
   код, courier оформляет **новый PR-2** («в тот же PR» неприменимо) → MERGED
   → nextStageId=do → build → deploy заново; loop guard +1.

8. **Гейт-контракт.** Сборка #N подтверждена. После фикса запуск идёт с
   изменённым параметром — наследуется ли подтверждение? А flaky-повтор тех
   же параметров?
   *Ожидание:* подтверждение привязано к **карточке**: изменение хотя бы
   одного параметра — новая карточка, новый вопрос; flaky-повтор
   идентичной карточки — `inherited`, без вопроса. Подтверждённая #N не
   разрешает #N+1 с другими параметрами.

9. **Loop guard.** fixBuild прошёл третий круг «фикс → PR → MERGED →
   пересборка», maxFixAttempts=2. Что делает run?
   *Ожидание:* STOPPED + задача в issues.md; новой попытки фикса нет; новый
   PR счётчик **не сбрасывает** (круг считается по «фикс → PR → MERGED →
   перезапуск»).

10. **Подмена исполнителя.** Как в проекте заставить не-код фиксы делать
    внешний скилл вместо doctor? Что скажет валидатор?
    *Ожидание:* одна строка в реестре: `executors: { mechanic: <скилл> }`;
    стадии и скиллы комплекта не трогаются; валидатор: предупреждение
    «контракт проверяется e2e» (скилл — текст, машинно контракт не
    проверить).

# Исследование: синхронизация конфигурационных файлов проекта при обновлении инструмента

Дата: 2026-11-20. Повод: задание пользователя — для ship-kit нужны идеи
поддержки синхронизации конфигурационных файлов в проекте, где комплект
вызывается, при обновлении самого комплекта; решение — переиспользовать
готовые решения популярных проектов.

## Вопрос

Как известные инструменты решают «дрейф» проектных конфигов при
собственном обновлении: инструмент обновился — конфиги в проекте
пользователя отстали. Что из готового переиспользовать для ship-kit.

## Метод

Веб-поиск + чтение официальной документации; делегирование двум
cheap-агентам (glm-5.3-flash, скилл cheap-web-search), 11 инструментов,
все страницы прочитаны напрямую 2026-11-20.

## Находки — готовые механизмы

| Механизм | Кто использует | Суть | Источник |
|---|---|---|---|
| Миграции в поставке, запуск при обновлении | Angular `ng update` | миграции — schematics внутри пакетов (ключ `ng-update` в package.json); CLI сам прогоняет их по дельте версий; refuses dirty repo, `-C` — коммит на шаг; «предпросмотр» = чистое git-дерево | angular.dev/cli/update; github.com/angular/angular-cli docs/specifications/update.md |
| Двухфазный план-файл, применение отдельно | Nx `nx migrate` | фаза 1: версии + `migrations.json` (конфиги не тронуты, файл можно править/вычёркивать); фаза 2: применение по одной, правки unstaged на ревью, обрыв продолжается | nx.dev/docs/features/automate-updating-dependencies |
| Интерактивный per-file diff + постепенные дефолты | Rails `app:update` | Thor-таска перегенерирует конфиги; на каждый расходящийся файл — вопрос Y/n/a/q/d(iff); новые дефолты — закомментированный `new_framework_defaults_X_Y.rb`, включаются постепенно | guides.rubyonrails.org/upgrading_ruby_on_rails.html |
| План → применение как две команды | kubeadm | `upgrade plan` только проверяет и печатает план; `upgrade apply` — отдельная команда с именованными фазами; `upgrade diff` — предпросмотр манифестов | kubernetes.io/docs/reference/setup-tools/kubeadm/kubeadm-upgrade/ |
| Версия в конфиге проекта + команда обновления | pre-commit `autoupdate` | правит только `rev:`-строки в `.pre-commit-config.yaml`; результат — обычный git-дифф; `--freeze` фиксирует sha («frozen: v2.4.0») | pre-commit.com |
| Lock-файл версий + явный обход | Terraform | `.terraform.lock.hcl` пишется `init` автоматически; новые версии — только `init -upgrade`; дифф печатается с просьбой review и закоммитить | developer.hashicorp.com/terraform/language/files/dependency-lock |
| Разовая миграционная команда с TODO-маркерами | Terraform `0.13upgrade`, ESLint `@eslint/migrate-config`, husky migrate | грубая автоконверсия + маркер ручной доработки (`TF-UPGRADE-TODO`; «starting point, not guaranteed to work»); подтверждение или `-yes` | developer.hashicorp.com/terraform/cli/commands/0.13upgrade; eslint.org/docs/latest/use/configure/migration-guide; typicode.github.io/husky/migrate-from-v4.html |
| Минимизация следа в проекте | Husky v4→v9 | v4 копировал хуки в проект (дрейф навсегда); v9 — shim-файлы + `core.hooksPath`, логика в инструменте | typicode.github.io/husky/how-to.html; блог «Why husky doesn't autoinstall anymore» |
| Дифф эталонного проекта как источник правды | React Native Upgrade Helper / rn-diff-purge | полный дифф шаблонного проекта между версиями с комментариями «зачем»; автоприменения нет — перенос руками | reactnative.dev/docs/upgrading (2026-10-27); github.com/react-native-community/upgrade-helper |
| Не писать в конфиг: схема + дефолты в инструменте | VS Code extensions | расширение декларирует `contributes.configuration` (схема, дефолты) и читает значения; в settings.json пользователя не пишет никогда | code.visualstudio.com/api/references/contribution-points |
| Только версии, конфиги вручную | Nuxt `nuxt upgrade`, Astro `@astrojs/upgrade` | поднимают версии пакетов, конфиги проекта не мигрируют — перенос по release notes | nuxt.com/docs/4.x/api/commands/upgrade; docs.astro.build/en/upgrade-astro/ |

## Ключевой вывод

Готовые решения сводятся к четырём ортогональным стратегиям: **(а)
автоматизировать** — миграции едут в поставке и запускаются самой
командой обновления (Angular/Nx), **(б) показать и спросить** — план
или per-file дифф до применения, применение отдельным шагом (kubeadm,
Rails), **(в) не создавать дрейфа** — версия фиксируется в проекте и
обновляется явной командой (pre-commit/Terraform), либо след в проекте
минимизируется (husky v9), либо инструмент вообще не пишет в конфиг
(VS Code), **(г) дать источник правды для ручного переноса** — дифф
эталона (RN). Полная автоматика без участия человека не встречается:
даже Angular/Nx оставляют дифф на git-ревью, Rails — на per-file
вопрос, а «разовые миграторы» честно маркируют ручную доработку.

## Отображение на ship-kit

Проектные следы комплекта, которые дрейфуют: `.gitignore` (`runs/`,
легаси `skill-runs/`), `settings.json` (mcpServers, permissions.allow),
макрос `ship-kit.workflows.md`, конвейер-копии `.qwen/skills`, след
версии комплекта. Стратегии ложатся так:

1. **След версии + сверка на Шаге-0** (паттерн Terraform lock /
   pre-commit rev): строка `ship-kit: <версия>` в
   `runs/<ПРОЕКТ>/<КЛЮЧ>/plan.md` при создании плана; Шаг-0 сверяет с
   манифестом комплекта, расхождение — строка в отчёте. Детектор
   дрейфа без новой конфигурации (след живёт в gitignore-уемом runs/).
2. **План → пофайловое применение под гейтом** (паттерн kubeadm plan +
   Rails per-file): команда «проверь адаптацию ship-kit» сначала
   печатает план расхождений по каждому файлу (ничего не меняя),
   применение — отдельное подтверждение на файл; новые умолчания не
   включаются молча (Rails-паттерн закомментированных дефолтов).
3. **Рецепты-миграции в комплекте** (паттерн Angular/Nx):
   `docs/upgrade.md` — по версиям, что меняется в проектных файлах;
   Nx-механика «план-файл отдельно, применение по одной, обрыв
   продолжается» уже есть в комплекте — это токен возобновления
   plan.md.
4. **Минимизация следа** (паттерн husky v9 / VS Code): долгосрочно —
   всё, что можно, держать в комплекте и только читать (схема+дефолты),
   в проекте остаётся один `runs/`; для конвейер-копий — RN-паттерн:
   показать дифф «копия vs текущий образец» вместо автоправки.

Рекомендация (синтез): 1 + 3 сейчас (детектор версии на Шаге-0 и
рецепты обновления — дёшево, не создают конфигурации), 2 при
необходимости исполнительной команды, 4 — принцип для будущих change.

## Предупреждение

Снимок зафиксирован на дату выше; документация продуктов меняется —
перед опорой на детали сверять с живыми страницами.

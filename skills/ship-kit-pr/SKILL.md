# ship-kit-pr — доставка

Фаза доставки: ветка, пуш, PR, цикл замечаний. Правки кода —
`ship-kit-task`; запуск сборки — `ship-kit-ci`. Следующую фазу сам не
запускаешь. Общие инварианты — [reference.md](reference.md).

## Правила действий

| действие | правило |
|---|---|
| чтение (PR, комментарии, задача) | allow |
| пуш ветки + создание PR | ask · всегда (одна карточка на оба) |
| ответы на замечания + пуш фикса | ask · всегда (одна карточка на цикл) |
| всё сверх переданных MCP | deny |

## Шаг 0

1. **MCP**: лёгкие вызовы переданных серверов (поиск задачи, список
   PR, последний коммит); недоступен — блок ошибки и стоп (как в
   `ship-kit-task`). Лесенка: задание > конвенция > один вопрос; ни
   алиасов, ни конвенции — вопрос и стоп. Роли MCP — как в
   `ship-kit-task` (tracker · docs · repo · build · deploy · quality
   · vuln · chat; несколько — через запятую, запись — куда назвало
   задание, иначе вопрос). Транспортный сбой — авто-повтор до 2,
   потом стоп.
2. **Git**: чистое состояние, отдельная ветка; задание предписало
   worktree — работай строго внутри него (запомни pwd для отчёта).
3. **План прогона**: найди по ключу (директория: задание > конвенция >
   дефолт `.qwen/tmp/ship-kit/<КЛЮЧ>/`); нет — создай (любая фаза
   входная), пометь слоты невыставленных фаз «фаза не установлена»;
   issues.md — в директории прогона; записи журнала — с
   `ГГГГ-ММ-ДД ЧЧ:ММ`, затем событие.

## Гейт — три правила

Необратимое (пуш, PR, ответы на комментарии): **карточка-превью →
явное «да» → действие**; отказ = стоп без перебора альтернатив;
повторный вопрос — только на новое действие; дословное
«подтверждаю …» в задании = pre-approved (отметь источник). Есть
инструмент вопроса с закрытыми опциями — карточка им: согласие =
утвердительная опция; текст вне опций ≠ подтверждение — ответь на
содержание, переспроси один раз тем же инструментом, затем стоп.
Инструмента нет — текстовый канал: подтверждение = дословная фраза
**целиком** из списка «да» · «ок» · «подтверждаю» · «подтверждаю
<действие карточки>» (часть фразы или фраза с добавками — не
подтверждение); отказ — «нет» · «стоп»; прочее — ответь на
содержание, переспроси один раз, затем стоп.

## implement + pr

1. Ветка `<X>/<КЛЮЧ>` (дефолты: `feature/` — задачи, `bugfix/` —
   баги; тип неясен — один вопрос); повторная попытка — суффикс
   `-2`, `-3`.
2. Коммиты готовы (исполнителем) или дозакоммить атомарно с ключом
   задачи.
3. **Карточка «пуш+PR»** (одна на оба действия): ветка, число
   коммитов, целевая ветка, суть PR. Целевая ветка (main/master/
   develop/release, база PR) — NEVER для пуша; несоответствие —
   отказ до любых действий.
4. После «да»: пуш ветки (транспортные повторы до 2). **Пуш не
   удался — стоп с ошибкой, PR не создавай** («PR в никуда»
   запрещён). Успех → PR через MCP репозитория; описание: что,
   зачем, как проверить, ссылка на задачу.
5. **Ожидание MERGED**: начинается сразу после создания PR,
   разрешение не спрашивается. Опрашивай статус PR (лёгкий get_pr) до
   исхода; интервал: задание `poll=<сек>` > конвенция > дефолт 10
   сек. Опрос — чтение, без карточки; каждый опрос — свежий вызов,
   прошлый статус не переносится. **MERGED** (дословный свежий
   статус) → слот зелёный, дальше «Завершение фазы»; **DECLINED** →
   честная ошибка, стоп, провал задачей в issues.md прогона.

### Посторонний тех-фикс

Задание передало тех-ветку (срезана от базовой, от `ship-kit-task`):
доставь её отдельным тех-PR в базовую той же карточкой; пометь
«тех-фикс» в описании PR.

## check

Состояние PR: OPEN/MERGED/DECLINED, число замечаний, нерешённые
комментарии (автор, текст, id), URL. Без изменений. Свои/чужие: id
каждого своего комментария фиксируй в журнале план-файла прогона;
замечания и unresolved считай только чужие — не из id-журнала и не
от игнорируемых авторов (агенты-ревьюеры: список — задание
`ignore-authors=<автор1,автор2>` + конвенция проекта, объединение,
совпадение дословное; пусто — никто).

## fix — замечания ревью

1. Правку делает исполнитель кода (`ship-kit-task`); твоя часть —
   обвязка.
2. Черновики ответов — на каждый **чужой** комментарий; свои (из
   id-журнала) и игнорируемые авторы замечаниями не считаются.
   Зафиксируй `fix(pr): <суть>`.
3. **Карточка фикса** (одна на цикл): черновики ответов, ветка,
   коммиты, закрываемые замечания. После «да»: отправь ответы
   (add_comment; id каждого своего ответа — в журнал), пуш в ту же
   ветку (не удался — стоп, resolve не отмечай), закрытые замечания
   пометь resolve_comment. Новый PR — только на новый фикс, не на
   замечание открытого PR.

## Верификация

В отчёт — дословные свежие статусы и URL (id/url созданного PR, ветка
и коммиты пуша, состояние check). Без свежих статусов успех не
заявляй.

## Ограничения

- Только переданные MCP; статусы трекера не менять.
- Пуш — только в рабочие ветки `<X>/<КЛЮЧ>` (или тех-ветку от
  базовой); целевые ветки запрещены — сверяй до любых действий.
- Ничего не искать: PR и комментарии — из переданных MCP по
  названному id, без перебора репозиториев.

## Отчёт

implement+pr — заверши строками:

```
OK: true|false
WORKTREE: <путь из pwd или пусто>
BRANCH: <ветка>
PRID: <id PR или пусто>
PRURL: <url PR или пусто>
GATE: confirmed | pre-approved(источник) | declined
HANDOFF: ci (после MERGED) | —
ДАЛЬШЕ: продолжи <КЛЮЧ> (план не закрыт; закрыт — строки нет)
```

check → state, commentsCount, unresolved, url. fix → ok, commit,
pushed, gate, summary.

## Завершение фазы

- Следующий незакрытый слот плана — сразу, без остановки: обычно
  `ship-kit-ci` после MERGED PR. Перед продолжением — **свежий статус
  PR из MCP**: слова человека — не статус; расхождение («смержил», а
  get_pr OPEN) — один вопрос: ждать MERGED или собрать на рабочей
  ветке; сборка на рабочей ветке — только после явного «да», слот в
  плане пометь **⚠ (жёлтым: успех на неподтверждённой базе)**.
- До MERGED цепочка стоит на слоте pr: жди опросом (шаг 5) тем же
  интервалом; ожидание не гейт и не пауза, первый опрос — сразу
  после создания PR. Резюм («продолжи <КЛЮЧ>» / «дождись мержа
  <КЛЮЧ>») — прочитай план-файл, найди PR прогона, продолжай цикл
  опроса без переспроса сделанного. «продолжи <КЛЮЧ>» вне ожидания
  мержа — вход `ship-kit-task` (канонический): остаток плана
  утверждается там.
- `check` одиночным вызовом вне плана — разовая проверка, без
  ожидания. Конец плана — предложи архивацию прогона по правилу
  `ship-kit-task` (архив `<корень>/archive/<КЛЮЧ>/`, судьба worktree —
  выбор человека). Паузы — только 🔒-карточки и вопросы правил;
  одиночный вызов — без цепочки.

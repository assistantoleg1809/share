# ship-kit-pr — доставка: ветка, PR, замечания

Ты — фаза доставки. Правки кода делает `ship-kit-task` (или
исполнитель, названный заданием); твоя часть — ветка, обвязка
коммитов, пуш, PR, цикл замечаний. Запуск сборки — `ship-kit-ci`.
Следующую фазу сам не запускаешь. Общие инварианты комплекта —
[reference.md](reference.md).

## Правила действий

| действие | правило |
|---|---|
| чтение (PR, комментарии, задача) | allow |
| пуш ветки + создание PR | ask · всегда (одна карточка на оба) |
| ответы на замечания + пуш фикса | ask · всегда (одна карточка на цикл фикса) |
| всё сверх переданных MCP | deny |

## Шаг 0 — проверки

1. **MCP**: лёгкие вызовы переданных серверов (поиск задачи по ключу,
   список PR репозитория, последний коммит). Недоступен — блок ошибки и
   стоп (как в `ship-kit-task`: /mcp; сверка alias с settings.json →
   mcpServers; перезапуск сессии; сеть/токен). Алиасы не названы —
   возьми из конвенции проекта (обычный контекст сессии: файлы
   проекта); ни конвенции, ни алиасов — вопрос и стоп.

   Роли алиасов: **tracker · docs · repo · build · deploy · quality ·
   vuln · chat** (несколько MCP роли — через запятую: все рабочие,
   чтение по всем, запись — куда названо заданием, иначе один вопрос).

**Транспортные сбои** (таймаут/обрыв MCP или git, сетевая ошибка)
— повторяй тот же вызов автоматически, до 2 повторов, без вопросов и
без повторного гейта (действие уже авторизовано, состояние не менялось);
исчерпаны — честная ошибка и стоп.

2. **Git**: работа с чистого состояния, в отдельной ветке. Задание
   предписало worktree — работай строго внутри него (запомни pwd для
   отчёта).

3. **План прогона**: найди по ключу план-файл (директория —
   каскадом: задание назвало директорию → конвенция проекта → дефолт
   `.qwen/tmp/ship-kit/<КЛЮЧ>/`); нет — создай (первый вызов фазы по
   ключу — любая фаза входная), пометь слоты невыставленных фаз
   «фаза не установлена»; `issues.md` — в директории прогона; записи
   журнала — каждая с даты и времени `ГГГГ-ММ-ДД ЧЧ:ММ` (локальное
   время), затем событие.

## Гейт — три правила

Необратимое (пуш, PR, ответы на комментарии) — всегда три шага: **карточка-превью** → **явное
«да»** человека → **действие**. Отказ = стоп без перебора альтернатив.
Дословное «подтверждаю …» в задании равносильно «да» — отметь источник
в отчёте. Повторный вопрос — только на новое действие, не на то же.

**Структурный вопрос**: в сессии есть инструмент вопроса с закрытыми
опциями — карточку и переспрос задавай им: согласие = утвердительная
опция, отказ = опция стопа; ответ текстом вне опций — не подтверждение
(ответь на содержание и переспроси один раз тем же инструментом, затем
стоп). Инструмента нет — текстовый канал: подтверждение = дословная
фраза **целиком** из списка «да» · «ок» · «подтверждаю» · «подтверждаю
<действие карточки>»; отказ = «нет» · «стоп»; прочее — не решение:
ответь на содержание, переспроси один раз, затем стоп. Инструмент
определяется по списку инструментов сессии, имя комплектом не вшито.

## implement + pr

1. Ветка `<X>/<КЛЮЧ>` (дефолты: `feature/` — задачи, `bugfix/` — баги;
   тип неясен — один вопрос). Повторная попытка — суффикс `-2`, `-3`.
2. Коммиты готовы (исполнителем) или дозакоммить атомарно с ключом
   задачи.
3. **Карточка «пуш+PR»** (одна на оба действия): ветка, число коммитов,
   целевая ветка, суть PR. Сверься: целевая ветка (main/master/develop/
   release, база PR) — NEVER для пуша; несоответствие — отказ до любых
   действий.
4. После «да»: пуш ветки (транспортные сбои — авто-повтор до 2).
   **Пуш не удался — стоп с ошибкой, PR не создавай** («PR в никуда»
   запрещён). Успешный пуш → создание PR через MCP репозитория.
   Описание PR: что, зачем, как проверить, ссылка на задачу.
5. **Ожидание мержа**: начинается сразу после создания PR — разрешение
   на ожидание не спрашивается (ни вопросом, ни карточкой). Опрашивай
   статус созданного PR через MCP репозитория (лёгкий get_pr) до
   исхода, с паузой-интервалом между опросами: задание (`poll=<сек>`)
   > конвенция проекта > дефолт 10 секунд. Опрос — чтение, без карточки; транспортный
   сбой — авто-повтор до 2. Каждый опрос — свежий вызов, прошлый статус
   не переносится. **MERGED** (дословный свежий статус) → слот зелёный,
   продолжай по «Завершению фазы»; **DECLINED** (закрыт без мержа) →
   честная ошибка, стоп, провал задачей в `issues.md` прогона.

### Посторонний тех-фикс

Задание передало техническую ветку (срезана от базовой, от
`ship-kit-task`): доставь её отдельным тех-PR в базовую ветку той же
карточкой; пометь «тех-фикс» в описании PR.

## check

Состояние PR: OPEN/MERGED/DECLINED, число замечаний, нерешённые
комментарии (автор, текст, id), URL. Без изменений. Свои и чужие: id
каждого своего комментария фиксируй в журнале план-файла прогона
(запись с даты и времени `ГГГГ-ММ-ДД ЧЧ:ММ`, локальное время);
замечания и unresolved считай только чужие — не из id-журнала и не от
игнорируемых авторов (агенты-ревьюеры: список — задание
`ignore-authors=<автор1,автор2>` + конвенция проекта, объединение,
совпадение дословное; пусто — никто).

## fix — замечания ревью

1. Правку делает исполнитель кода (`ship-kit-task`); твоя часть —
   обвязка.
2. Черновики ответов — на каждый **чужой** комментарий; свои (из
   id-журнала план-файла) и игнорируемые авторы (агенты-ревьюеры:
   список — задание `ignore-authors=` + конвенция проекта) замечаниями
   не считаются, ответов на них нет. Зафиксируй `fix(pr): <суть>`.
3. **Карточка фикса** (одна на цикл): черновики ответов, ветка,
   коммиты, закрываемые замечания. После «да»: отправь ответы
   (add_comment; id каждого своего ответа занеси в журнал — запись
   с даты и времени), пуш в ту же ветку (не удался — стоп, resolve не
   отмечай), закрытые замечания пометь resolve_comment. Новый PR — только на новый
   фикс, не на замечание открытого PR.

## Верификация

В отчёт — дословные свежие статусы и URL (id/url созданного PR, ветка и
коммиты пуша, состояние check). Без свежих статусов успех не заявляй.

## Ограничения

- Только переданные MCP. Статусы задач трекера не менять.
- Пуш — только в рабочие ветки `<X>/<КЛЮЧ>` (или тех-ветку от базовой);
  целевые ветки запрещены — сверяй до любых действий.
- Ничего не искать: PR и комментарии — из переданных MCP по названному
  id, без перебора репозиториев.

## Формат отчёта

implement+pr — заверши строками:

```
OK: true|false
WORKTREE: <путь из pwd или пусто>
BRANCH: <ветка>
PRID: <id PR или пусто>
PRURL: <url PR или пусто>
GATE: confirmed | pre-approved(источник) | declined
HANDOFF: ci (после MERGED) | —
ДАЛЬШЕ: продолжи <КЛЮЧ> (план не закрыт; закрыт — строка не выводится)
```

check → state, commentsCount, unresolved, url. fix → ok, commit,
pushed, gate, summary.

## Завершение фазы

Следующий незакрытый слот плана вызывай сразу, без остановки: обычно
`ship-kit-ci` после MERGED PR. Перед продолжением — **свежий статус PR
из MCP**: слова человека — не статус; расхождение (человек говорит
MERGED, MCP показывает OPEN) — один вопрос: «ждать MERGED или собрать
на рабочей ветке?»; сборка на рабочей ветке — только после явного «да»,
тогда продолжай `ship-kit-ci` с рабочей веткой, а слот в плане пометь
**⚠ (жёлтым: успех на неподтверждённой базе)**, не зелёным. До MERGED
цепочка стоит на слоте pr: жди опросом (шаг 5 implement+pr) тем же
интервалом — ожидание не гейт и не пауза: разрешение на ожидание не
спрашивается, первый опрос — сразу после создания PR. Возобновление
(«продолжи <КЛЮЧ>» / «дождись мержа <КЛЮЧ>») — прочитай план-файл по
каскаду директории, найди PR прогона и продолжай тот же цикл опроса без
переспроса сделанного; после MERGED — обычное продолжение по плану.
«продолжи <КЛЮЧ>» вне ожидания мержа — вход `ship-kit-task`
(канонический): остаток плана утверждается там, слоты дальше ведёт
ship-kit-task. `check` одиночным вызовом вне плана — разовая проверка
состояния, без ожидания. Конец плана (последний слот закрыт тобой) —
предложи архивацию прогона по правилу `ship-kit-task` (архив —
`<корень прогонов>/archive/<КЛЮЧ>/`, корень по каскаду; судьба
worktree — выбор человека). Паузы — только 🔒-карточки и вопросы
правил; одиночный вызов человеком вне плана — без цепочки.

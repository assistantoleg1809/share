# Qwen Code Workflows — исследование обновления (2026-11-03)

Основание: официальная документация установленного Qwen Code 0.24.6 (Qwen Code Desktop),
bundled-скиллы `workflow-authoring` и `workflow-creator`, транскрипт рабочего процесса
[about-my-work.md](../about-my-work.md), сверка с [PLAN.md](../PLAN.md).
Реализация не выполнялась — по условию задачи.

---

## 1. Сводка (одним абзацем)

В Qwen Code появился инструмент **Workflow**: модель за один ход пишет небольшой JavaScript-скрипт,
который оркестрирует субагентов — параллельные проверки, конвейеры, изолированные правки в
git-worktree, ограничение инструментов и MCP у каждого агента, бюджет токенов, фазы с живым
прогрессом и докатываемый resume. Скрипты можно сохранять в `.qwen/workflows/<name>.js` — они
становятся slash-командами `/name` и переиспользуются. Фича выключена по умолчанию и включается
настройкой `tools.workflowsEnabled`. Для работы пользователя это прежде всего: adversarial-проверка правок
перед PR, разбор логов упавших сборок/деплоев Jenkins, точечное отключение MCP-серверов на
отдельного агента и «быстрые» правки во временном worktree без захламления рабочего каталога.

## 2. Что появилось — проверенные факты

### 2.1 Инструмент Workflow (Dynamic Workflows)

- Модель авторит **JS-скрипт оркестрации**, Qwen исполняет его в песочнице `node:vm`:
  **нет** доступа к файловой системе, shell, сети, окружению, `import` запрещён (скрипт с
  `import()` вообще не стартует). Весь I/O — через промпты субагентам.
- Глобалы скрипта: `phase(title)`, `log(msg)`, `agent(prompt, opts?)`, `parallel(thunks)`,
  `pipeline(items, ...stages)`, `workflow(nameOrRef, args?)`, `args`, `budget`.
- Скрипт начинается с литерального `export const meta = { name, description, whenToUse?, phases }` —
  имя, описание и фазы с пояснениями показываются пользователю **в диалоге подтверждения до запуска**.
- Детерминированность обязательна: `Math.random()` и все `Date`-функции бросают исключение
  (нужно для resume-журнала). Время передают через `args`.
- Результат каждого агента — текст или валидированный объект (`schema`, JSON Schema).
  Упавший агент даёт `null` — проверки на `null` обязательны в той стадии, которая его звала.

### 2.2 Включение — три уровня

1. **Постоянно (инструмент как таковой):** `tools.workflowsEnabled: true` в settings
   (только User/System scope, workspace-значения игнорируются) или env
   `QWEN_CODE_ENABLE_WORKFLOWS=1` (`QWEN_CODE_DISABLE_WORKFLOWS=1` сильнее). Требуется рестарт.
2. **Ключевое слово на один ход:** в сообщении человека `ultracode:` или слово `workflow`
   (например `ultracode: проверь эти три модуля`) — модель получает напоминание рассмотреть
   Workflow именно для этого хода. Отключается `ui.disableWorkflowKeywordTrigger: true`.
   **`qwen -p`, stdin и SDK-строки этот триггер НЕ активируют** (см. §7 для автоматизации).
3. **Session Workflow mode:** `--workflow-mode on` / `/workflows mode on` — сохранённое на сессию
   предпочтение «рассматривать Workflow для обычных сообщений» (напоминания на 1-м, 11-м, 21-м…
   подходящем ходе). Управляется также из SDK (`workflowMode`) и ACP (опция `workflow_mode`).

### 2.3 Сохранённые workflows

- `.qwen/workflows/<name>.js` — проектный скоуп (плюс доверенные родительские каталоги до
  git-корня), `~/.qwen/workflows/` — пользовательский. Имя = slash-команда `/name`.
- Расширения Qwen Code поставляют свои workflows (`'<extension>:<name>'`), поле `whenToUse`
  позволяет модели запускать их по смыслу запроса.
- Вложенный вызов `workflow(name, args)` из скрипта — разрешён (1 уровень вложенности),
  разделяет лимиты и бюджет внешнего прогона.
- `tools.workflowNameOnly: true` — режим «только поимённые запуски»: модель не может писать
  inline-скрипты, только `Workflow({ name, args })`. Каждый запуск покрыт правилом разрешения
  `Workflow(name:...)` — **прямой механизм безопасного внедрения в корп. среде**.

### 2.4 Ключевые настройки и лимиты

| Что | Значение |
|---|---|
| `tools.workflowsEnabled` | `false` по умолчанию; включает инструмент |
| `tools.workflowSizeGuideline` | `small` (<5 агентов) / `medium` (<15, дефолт) / `large` (<50) / `unrestricted` — рекомендация масштаба |
| `tools.workflowNameOnly` | только сохранённые workflows по имени (без inline-скриптов) |
| Параллельность | `max(2, min(16, CPU-2))` агентов одновременно (env `QWEN_CODE_MAX_WORKFLOW_CONCURRENCY`) |
| Агентов на прогон | 1000 (env `QWEN_CODE_MAX_WORKFLOW_AGENTS`); список `parallel`/`pipeline` ≤ 4096 |
| Wall-clock | 30 мин на прогон (`QWEN_CODE_MAX_WORKFLOW_SECONDS`) |
| На агента | 50 ходов / 10 мин / 3 stall-ретрая |
| Бюджет | `budget.total` (директива `+500k` в сообщении или операторский кап); по исчерпании новые `agent()` бросают исключение |

### 2.5 Опции `agent()` — важное для сценариев ниже

- `schema` — структурированный ответ (валидация, 3 попытки, иначе `null`);
- `model`, `effort` (`low…max`) — дешёвые механические стадии на `low`, дорогая верификация на `high`;
- `isolation: 'worktree'` — **свежий git-worktree** под агента (`.qwen/worktrees/agent-<hex>`),
  авто-удаление, если изменений нет; иначе возвращаются путь и ветка;
- `workingDir` — прикрепить агента к **существующему** worktree (например, подготовленному
  предыдущей стадией);
- `disallowedTools` / `tools` — сузить инструменты, в т.ч. `mcp__<server>` целиком или
  `mcp__<server>__<tool>` точечно;
- `stallMs` — watchdog «нет прогресса» с ретраями.

Субагентам workflow **недоступны**: AskUserQuestion, SendMessage, Monitor, Plan-mode, Agent tool —
субагент не может ни спросить человека, ни породить своих верификаторов; весь фан-аут и все
развязки описываются в скрипте.

Прогресс: живое дерево фаз в `/workflows` и background-tasks, кооперативные pause/resume/cancel;
журнал прогона (JSON-line на событие) даёт `resumeFromRunId` — неизменённый префикс вызовов
берётся из кэша, живут только изменённые.

## 3. Для каких задач применять

Справочник формулирует три причины достать workflow:

1. **Comprehensive — полный охват.** Работа декомпозируется, все части закрываются параллельно
   (аудит всех вызовов API, проверка всех модулей, миграция по всем файлам).
2. **Confident — уверенность.** Независимые перспективы + adversarial-проверки до того, как ответ
   зафиксирован: несколько подходов к дизайну, судьи, опровержение находок.
3. **Scale — масштаб сверх одного контекста.** Миграции, аудиты, широкие свипы, которые не
   влезают в один контекст сессии.

Типовые однофазные формы: **understand** (параллельные читатели подсистем → общая карта),
**design** (независимые подходы → судьи → синтез), **review** (измерения → находки → проверка
каждой), **research** (широкий свип → глубокое чтение → синтез), **migrate** (обнаружить места →
преобразовать каждое в изоляции → проверить).

Рекомендуемый гибрид: **сначала скаутинг в главном цикле** (список файлов, объём диффа, падающий
тест), потом список — в workflow. Несколько маленьких workflows по ходам лучше одного большого
безнадзорного.

**Когда НЕ применять:** работа — короткая последовательность правок или одиночный вопрос;
«параллельность сама по себе» — не причина. Workflow — не замена обычному циклу правок.

## 4. Примеры использования (общие)

### 4.1 Ревью диффа по измерениям с adversarial-верификацией (pipeline)

Каждое измерение (корректность/безопасность/производительность) ревьюит свой агент; каждая находка
тут же проверяется независимым агентом с задачей **опровергнуть**; выжившее — подтверждено.

```js
export const meta = {
  name: 'Review changes',
  description: 'Ревью диффа по измерениям с проверкой каждой находки',
  phases: [
    { title: 'Review', detail: 'По одному ревьюеру на измерение' },
    { title: 'Verify', detail: 'Независимый верификатор пытается опровергнуть' },
  ],
};
const reviewed = await pipeline(
  DIMENSIONS,
  async (d) => {
    const r = await agent(`Ревью изменений в ${args.target}: ${d.lens}. Только чтение.`,
      { label: `review:${d.key}`, schema: FINDINGS });
    return r === null ? [] : r.findings;
  },
  (findings, d) => parallel(findings.map((f, i) => async () => {
    const v = await agent(`Проверь опровержением: ${f.file} "${f.claim}". Сначала прочти код.`,
      { label: `verify:${d.key}:${i + 1}`, schema: VERDICT });
    return v === null ? null : { ...f, verdict: v };
  })),
);
```

### 4.2 Массовая миграция/аудит в изоляции

Скаутинг в главном цикле даёт список файлов → каждый файл преобразуется агентом в собственном
worktree (`isolation: 'worktree'`) → финальная сводка путей/веток для слияния. Рабочий каталог
остаётся чистым.

### 4.3 Сохранённый workflow как «команда»

`/deploy-check` с `args: { logPath, project }`: классификация ошибки лога, поиск известных
решений, сводка. Один раз написали — дальше это slash-команда или `Workflow({ name, args })`.

## 5. Применение в работе пользователя (по транскрипту about-my-work.md)

### 5.1 Карта «боль → что даёт Workflow»

| Боль из транскрипта | Что даёт Workflow | Что НЕ решает |
|---|---|---|
| «Бурные дни»: правки «здесь и сейчас», захламление каталога, git stash, потеря контекста | `isolation: 'worktree'`: временный worktree на агента, авто-удаление при отсутствии изменений, ветка возвращается при наличии | Реестр «где что лежит» между сессиями — это по-прежнему MVP `assistant` |
| Нельзя переключаться между ветками при работе с агентом (нужен git worktree) | Частично: параллельные агенты в разных worktree (`isolation`/`workingDir`); долгоживущее переключение задач человеком — `assistant`/Worktrunk | Пауза/возобновление задачи днями позже |
| Хочется, чтобы агент проверял ошибки сборки и лог жабы-деплоя, искал тикеты DevOps | Да: агент читает лог (если permissions сессии позволяют shell/MCP), классифицирует, ищет, сводит | Сам вызов Jenkins — остаётся за человеком/permissions |
| Задачи, где нужно отключать MCP (Confluence, Sonar, Jenkins) | `disallowedTools: ['mcp__confluence', 'mcp__sonar']` на конкретного агента; `tools: [...]` — белый список | Общие permissions проекта — это settings.json, не workflow |
| Обёртки для `qwen -p`, меньше внимания человека | Сохранённые `/name`-сценарии; headless-триггеры ограничены (см. §7) | Полная автоматизация цикла правка→сборка→деплой |
| Проверка правок перед передачей тестировщику | Adversarial-ревью диффа (§4.1) перед PR | Замена ревью человеком |

### 5.2 Сценарий A: подготовка задачи из Jira

Сейчас: skill читает баг, создаёт OpenSpec-каталог, пишет документацию, пользователь проверяет.
Усиление workflow'ом: параллельные читатели (баг + привязанные истории + затронутый код +
Confluence-страница по МСП) → синтез в черновик документации → adversarial-проход «что в черновике
не подтверждается источниками». Результат тот же формат, но с проверкой утверждений.

### 5.3 Сценарий B: разбор упавшей сборки/деплоя (сохранённый workflow)

Скелет (не реализация):

```js
export const meta = {
  name: 'build-failure-triage',
  description: 'Разбор лога упавшей сборки Jenkins: классификация + известные решения',
  whenToUse: 'Сборка или деплой упали и нужно понять причину и что делать',
  phases: [
    { title: 'Triage', detail: 'Классификация ошибки лога' },
    { title: 'Known issues', detail: 'Поиск известных решений и массовых проблем' },
  ],
};
// args: { logPath, project, devopsBoard }
const err = await agent(
  `Прочитай лог ${args.logPath}. Классифицируй ошибку: sonar / компиляция / тесты / инфра / деплой.`,
  { schema: ERROR_SCHEMA });
const known = await parallel([
  () => agent(`По классифицированной ошибке найди открытые тикеты на ${args.devopsBoard}`, { schema: TICKETS_SCHEMA }),
  () => agent(`Проверь, массовая ли проблема (сколько открытых тикетов с той же ошибкой)`, { schema: MASS_SCHEMA }),
]);
return { error: err, known };
```

Для EFS-проектов вторая ступень — то же самое по логу deploy-жабы, о чём в транскрипте:
«открываю лог, ищу ошибку, ищу открытые тикеты на DevOps».

### 5.4 Сценарий C: замечания тестировщиков как конвейер

Каждое замечание — item в `pipeline`: (1) агент воспроизводит/читает код, (2) агент правит в
`isolation: 'worktree'`, (3) верификатор проверяет правку против текста замечания. Медленное
замечание не блокирует остальные (это pipeline, а не барьер).

### 5.5 Сценарий D: «здесь и сейчас» без мусора

Мелкие urgent-правки/проверки, которые сейчас делаются в случайном чистом каталоге: workflow с
`isolation: 'worktree'` на каждого агента — нет изменений, worktree исчез; есть изменения —
получена ветка с результатом, рабочий каталог не тронут. Для задач, которые **переживают сессию**,
нужен реестр — это `assistant` из PLAN.md.

## 6. Влияние на MVP-план (PLAN.md, вариант C)

1. **Вариант C не отменяется.** Workflow не хранит состояние между сессиями (журнал — только для
   resume), не ведёт реестр задач/проектов, не даёт человеку «переключиться на задачу N».
   `assistant` остаётся менеджером задач; Workflow — исполнитель **внутри** сессии Qwen.
2. **Границы MVP смягчаются:** «мультиагентная оркестрация» была исключена из MVP как
   собственная разработка — теперь она частично есть в самом Qwen Code из коробки.
3. **Новое в §14 (корп. неизвестные):** версия корп. Qwen и наличие там инструмента Workflow;
   `tools.workflowsEnabled` ставится только в User/System scope (workspace-файл не сработает) —
   как с этим у корп. политики; безопасный режим внедрения — `tools.workflowNameOnly: true` +
   разрешения `Workflow(name:...)`.
4. **Разделение ролей в будущем стеке:** `assistant` — проекты/задачи/worktree/жизненный цикл;
   Qwen Workflows — параллельные проверки, аудиты, triage внутри одной задачи.

## 7. Автоматизация и headless — важно

- Ключевые слова (`ultracode`/`workflow`) срабатывают **только** на input человека в
  интерактивных входах; `qwen -p`, stdin и обычные SDK-строки их не активируют.
- Явный путь для автоматов: SDK с `origin: { kind: 'human' }` у сообщения или опция
  `workflowMode`; host-приложения могут запускать сохранённые workflows поверх ACP
  (`run-saved`, не ограничен `workflowNameOnly`).
- Практический вывод для `assistant`: запускать сохранённый workflow в headless-режиме можно
  просьбой к модели вызвать `Workflow({ name, args })` при включённых tools — но это предмет
  этапа 7 (пилот), как и остальные §14-вопросы.

## 8. Ограничения и грабли

- Скрипт: без `import`, без `Date`/`Math.random`, без FS/shell/сети; всё I/O — промпты агентов.
- `parallel([agent(...)])` с готовыми промисами отказывает на корню, агенты уже потрачены —
  передавать только thunks `() => agent(...)`.
- `null` из `agent()` — штатный случай (падение агента, 3 неудачные попытки schema); проверять
  там, где звали, иначе молча потеряется измерение/файл.
- Стадия `pipeline`, вернувшая `null`/бросившая, роняет весь item без запуска остальных стадий.
- Субагент не спрашивает человека и не плодит субагентов — все развязки в скрипте.
- Токены: фан-аут из сотен агентов дорог; ориентир — `tools.workflowSizeGuideline`, `budget.total`
  и явный размер в промпте («small workflow, 5 agents max»).
- Resume требует тех же `args` (они сеют цепочку кэша); вложенность `workflow()` — один уровень;
  30-минутный wall-clock по умолчанию.

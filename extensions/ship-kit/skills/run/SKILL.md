# run — полный прогон конвейера

Единственный скилл, которому разрешено запускать скиллы-роли **цепочкой**:
явно вызванный одиночный скилл остаётся одиночным — после `build-status`
не ехать в `build-triage` самовольно. Ты — вызывающий для ролей: читаешь
реестр проектов, собираешь аргументы, вызываешь скилл, принимаешь отчёт.

## Шаг 0 — реестр и план (обязательны)

1. Прочитай реестр проектов (`ship-kit.projects.md` в корне проекта, иначе
   `~/.qwen/ship-kit/projects.md`): проект по умолчанию или из args. Реестра
   нет — остановись и попроси завести его скиллом `projects`.
2. Собери контекст прогона: alias→сервер (только существующие записи;
   отсутствие записи = «в проекте этого MCP нет»), пути и названия джоб,
   КЭ, `branchDefault`, лимиты (`runLimit.build`, `runLimit.deploy`),
   `errorPolicy.notFixable`.
3. Запиши план прогона в `skill-runs/<тег>/plan.md` (тег = ключ задачи или
   slug): чек-лист запланированных шагов. План ведётся по ходу: выполненный
   шаг отмечается, провалившийся — уходит в задачу с ошибкой (см. ниже).
   Каталог `skill-runs/` живёт в корне проекта и не привязан к
   openspec/changes.

## Цепочка (образец замороженного autonomous-worker)

1. **openspec** — спека по задаче Jira (передать mcp-jira, при наличии
   mcp-confluence, mcp-mmap; ключ задачи). Каталог спеки уже существует —
   шаг пропусти.
2. **implementer** (режим implement + pr) — ветка, реализация, PR (передать
   mcp-jira, mcp-bitbucket, repoSsh/ветку).
3. **PR-цикл** — implementer в режимах check/fix: замечания → правки →
   пуш → resolve, максимум 3 круга; MERGED — дальше, DECLINED/застрял —
   задача с ошибкой, стоп.
4. **Сборка** — цикл до лимита `runLimit.build` (по умолчанию 3):
   build-trigger → build-status (до терминального состояния) → FAILURE —
   build-triage → notFixable или категория из `errorPolicy.notFixable` —
   задача с ошибкой, стоп; fixable — build-fix → повторный build-trigger.
5. **Деплой** — есть запись `mcp-deploy.*` → тот же цикл с deploy-линейкой
   до лимита `runLimit.deploy` (по умолчанию 2). Записи нет — ступень
   пропускается целиком.

Каждому скиллу передавай только его MCP (alias→сервер) и его аргументы:
джоба, ветка, номер сборки, диагноз предыдущего шага. Скилл-роль не читает
реестр и не ищет ничего сам.

## Аргументы запуска джобы (наследование)

Аргументы запуска не заданы явно — возьми их из **предыдущей успешной**
(обязательно успешной) джобы того же имени через mcp-build/mcp-deploy,
затем дополни и переопредели аргументами скилла: типичный случай — у
прошлой успешной сборки ~50 параметров, меняется один (номер сборки,
ветка). Прошлой успешной нет — запускай с дефолтами джобы и скажи об этом.

**Ничего не искать**: не перечислять джобы, не сканировать сервер, не
угадывать пути — источники только реестр, args и (для наследования) прошлая
успешная джоба.

## Ошибки — отдельные задачи

Шаг провалился — не пропускай молча: в `skill-runs/<тег>/issues.md` пиши
задачу с ошибкой: номер, шаг, дословная ошибка/диагноз, каким скиллом
чинить (фикс-скилл), статус (open/fixed/wontfix). Правит — другой скилл,
не тот, что упал. Итог прогона честный: SUCCESS только при зелёных
сборке/деплое; иначе — список открытых задач.

## Ограничения

- Реестр читаешь ты; скиллам-ролям он не передаётся.
- Лимиты запусков из реестра не превышать.
- Ничего не искать: источники — реестр, args и прошлая успешная джоба.
- Статусы Jira не меняет никто в цепочке; push — только в рабочие ветки.
- Замороженные агенты/workflows не вызывать — конвейер идёт скиллами.

## Формат отчёта

Итог (SUCCESS / FAILED / STOPPED); пройденные шаги с номерами сборок/деплоев;
ветка/PR/коммиты фиксов; открытые задачи с ошибками (файл issues.md).

# run — диспетчер и прогон конвейера

Универсальная точка входа: получаешь «`<тег> <что сделать>`» — сам выбираешь
нужное подмножество ступеней, ведёшь план, вызываешь роли по одной. Ты —
единственный, кто ведёт цепочку: явно вызванная одиночная роль остаётся
одиночной (после `build-status` никакого автоматного `build-triage`).

## Шаг −1 — разобрать задание

1. Выдели тег (ключ задачи вида `PRJ-123` или slug) и суть задания.
2. Выбери ступени по таблице (задание чаще всего требует подмножество):

| Намёк в задании | Ступени |
|---|---|
| «запусти джобу/сборку/деплой» | trigger → status |
| «…и исправь ошибки» / «доведи до зелёной» | + при падении: triage → fix → пересборка (цикл до лимита) |
| «полный прогон» / «от задачи до деплоя» | openspec → implementer → PR-цикл → сборка → деплой |
| «сделай ПР» / «отправь на ревью» | implementer (+ ожидание MERGED) |
| «продолжи прогон <тег>» | прочитай `skill-runs/<тег>/plan.md`, продолжи с зафиксированной фазы |

Не понял, какие ступени нужны, — один вопрос пользователю, не угадывай.

3. Тег → проект: найди в md-реестре запись, чей `jiraKey` совпадает с
префиксом тега; не нашёл — явный `project` из args; проекта нет вообще —
остановись: реестр заводится скиллом `projects`.

## Шаг 0 — реестр и план

1. Прочитай md-реестр (`ship-kit.projects.md` в корне проекта, иначе
   `~/.qwen/ship-kit/projects.md`): alias→сервер (только существующие
   записи; отсутствие записи = «в проекте этого MCP нет»), пути и названия
   джоб, КЭ, `branchDefault`, `fixFlow` (`direct`|`pr`), лимиты
   (`runLimit.build`, `runLimit.deploy`, `fixRetries`, `runBudget`),
   `errorPolicy.notFixable`.
2. Создай/прочитай `skill-runs/<тег>/plan.md` — план и есть состояние
   прогона (шаблон ниже). Отмечай каждое действие в нём сразу же: план —
   токен возобновления после обрыва сессии.

### Шаблон plan.md

```markdown
# Прогон <тег> — <задание>

## Состояние
Фаза: dev | pr_wait | waiting-approval | build | deploy | done | stopped
Попытка сборки: 1/3 | Деплой: 0/2 | Фикс-круги PR: 0/3
PR: <id/url или —> | Последняя сборка: <#N или —>
Ждём: <чего ждём или —> | Бюджет: <осталось минут или —>

## Ступени (выбраны по заданию)
- [ ] openspec — спека
- [ ] implementer — ветка, PR
- [ ] pr-цикл — замечания до MERGED
- [ ] сборка — цикл до runLimit.build
- [ ] деплой — цикл до runLimit.deploy

## Аргументы джоб
job: <имя> (источник: реестр)
параметры: <карта> (источник: args | прошлая успешная #N | ответ
пользователя | дефолты по слову пользователя)
ожидаемая длительность: <мин> (история: #N — <мин>)

## Журнал
- <время> — событие (сборка #N запущена; фикс <sha>; PR открыт; …)
```

Лишние ступени из шаблона вычёркивай при создании плана.

## Аргументы запуска джоб — цепочка разрешения

Порядок строго такой: **args → реестр (имя/путь джобы) → прошлая успешная
джоба (параметры) → вопрос пользователю → дефолты только если пользователь
сам сказал «дефолты»**. Каждый разрешённый аргумент и ответ пользователя
записывай в раздел «Аргументы джоб» с источником — возобновлённый прогон
не переспрашивает. Прошлой успешной джобы нет — спроси, а не запускай молча
с дефолтами. Роль вернула «не хватает аргументов» — спроси, допиши в план,
вызови роль повторно ровно один раз.

Из истории той же успешной джобы возьми её длительность и передай
`build-status`/`deploy-status` аргументом «ожидаемая длительность» —
роль сообщит ETA и флаг possiblyStuck при ~2× ожидаемого.

**Ничего не искать**: не перечислять джобы, не сканировать сервер, не
угадывать пути — источники только реестр, args, история прошлой успешной
джобы и ответ пользователя.

## Исполнение — ступени

Роли вызываешь по одной, передавая только их MCP (alias→сервер) и их
аргументы: джоба, ветка, номер сборки, диагноз предыдущего шага.

1. **openspec** — спека по задаче (mcp-jira, при наличии mcp-confluence,
   mcp-mmap). Каталог спеки уже есть — пропусти.
2. **implementer** (режим implement + pr) — ветка, реализация, PR
   (mcp-jira, mcp-bitbucket).
3. **PR-цикл** — implementer в режимах check/fix: замечания → правки → пуш
   → resolve, максимум `fixRetries` кругов (дефолт 3; args сильнее реестра).
   MERGED — дальше; DECLINED/застрял — задача в issues.md, стоп.
4. **Сборка** — цикл до `runLimit.build` (дефолт 3; args сильнее):
   build-trigger → build-status (до терминального состояния, с ETA) →
   FAILURE — build-triage → `notFixable` или категория из
   `errorPolicy.notFixable` — задача в issues.md, стоп; fixable —
   build-fix (push ветки фикса) → далее по `fixFlow`:
   - `direct` — сразу повторный build-trigger;
   - `pr` — implementer открывает PR из ветки фикса → **waiting-approval**:
     прогон останавливается, в плане фиксируются PR, попытка и «чего ждём»;
     после MERGED (апрув пользователя) — «продолжи прогон <тег>» возобновляет
     пересборку.
   Одна попытка = весь цикл «фикс → (ПР + апрув) → пересборка».
5. **Деплой** — есть запись `mcp-deploy.*` → тот же цикл с deploy-линейкой
   до `runLimit.deploy` (дефолт 2). Записи нет — ступень пропускается
   целиком.

**Возобновление** («продолжи прогон <тег>»): читай план, сверься с
фактическим состоянием (статус джобы, состояние PR), продолжай с
зафиксированной фазы; счётчики попыток не сбрасывай.

**Бюджет прогона**: `runBudget` (минуты; реестр или args; не задан — не
ограничивай) — по исчерпании честная остановка с итогом STOPPED_BUDGET и
открытыми задачами.

## Ошибки — отдельные задачи

Шаг провалился — не пропускай молча: в `skill-runs/<тег>/issues.md` пиши
задачу: номер, шаг, дословная ошибка/диагноз, каким скиллом чинить
(фикс-скилл), статус (open/fixed/wontfix). Правит другой скилл, не тот, что
упал. Итог честный: SUCCESS только при зелёных сборке/деплое (или достижении
явной цели задания); иначе — список открытых задач.

## Ограничения

- Реестр читаешь ты; скиллам-ролям он не передаётся.
- Лимиты (`runLimit.*`, `fixRetries`, `runBudget`) не превышать; args сильнее
  реестра.
- Ничего не искать (источники — выше).
- Статусы Jira не меняет никто в цепочке; push — только в рабочие ветки.
- Замороженные агенты/workflows не вызывать — конвейер идёт скиллами.

## Формат отчёта

Итог (SUCCESS / FAILED / STOPPED / STOPPED_BUDGET / WAITING_APPROVAL);
пройденные ступени с номерами сборок/деплоев и URL; ветка/PR/коммиты фиксов
со ссылками; открытые задачи (issues.md); путь к плану.

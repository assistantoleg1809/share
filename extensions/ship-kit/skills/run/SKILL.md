# run — диспетчер items-конвейера

Универсальная точка входа: «`<тег> [items | скилл] <что сделать>`».
Конвейер — последовательность **item**; ты выбираешь items из задания или
реестра (нет — дефолтный конвейер), ведёшь план, вызываешь роли по одной.
Ты — единственный, кто ведёт цепочку: явно вызванная одиночная роль остаётся
одиночной (после `jobs` никакого автоматного `diagnosis`).

## Item — единица конвейера

item = `item(action, skill, knowledge, PR)`; слоты независимы:

- **action** — что делает ступень: `openspec` (спека + реализация), `build`,
  `deploy`, `fix` (исправление по диагнозу).
- **skill** — кто исполняет: `openspec`, `superpowers`, другой скилл или без
  скилла. В точках выбора (замечания PR, код-фикс) **точный скилл называет
  человек** — пауза-вопрос или скилл назван в задании; выбор фиксируй в
  плане, молча не выбирай.
- **knowledge** — пак знаний: имя пака (дефолт `jenkins` — командные файлы
  `build.md`/`deploy.md` ролей); передавай роли вместе с её MCP.
- **PR** — часть item, не отдельная ступень: есть правка кода → PR
  создаётся внутри item; замечания правятся пушем в **тот же** PR; новый PR
  — только на новый фикс. У деплоя PR может отсутствовать: исправления кода
  нет → решение в починке самой джобы, PR не создаётся вообще.

Источник items: **задание > реестр > дефолт**.

## Дефолтный конвейер

1. **item1**: action=openspec, skill=openspec, knowledge=—, PR-1.
2. **item2**: action=build, skill=любой/без скилла, knowledge=jenkins.
3. **item3**: action=deploy, skill=любой/без скилла, knowledge=jenkins;
   стенды по `deploy.stands`.

Падение ступени → item-fix (раздел «Циклы и фиксы»). Между item1 и «пушем
ветки + PR» других скиллов нет.

## Шаг −1 — разобрать задание

1. Выдели тег (ключ задачи вида `PRJ-123` или slug) и суть задания. В
   задании назван item или скилл → выполняется только он.
2. Намёки (задание чаще всего требует подмножество):

   | Намёк в задании | Items |
   |---|---|
   | «запусти джобу/сборку» | item2 (запуск → ожидание) |
   | «…и исправь ошибки» / «доведи до зелёной» | item2 + циклы fix/retry |
   | «задеплой [на <стенд>]» | item3 (стенд из задания) |
   | «полный прогон» / «от задачи до деплоя» | item1 → item2 → item3 |
   | «продолжи прогон <тег>» | прочитай план, продолжи с зафиксированной фазы |

   Не понял — один вопрос пользователю, не угадывай.
3. Тег → проект: найди в md-реестре запись, чей `jiraKey` совпадает с
   префиксом тега; не нашёл — явный `project` из args; проекта нет —
   остановись: реестр заводится скиллом `registry`.

## Шаг 0 — реестр и план

1. Прочитай md-реестр (`ship-kit.projects.md` в корне проекта, иначе
   `~/.qwen/ship-kit/projects.md`): alias→сервер (только существующие
   записи; отсутствие записи = «в проекте этого MCP нет»), параметры
   запуска джоб по модели транспорта (`<alias>.model`, дефолт `jenkins` —
   `job.path`/`job.name`, в т.ч. `mcp-deploy.job.name.<СТЕНД>`;
   `custom` — `launch.params`), `deploy.stands`, knowledge-пак, КЭ,
   `branchDefault`, `branch.task`/`branch.bug`, лимиты
   (`runLimit.build`, `runLimit.deploy`, `retryLimit`, `fixRetries`,
   `runBudget`), `errorPolicy.notFixable`.
2. Создай/прочитай `skill-runs/<тег>/plan.md` — план и есть состояние
   прогона (шаблон ниже). Отмечай каждое действие сразу: план — токен
   возобновления после обрыва сессии.

### Шаблон plan.md

```markdown
# Прогон <тег> — <задание>

## Состояние
Фаза: item1 | item2 | item3 | fix | waiting | done | stopped
Item: <action/skill/knowledge> | Попытка: <n/limit> | Retry: <n/retryLimit>
PR: <id/url или —> | Сборка: <#N или —> | Деплой: <стенд i/n, попытка j/k>
Ждём: <гейт | апрув | починка джобы | —> | Бюджет: <осталось минут или —>

## Items (выбраны по заданию)
- [ ] item1 openspec — спека + реализация, PR-1
- [ ] item2 build — цикл до runLimit.build (+ retryLimit)
- [ ] item3 deploy — стенды <список>, цикл до runLimit.deploy на стенд

## Аргументы джоб
job: <имя> (источник: реестр)
параметры: <карта> (источник: args | прошлая успешная #N | ответ
пользователя | дефолты по слову пользователя)
ожидаемая длительность: <мин> (история: #N — <мин>)

## Гейты
- <действие> — confirmed | pre-approved(источник) | inherited(причина) | declined

## Журнал
- <время> — событие (сборка #N; PR-2 открыт; гейт отклонён; …)
```

Лишние ступени из шаблона вычёркивай при создании плана.

## Гейты — подтверждение человеком

Необратимые действия — **запуск джобы (каждый, включая каждый стенд),
любой пуш, создание PR** — роли спрашивают человека сами (вопрос с карточкой
действия). Ты не выполняешь необратимое в обход роли.

- Каждый гейт фиксируй в плане (раздел «Гейты»): действие, результат,
  источник подтверждения.
- Отказ → прогон STOPPED с причиной «гейт отклонён»; не подбирай
  альтернативы молча.
- В задании есть дословное «подтверждаю <действие>» → передай его роли
  вместе с заданием и зафиксируй `pre-approved(задание)`.
- Повтор по таймауту/flaky наследует гейт: передай роли
  `gate=inherited(<причина>)` и зафиксируй в плане.

## Аргументы запуска джоб — цепочка разрешения

Порядок строго такой: **args → реестр (имя/путь джобы, стенд) → прошлая
успешная джоба (параметры) → вопрос пользователю → дефолты только если
пользователь сам сказал «дефолты»**. Каждый разрешённый аргумент и ответ
пользователя записывай в раздел «Аргументы джоб» с источником —
возобновлённый прогон не переспрашивает. Прошлой успешной джобы нет —
спроси, а не запускай молча с дефолтами. Роль вернула «не хватает
аргументов» — спроси, допиши в план, вызови роль повторно ровно один раз.

Из истории той же успешной джобы возьми её длительность и передай `jobs`
(режим ожидания) аргументом «ожидаемая длительность».

**Ничего не искать**: не перечислять джобы, не сканировать сервер, не
угадывать пути — источники только реестр, args, история прошлой успешной
джобы и ответ пользователя.

## Исполнение item

Роли вызываешь по одной, передавая только их MCP (alias→сервер) и их
аргументы: джоба, ветка, **целевая ветка** (из `branchDefault` — для сверки
запрета целевых веток), стенд, knowledge (имя пака), номер сборки, диагноз
предыдущего шага, подтверждение из задания.

- **item1**: `openspec` (mcp-jira, при наличии mcp-confluence, mcp-mmap).
  Реализацию tasks.md и фикс замечаний делает openspec-скилл — между item1
  и «пушем ветки + PR» других скиллов нет. Обвязку (ветка `<X>/<КЛЮЧ>`,
  атомарные коммиты, PR, resolve замечаний) делает `pr`.
- **item2/item3**: `jobs` (запуск → ожидание), при падении `diagnosis` →
  фикс-механика (ниже).

## Циклы и фиксы

- **Замечания PR** (`pr`, режим fix): фикс — openspec-скилл (точный называет
  человек), 🔒 пуш в **тот же** PR, resolve; максимум `fixRetries` кругов
  (дефолт 3; args сильнее). MERGED — дальше; DECLINED/застрял — задача в
  issues.md, стоп.
- **item2 FAILURE**: отчёт наблюдателя + диагноз дают категорию.
  - Категория `flaky`/таймаут и `retryLimit` (дефолт 1) не исчерпан → **один
    повторный запуск тех же параметров без фикса и без нового гейта**
    (передай `gate=inherited(таймаут #N)`); повторное стабильное падение →
    diagnosis.
  - Код (компиляция/тесты), fixable → **openspec-скилл** (точный называет
    человек) — item-fix, PR-2 → MERGED → пересборка (item2).
  - Не-код, fixable → `repair` (механика TDD-фикса по диагнозу) — item-fix,
    PR-2 → MERGED → пересборка (item2).
  - `notFixable` / категория из `errorPolicy.notFixable` → задача в
    issues.md, стоп.
- **item3 FAILURE** (на стенде): flaky/таймаут → retry-lazy как в item2;
  стабильно → `diagnosis` (kind=deploy):
  - фикс кода/конфига репозитория → item-fix, **PR-3** → MERGED →
    **item2 (пересборка)** → снова стенды;
  - **исправления кода нет → PR не создаётся**: решение в починке самой
    джобы — knownIssues/эскалация DevOps (тикет по диагнозу), задача в
    issues.md, прогон ждёт (`Ждём: починка джобы <тикет>`); после слов
    пользователя «продолжи прогон» — повтор item3.
- Одна попытка = весь цикл «фикс → PR → MERGED → пересборка»; счётчики
  попыток не сбрасывай.
- **Целевая ветка**: push только в рабочую ветку `<X>/<КЛЮЧ>` этого
  прогона; `branchDefault`/база PR — никогда (роли сверяют; ты передаёшь
  целевую ветку аргументом).

## Стенды (item3)

`deploy.stands` — упорядоченный список; канонический порядок `DEV, ST, IFT,
PSI`, в составе обязательны IFT и PSI, остальные опциональны. Задание
назвало стенд → только он; полный прогон → все по порядку; не назван и не
полный → вопрос пользователю (цепочка аргументов). Каждый стенд — свой
запуск джобы (гейт). `runLimit.deploy` — лимит попыток **на стенд**.
Записи `mcp-deploy.*` нет — item3 пропускается целиком.

## Бюджет и возобновление

- `runBudget` (минуты; реестр или args; не задан — не ограничивай) — общий
  предохранитель; **заморожен**, пока прогон ждёт (гейт, апрув PR, починка
  джобы). По исчерпании — честная остановка STOPPED_BUDGET.
- «продолжи прогон <тег>»: читай план, сверься с фактическим состоянием
  (статус джобы, состояние PR), продолжай с зафиксированной фазы.

## Ошибки — отдельные задачи

Шаг провалился — не пропускай молча: в `skill-runs/<тег>/issues.md` пиши
задачу: номер, шаг, дословная ошибка/диагноз, каким скиллом чинить,
статус (open/fixed/wontfix). Правит другой скилл, не тот, что упал. Итог
честный: SUCCESS только при зелёных сборке/деплое (или достижении явной
цели задания); иначе — список открытых задач.

## Ограничения

- Реестр читаешь ты; скиллам-ролям он не передаётся.
- Гейты не обходить: отклонённый гейт = стоп прогона, без молчаливого
  перебора альтернатив.
- Лимиты (`runLimit.*`, `retryLimit`, `fixRetries`, `runBudget`) не
  превышать; args сильнее реестра.
- Ничего не искать (источники — выше).
- Статусы Jira не меняет никто в цепочке; push — только в рабочие ветки,
  целевые ветки (branchDefault, база PR) запрещены.

## Формат отчёта

Итог (SUCCESS / FAILED / STOPPED / STOPPED_BUDGET / WAITING — чего ждём:
гейт, апрув PR, починка джобы); пройденные items с номерами сборок/деплоев
и URL; ветки/PR-N/коммиты фиксов со ссылками; гейты (результат и источник
каждого); открытые задачи (issues.md); путь к плану.

# Правила доработки комплекта ship-kit

Действуют при любой правке комплекта в эталоне (репозиторий ship-kit) и в
проектных копиях. Приоритет — скилл-контур. Перед
правкой ответь на три вопроса:

1. Я меняю **точку адаптации** или **методику**?
2. Не ломаю ли **инвариант**?
3. Изменение **универсальное или проектное**?

## 1. Точки адаптации — где живут проектные детали

Проектные детали **никогда не вносятся в тела скиллов**. Их законные места:

- **Файл проектов** `ship-kit.projects.md` (ведётся скиллом `registry`):
  alias MCP → фактический сервер, пути и названия джоб, КЭ, jira-ключ,
  ssh-репо, лимиты запусков, fixFlow, политики ошибок. Схема —
  [docs/ship-kit.projects.example.md](../../docs/ship-kit.projects.example.md).
- **Аргументы вызова**: kind (build/deploy), номер джобы, ветка, диагноз
  предыдущего шага, выбор MCP при неочевидности.
- **`settings.json → mcpServers`** проекта (id серверов) — за пользователем.

Скилл-роль не знает о файле проектов: что ей передали аргументами, тем и
работает.

## 2. Инварианты — нельзя ломать

1. **Один скилл — одна область знания, один вызов — один шаг.** Скилл может
   нести режимы (jobs: запуск/ожидание) и командные файлы (diagnosis/
   repair: build.md/deploy.md), но вызов всегда выполняет один шаг; роль не
   расширяется «по дороге».
2. **MCP — только из аргументов вызова.** Скилл не выбирает сервер, не
   перечисляет серверы, не читает файл проектов. Alias не передан — «в
   проекте этого MCP нет»: работать без него и отметить в отчёте. Ничего не
   передано и непонятно — запросить у пользователя, не подбирать молча.
3. **Ничего не искать.** Не сканировать Jenkins, не перечислять джобы, не
   угадывать пути — источники: реестр, args, история прошлой успешной
   джобы и ответ пользователя (наследование аргументов и подсказку
   ожидаемой длительности передаёт вызывающий — скилл `run` или человек).
4. **Командные файлы kind обязательны и взаимоисключающие.** В diagnosis и
   repair: читается только файл своего kind; сборку и деплой обслуживают
   разные команды, инструкции эскалации разные.
5. **Формат отчёта — контракт.** Отчёт читают человек и скилл `run`.
   Изменил поле — синхронно проверь
   вызывающих.
6. **Без контекста исполнения.** В скилле не описывается, где выполнять
   инструкцию (саб-агент, основной агент) — это решает вызывающая среда.
7. **Явный вызов не тянет цепочку.** «Соседние шаги» — навигация для
   человека; автоматически следующий скилл не запускается. Цепочку ведёт
   только `run`.
8. **Push только в рабочие ветки; статусы Jira не трогать.**
9. **Шаг 0 обязателен**: лёгкая проверка переданного MCP с внятным блоком
   ошибки и остановкой.
10. **Новые скиллы** пишутся по методике writing-skills (baseline-сценарий
    «без скилла» до написания, описание — только условия срабатывания,
    проверка прогоном на дешёвой модели glm-5.3-flash). До подтверждения
    пользователем архитектуры тестов (docs/tests-architecture.md)
    baseline-прогоны отложены.

## 3. Универсальный или проектный

Транспорт CI — **контракт, а не бренд**. Скиллы работают с любым CI, дающим
MCP-контракт трёх операций: **запуск** (джоба+ветка/параметры → номер+URL),
**статус** (номер → состояние), **лог** (номер → текст). Имена инструментов
не фиксированы: реестр может пиновать их
(`<alias>.tool.run|.tool.status|.tool.log`); не запинковано — роль ищет
инструмент по описанию на переданном сервере. CI-специфика (эскалации,
источники, известные проблемы) живёт в **knowledge-паке** — командных
файлах `build.md`/`deploy.md` (дефолтный пак — `jenkins`), не в телах
скиллов: для другого CI пишется свой пак, скиллы не правятся.

Проект подходит под универсальные скиллы, если: CI-транспорт даёт
MCP-контракт трёх операций (Jenkins, GitLab CI, TeamCity, GitHub Actions —
без разницы); роли MCP сводятся к фиксированным alias (`mcp-build`/
`mcp-deploy`/`mcp-sonar`/`mcp-jira`/`mcp-confluence`/`mcp-bitbucket`/
`mcp-mmap`); операции линейны; push в рабочие ветки разрешён. Иначе —
проектный вариант:

1. **CI-транспорт без MCP-контракта** или другая гранулярность операций
   (деплой = параметр сборки, цепочки вызовов) — проектная версия `jobs` с
   тем же форматом отчёта; специфические знания — свой knowledge-пак
   (командные файлы), не правка эталонных скиллов.
2. **Другая роль MCP** (нет Jira/Confluence, другой трекер) — проектные
   openspec/diagnosis, не переименование alias.
3. **Особые политики** (запрет push, коммиты ботом, обязательные проверки) —
   проектные repair/pr.

Правила сосуществования: универсальные скиллы из проекта не правятся;
проектный скилл — новый файл/каталог с префиксом проекта или транспорта;
командные файлы (build.md/deploy.md) может вести профильная команда —
файл и есть граница владения; фича идёт в эталон, только если полезна
≥2 проектам и без проектных деталей.

## 4. Порядок доработки

1. Реши уровень: эталон или проектный (сомневаешься — проектный).
2. Эталон: правка скилла → синхронизация вызывающих формата отчёта →
   docs → baseline/e2e-проверка (после подтверждения архитектуры тестов)
   → коммит.

# repair — исправление по диагнозу

Получаешь диагноз (kind, категория, первопричина, подсказка) — вносишь
минимальную правку, проверяешь локально, коммитишь и пушаешь. Пересборку
запускает вызывающий, не ты.

**Сборку и деплой чинят по разным инструкциям** — обязательный шаг:

> Определи kind и прочитай **только свой командный файл**: kind=build →
> [build.md](build.md), kind=deploy → [deploy.md](deploy.md). Другой файл
> не открывай. Читай его до правки.

## Шаг 0 — проверки (обязательны)

1. MCP: лёгкий вызов переданного `mcp-build`/`mcp-deploy` (нужен для сверки
   лога). Недоступен — верни блок ошибки и остановись.
2. Git: если ты запущен в свежем git-worktree (pwd покажет каталог вида
   `.qwen/worktrees/...`) — создай в нём рабочую ветку по шаблону бага:
   `bugfix/<КЛЮЧ>` (шаблон из задания сильнее; повторная попытка того же
   прогона — суффикс `-2`, `-3`, …, чтобы PR попыток не путались) и
   работай оттуда. Если ты в основном чекауте — ветка должна быть рабочей
   (не main/master), каталог чистым, upstream настроенным. Проблема — верни
   ошибку с описанием и что сделать, ничего не трогай.

```
❌ MCP <переданный сервер> недоступен
Симптом: <что произошло, дословно>
Рекомендации:
1. Выполнить /mcp и посмотреть статус сервера.
2. Сверить alias с фактическим id в файле проектов
   (ship-kit.projects.md) и settings.json → mcpServers — их читает
   вызывающий, не ты.
3. Перезапустить сессию Qwen Code — клиент не перезапускает MCP сам.
```

## Протокол (общий скелет)

1. Прочитай код/конфиг по fixHint; детали — командный файл build.md /
   deploy.md. Подтверди первопричину логом: не подтверждается — верни
   not-fixable с объяснением, ничего не правь.
2. Минимальная правка: меняй только то, что нужно для первопричины.
   Смежные улучшения не трогай.
3. Локальная проверка по TDD, строго в этом порядке:
   - (а) воспроизведи: запусти упавший тест/компиляцию/скрипт, зафиксируй
     «красный» вывод (совпадает с логом джобы);
   - (б) минимальная правка;
   - (в) повтори запуск — «зелёный».
   Воспроизвести локально невозможно — прямо напиши это в verification и
   укажи, чем заменил проверку (чтение кода, анализ пути выполнения). Не
   заявляй ok без результата проверки: вставь последние строки прогона
   дословно.
4. Коммит: `fix(build): <первопричина> [build #N]` или
   `fix(deploy): <первопричина> [deploy #N]`. Один коммит, без мусора.
5. 🔒 Гейт перед пушем: задай пользователю вопрос (ask_user_question) с
   карточкой — ветка, коммит, суть правки. Подтверждение — только явное:
   ответ на вопрос или дословное «подтверждаю …» в задании (передано
   вызывающим — `pre-approved(источник)`, без вопроса). Отказ → отчёт
   OK: false, PUSHED: false, GATE: declined — без пуша.
6. Push в ту же рабочую ветку.

## Ограничения

- Только MCP, переданные аргументами вызова; ничего сверх них не вызывать.
- Пуш — только в рабочую ветку `<X>/<КЛЮЧ>`; целевые ветки (branchDefault,
  база PR) запрещены.
- Не править чужие сервисы и окружения за пределами репозитория.
- Статусы Jira не менять.

## Формат отчёта

Свободный markdown с разбором, но обязательно закончи строками (по одной,
без маркдауна):

```
OK: true|false
COMMIT: <sha или пусто>
BRANCH: <ветка или пусто>
PUSHED: true|false
GATE: confirmed | pre-approved(источник) | declined
SUMMARY: <суть правки одной строкой>
WORKTREE: <путь из pwd; пусто, если работа не в worktree>
```

## Соседние шаги

Диагноз ещё не поставлен — скилл `diagnosis`; перезапуск после пуша —
скилл `jobs`. Переход — только явный вызов (пользователем или скиллом
`run`): сам следующий скилл не запускай.

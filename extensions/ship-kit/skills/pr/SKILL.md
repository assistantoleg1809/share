# pr — ветка, pull request и цикл замечаний

Работаешь по tasks.md из OpenSpec-каталога. Реализацию пунктов выполняет
скилл OpenSpec (если установлен) — твоя часть обвязка контура: ветка,
коммиты, PR, замечания. mcp-jira и mcp-bitbucket доступны; сборкой
занимается соседний шаг (скилл `jobs`).

## Шаг 0 — проверки (обязательны)

1. MCP: лёгкие вызовы переданных mcp-jira (поиск по ключу задачи) и
   mcp-bitbucket (список PR или репозитория); alias → фактический сервер
   знает вызывающий (файл проектов скилл не читает). Хоть один недоступен —
   верни блок ошибки и остановись:

```
❌ MCP <переданный сервер> недоступен
Симптом: <что произошло, дословно>
Рекомендации:
1. Выполнить /mcp и посмотреть статус сервера.
2. Сверить alias с фактическим id в файле проектов
   (ship-kit.projects.md) и settings.json → mcpServers — их читает
   вызывающий, не ты.
3. Перезапустить сессию Qwen Code — клиент не перезапускает MCP сам.
4. Для удалённых серверов — проверить сеть и токен.
```

2. Git: состояние рабочего каталога. Работа — только с чистого состояния,
   в отдельной ветке.

## Режимы (задаётся в задании)

### implement + pr

1. Если задание предписывает работу в предоставленном worktree — работай
   строго внутри него (не переключайся в основной чекаут): ветка, коммиты
   и PR делаются оттуда. Выполни `pwd` и запомни путь для отчёта.
2. Ветка по шаблону `<X>/<КЛЮЧ>`: шаблон из задания или реестра
   (`branch.task`/`branch.bug`); не указан — `feature/<КЛЮЧ>` для задач и
   `bugfix/<КЛЮЧ>` для багов (тип — из задачи Jira или задания; неясен —
   один вопрос пользователю, не угадывай).
3. Реализацию пунктов tasks.md делегируй скиллу OpenSpec (openspec-*),
   если он установлен; нет — выполняй сам по чек-листу по порядку.
   Выполненное отмечай в tasks.md. Твоя часть — обвязка контура: ветка,
   атомарные коммиты, PR, цикл замечаний.
4. Коммить атомарно, в сообщении ссылайся на ключ Jira.
5. 🔒 Гейт перед пушем ветки и созданием PR: задай пользователю один вопрос
   (ask_user_question) с карточкой **обоих действий** — ветка, число
   коммитов, целевая ветка, суть PR. Подтверждение — только явное: ответ на
   вопрос или дословное «подтверждаю …» в задании (передано вызывающим —
   `pre-approved`, без вопроса). Отказ → отчёт OK: false, GATE: declined,
   без пуша и без PR.
6. Запушь ветку и создай PR через переданный mcp-bitbucket: описание — что,
   зачем, как проверить, ссылка на задачу Jira. PR — часть item: замечания
   правятся пушем в этот же PR, новый PR не открывается.
7. Статусы Jira не менять. Комментарий в задачу — только если задание
   просит.
8. Заверши отчёт обязательными строками (по одной, в конце, без
   маркдауна):

   ```
   OK: true|false
   WORKTREE: <путь из pwd; пусто, если работа не в worktree>
   BRANCH: <ветка>
   PRID: <id PR>
   PRURL: <url PR>
   GATE: confirmed | pre-approved(источник) | declined
   ```

### check

Узнай состояние PR: OPEN/MERGED/DECLINED, количество замечаний, нерешённые
комментарии (автор, текст, id). Верни без изменений.

### fix

Замечания правятся в **тот же** PR — новый PR не открывается:

1. Фикс делегируй скиллу OpenSpec (openspec-*), если он установлен; точный
   скилл **называет человек** — не назван в задании, задай один вопрос
   (пауза-выбор), молча не выбирай. Скиллов OpenSpec нет — правь сам по
   замечанию.
2. Ответь на каждый комментарий в PR (add_comment), закоммить
   `fix(pr): <суть замечания>`.
3. 🔒 Гейт перед пушем в ту же ветку: карточка — ветка, коммиты, закрываемые
   замечания. Подтверждение — как в implement+pr; отказ → отчёт OK: false,
   GATE: declined, без пуша.
4. Запушь в ту же ветку, закрытое замечание пометь resolve_comment. Работай
   в том же worktree, если он указан в задании.

## Ограничения

- Только MCP, переданные аргументами вызова; ничего сверх них не вызывать.
  Файл проектов не читается.
- Пуш — только в рабочую ветку `<X>/<КЛЮЧ>` текущего item; целевые ветки
  (branchDefault реестра: main/master/develop/release, база PR) запрещены —
  сверяй ветку пуша с целевой, переданной аргументом; несоответствие
  шаблону — отказ до любых действий.
- Не начинай, если OpenSpec-каталога нет — верни ошибку «сначала нужен
  шаг спеки» (скилл `openspec`).

## Формат отчёта

По режиму: implement+pr → ok, branch, prId, prUrl, gate, summary; check →
state, commentsCount, unresolved, url; fix → ok, commit, pushed, gate,
summary.

## Соседние шаги

Спека — скилл `openspec`; после merge — скилл `jobs`. Переход — только
явный вызов (пользователем или скиллом `run`): сам следующий скилл не
запускай.

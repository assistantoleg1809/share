# Правила доработки скиллов

Действуют при любой правке скиллов комплекта `ship-kit` (эталон и проектные
копии). Правки агентов/workflows — отдельный скилл
`adapt-agents-workflows` (эта часть комплекта заморожена). Перед правкой
ответь на три вопроса:

1. Я меняю **точку адаптации** или **методику роли**?
2. Не ломаю ли **инвариант** скиллов?
3. Изменение **универсальное или проектное**?

## 1. Точки адаптации — где живут проектные детали

Проектные детали **никогда не вносятся в тела скиллов**. Их законные места:

- **Реестр проектов** `ship-kit.projects.md` (ведётся скиллом `projects`):
  alias MCP → фактический сервер, пути и названия джоб, КЭ, jira-ключ,
  ssh-репо, лимиты запусков, политики ошибок. Схема —
  [docs/ship-kit.projects.example.md](../../docs/ship-kit.projects.example.md).
- **Аргументы вызова**: номер сборки, ветка, диагноз предыдущего шага,
  выбор MCP при неочевидности.
- **`settings.json → mcpServers`** проекта (id серверов) — за пользователем.

Скилл-роль не знает о реестре: что ей передали аргументами, тем и работает.

## 2. Инварианты — нельзя ломать

1. **Роль = одна операция.** Trigger — один запуск; status — ожидание;
   triage — только чтение; fix — правка+коммит+push; openspec — документация;
   implementer — реализация/PR; reviewer — чтение; projects — реестр;
   run — только run ведёт цепочку. Роль не расширяется «по дороге».
2. **MCP — только из аргументов вызова.** Скилл не выбирает сервер, не
   перечисляет серверы, не читает реестр. Alias не передан — «в проекте
   этого MCP нет»: работать без него и отметить в отчёте. Ничего не передано
   и непонятно — запросить у пользователя, не подбирать молча.
3. **Ничего не искать.** Не сканировать Jenkins, не перечислять джобы, не
   угадывать пути — только входные аргументы (и наследование аргументов
   прошлой успешной джобы у вызывающего).
4. **Формат отчёта — контракт.** Отчёт роли читает вызывающий (человек,
   скилл `run`, замороженные workflows). Изменил поле — синхронно проверь
   всех потребителей.
5. **Без контекста исполнения.** В скилле не описывается, где выполнять
   инструкцию (саб-агент, основной агент, workflow) — это решает вызывающий
   среда, не скилл.
6. **Явный вызов не тянет цепочку.** «Соседние шаги» — навигация для
   человека; автоматически следующий скилл не запускается. Цепочку ведёт
   только `run`.
7. **Push только в рабочие ветки; статусы Jira не трогать.**
8. **Шаг 0 обязателен**: лёгкая проверка переданного MCP с внятным блоком
   ошибки и остановкой.
9. **Новые скиллы** пишутся по методике writing-skills (baseline-сценарий
   «без скилла» до написания, описание — только условия срабатывания,
   проверка прогоном на дешёвой модели). До подтверждения архитектуры
   тестов пользователем baseline-прогоны отложены — фиксация отступления
   в docs/tests-architecture.md.

## 3. Универсальный или проектный

Проект подходит под универсальные скиллы, если: CI — Jenkins; роли MCP
сводятся к `mcp-build`/`mcp-deploy`/`mcp-sonar`/`mcp-jira`/
`mcp-confluence`/`mcp-bitbucket`/`mcp-mmap`; операции линейны; push в
рабочие ветки разрешён. Иначе — проектный вариант:

1. **Другой CI-транспорт** (GitLab CI, GitHub Actions, TeamCity) — проектная
   линейка `<ci>-trigger/status/triage/fix`, структура и форматы отчётов —
   как у эталона.
2. **Другая роль MCP** (нет Jira/Confluence, другой трекер) — проектные
   openspec/triage, не переименование alias.
3. **Другая гранулярность операций** (деплой = параметр сборки, цепочки
   вызовов) — проектные trigger-скиллы с теми же форматами отчётов.
4. **Особые политики** (запрет push, коммиты ботом, обязательные проверки) —
   проектные fix/implementer.

Правила сосуществования: универсальные скиллы из проекта не правятся;
проектный скилл — новый файл с префиксом проекта/транспорта; фича идёт в
эталон, только если полезна ≥2 проектам и без проектных деталей.

## 4. Порядок доработки

1. Реши уровень: эталон или проектный (сомневаешься — проектный).
2. Эталон: правка скилла → синхронизация потребителей формата отчёта →
   docs → baseline/e2e-проверка (после подтверждения архитектуры тестов) →
   коммит.
3. Замороженные workflows формат отчётов ролей не меняют: если правка
   отчёта ломает их схемы — это сигнал остановиться и пересмотреть правку.

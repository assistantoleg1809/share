# deploy-status — наблюдатель деплоев

Узнать статус deploy-джобы, дождаться завершения, принести хвост лога
упавшего. Ничего не запускаешь и не правишь.

## Шаг 0 — проверка MCP из аргументов (обязательна)

Сервер не выбирается сам: MCP наблюдения (alias `mcp-deploy` → фактический
сервер) передаётся аргументами вызова вместе с джобой и номером запуска.
Не передан — запроси у пользователя, какой MCP использовать, и остановись
до ответа.

Один лёгкий вызов переданного сервера (статус известного деплоя или список
джоб). Сервер недоступен — верни блок ошибки и остановись:

```
❌ MCP <переданный сервер> недоступен
Симптом: <что произошло, дословно>
Рекомендации:
1. Выполнить /mcp и посмотреть статус сервера.
2. Сверить alias mcp-deploy с фактическим id в файле проектов
   (ship-kit.projects.md) и settings.json → mcpServers — их читает
   вызывающий, не ты.
3. Перезапустить сессию Qwen Code — клиент не перезапускает MCP сам.
```

## Протокол наблюдения

1. Узнай статус деплоя (номер или последний по джобе).
2. Идёт — подожди через shell `sleep 45` и проверь снова. Интервал не чаще
   45 секунд, очередь не дёргать.
3. Бюджет одного захода — около 8 минут. Деплой всё ещё идёт — верни
   state=RUNNING: вызывающий вызовет следующего наблюдателя.
4. Терминальные состояния: SUCCESS, FAILURE, UNSTABLE, ABORTED.
5. При FAILURE/UNSTABLE приложи: первую ошибку (errorSnippet) и последние
   ~100 строк лога деплоя (logTail).

## Ограничения

- Только MCP, переданный аргументами вызова (alias mcp-deploy). Файл проектов
  не читается. Shell — исключительно для `sleep`.
- Файлы не менять.

## Формат отчёта

state (RUNNING/SUCCESS/FAILURE/UNSTABLE/ABORTED/UNKNOWN), deployNumber,
url, errorSnippet, logTail.

## Соседние шаги

Запуск деплоя — скилл `deploy-trigger`; упал и нужен диагноз — скилл
`deploy-triage`. Переход — только явный вызов (пользователем или скиллом
`run`): сам следующий скилл не запускай.

# courier — ветка, pull request и цикл замечаний

Позиция **courier**: доставка кода — рабочая ветка, атомарные коммиты, PR,
замечания. Реализацию/правки делает исполнитель, передавший работу (обычно
analyst); сборкой занимается соседний шаг (operator).

## Правила действий (ask-таблица)

| действие | правило |
|---|---|
| пуш ветки | ask · всегда (карточка «пуш+PR» одной карточкой) |
| создание PR | ask · всегда (та же карточка) |
| пуш в тот же PR по замечаниям | ask · всегда (своя карточка) |
| чтение (PR, комментарии, задача) | allow |
| всё сверх переданных MCP | deny |

## Шаг 0 — проверки (обязательны)

1. MCP: лёгкие вызовы переданных mcp-jira (поиск по ключу) и mcp-bitbucket
   (список PR репозитория). Хоть один недоступен — блок ошибки и стоп
   (формат: ❌ MCP <сервер> недоступен; рекомендации — /mcp, сверка alias с
   ship-kit.projects.yaml и settings.json, перезапуск сессии, сеть/токен).
2. Git: работа только с чистого состояния, в отдельной ветке. Задание
   предписало worktree — работай строго внутри него (запомни `pwd` для
   отчёта).

## Режимы (задаётся в задании)

### implement + pr

1. Ветка по шаблону `<X>/<КЛЮЧ>` (шаблон из задания; дефолты `feature/` для
   задач, `bugfix/` для багов; тип неясен — один вопрос, не угадывай).
   Повторная попытка того же прогона — суффикс `-2`, `-3`, …
2. Коммиты уже готовы (исполнителем) или дозакоммить атомарно, с ключом Jira.
3. **prepare — карточка «пуш+PR»** (одна карточка на оба действия): ветка,
   число коммитов, **целевая ветка** (передана аргументом; сверяй: пуш в
   целевую ветку — NEVER, только рабочая `<X>/<КЛЮЧ>`), суть PR.
4. Подтверждение — только явное: ответ на карточку или дословное
   «подтверждаю …» в задании (`pre-approved(источник)`, без вопроса). Отказ →
   отчёт OK: false, GATE: declined, без пуша и без PR. **apply**: запушь
   ветку и создай PR через mcp-bitbucket (описание: что, зачем, как
   проверить, ссылка на задачу).
5. PR — часть стадии: замечания правятся пушем в **этот же** PR; новый PR —
   только на новый фикс после упавшей джобы (или по `humanDirective` для
   переделки слитой стадии).
6. Статусы Jira не менять; комментарий — только если задание просит.

```
OK: true|false
WORKTREE: <путь из pwd; пусто, если не в worktree>
BRANCH: <ветка>
PRID: <id PR>
PRURL: <url PR>
GATE: confirmed | pre-approved(источник) | declined
```

### check

Состояние PR: OPEN/MERGED/DECLINED, число замечаний, нерешённые комментарии
(автор, текст, id). Без изменений.

### fix

1. Замечание правит исполнитель кода (обычно analyst — точный скилл называет
   человек, если в задании не назван); твоя часть — обвязка.
2. Ответь на каждый комментарий (add_comment), зафиксируй `fix(pr): <суть>`.
3. **prepare — карточка пуша в ту же ветку**: ветка, коммиты, закрываемые
   замечания. Подтверждение как в implement+pr; отказ → без пуша.
4. **apply**: пуш в ту же ветку, закрытое замечание пометь resolve_comment.

## Ограничения

- Только переданные MCP; реестр не читается.
- Пуш — только в рабочую ветку `<X>/<КЛЮЧ>` текущей стадии; целевые ветки
  (branchDefault: main/master/develop/release, база PR) запрещены — сверяй с
  целевой, переданной аргументом; несоответствие — отказ до любых действий.
- Не начинать без changes-каталога OpenSpec в режиме implement+pr — верни
  «сначала нужен шаг спеки» (analyst).

## Формат отчёта

implement+pr → ok, branch, prId, prUrl, gate, worktree; check → state,
commentsCount, unresolved, url; fix → ok, commit, pushed, gate, summary.

## Соседние шаги

Спека и правки — analyst; после merge — operator (сборка). Переход — только
явный вызов (пользователем или скиллом `run`): сам следующий скилл не
запускай.

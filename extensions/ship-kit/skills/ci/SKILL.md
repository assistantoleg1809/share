# ci — запуск, ожидание, диагноз

Ты — фаза CI. Правки репозитория — не твои (их делает `task` по
диагнозу); ты запускаешь, ждёшь, читаешь лог и ставишь диагноз.
Следующую фазу сам не запускаешь.

## Правила действий

| действие | правило |
|---|---|
| чтение статуса/лога/тикетов/runbook | allow |
| запуск джобы | ask · всегда (карточка) |
| правки репозитория, пуш, статусы трекера | deny |
| всё сверх переданных MCP | deny |

## Шаг 0 — проверки

MCP: лёгкий вызов каждого переданного сервера (статус известной джобы,
поиск по ключу задачи). Недоступен — блок ошибки и стоп (как в `task`:
/mcp; сверка alias с settings.json → mcpServers; перезапуск сессии).
Alias не назван нигде — в проекте этого MCP нет: работай без него и
честно отметь (confidence ниже). Алиасы — лесенкой: **задание >
конвенция проекта > один вопрос** (конвенция — обычный контекст
сессии: файлы проекта). Ни одного и конвенции нет — вопрос и стоп.

   Роли алиасов: **tracker · docs · repo · build · deploy · quality ·
   vuln · chat** (несколько MCP роли — через запятую: все рабочие,
   чтение по всем, запись — куда названо заданием, иначе один вопрос).

**Транспортные сбои** (таймаут/обрыв MCP или git, сетевая ошибка)
— повторяй тот же вызов автоматически, до 2 повторов, без вопросов и
без повторного гейта (действие уже авторизовано, состояние не менялось);
исчерпаны — честная ошибка и стоп.

## Гейт запуска — три правила

Карточка-превью → явное «да» → запуск (правила как в `pr`; дословное
«подтверждаю …» в задании = pre-approved с источником). Карточка
запуска: kind (build/deploy), джоба (имя/путь), ветка и **её источник**
(MERGED-база или рабочая ветка — по решению человека при расхождении
статуса PR), стенд (для деплоя), параметры — **с источником каждого**:
задание → конвенция проекта → прошлая успешная джоба → ответ человека.
Сборка на рабочей ветке разрешена только после явного «да» человека;
успех на неподтверждённой базе помечай в плане ⚠ (жёлтым), не зелёным.
Прошлой успешной нет и аргументы не названы — спроси, не запускай
молча. **Ничего не искать**: не перечислять джобы, не сканировать
сервер, не угадывать пути.

**Структурный вопрос**: в сессии есть инструмент вопроса с закрытыми
опциями — карточку запуска и переспросы задавай им: согласие =
утвердительная опция, отказ = опция стопа; ответ текстом вне опций —
не подтверждение (ответь на содержание и переспроси один раз тем же
инструментом, затем стоп). Инструмента нет — текстовый канал:
подтверждение = дословная фраза целиком из списка «да» · «ок» ·
«подтверждаю» · «подтверждаю <действие карточки>»; отказ = «нет» ·
«стоп»; прочее — не решение: ответь на содержание, переспроси один
раз, затем стоп; инструмент определяется по списку инструментов сессии.

## Запуск и ожидание

Запусти, наблюдай статус; долгая джоба — отчитывайся этапами, а не
молчи. Завершилось — статус SUCCESS/FAILURE/UNSTABLE + номер и URL
джобы.

## Flaky-повтор

Таймаут вызова или явно flaky в логе — предложи повтор тех же
параметров одной строкой: «повторить те же параметры?» (инструментом
закрытых опций при наличии). Максимум один
повтор подряд; дальше — диагностика.

## Диагностика падения

Определи kind (build/deploy — из задания или имени джобы) и прочитай
**только свой командный файл**: build → [build.md](build.md), deploy →
[deploy.md](deploy.md).

1. Лог: найди первую настоящую ошибку; причину отдели от последствий.
2. Тикеты и runbook — из переданных MCP, по протоколу командного файла.
3. Собери диагноз: категория, rootCause, fixable (правится ли правкой
   кода/конфига репозитория), fixHint, knownIssues и **связанность** —
   первопричина в диффе ветки задачи или вне его (сверь с последними
   коммитами ветки через MCP репозитория/git).
4. Данных мало — честно confidence: low; догадку за диагноз не выдавай.

### Исходы диагноза

- fixable, первопричина **в диффе задачи** → HANDOFF: `task` (fix в
  ветку задачи, доставку в тот же PR).
- fixable, **посторонний** (инфра/конфиг CI/чужой код) → HANDOFF:
  `task` (тех-ветка от базовой, отдельный PR; артефакты спеки не
  трогать).
- не-код (infra/devops-known и т.п.) → задача в
  `runs/<ПРОЕКТ>/<КЛЮЧ>/issues.md` + рекомендация эскалации человеку.
- Перезапуск после фикса — новая карточка запуска.

## Верификация

В отчёт — дословный хвост лога (последние строки упавшей/успешной
джобы) и статус с номером. Без свежих строк успех не заявляй.

## Ограничения

- Только переданные MCP; правки репозитория запрещены.
- Статусы задач трекера не менять. Ничего не искать.
- План прогона (если ведётся) отмечай в `runs/<ПРОЕКТ>/<КЛЮЧ>/plan.md`;
  записи журнала — каждая с даты и времени `ГГГГ-ММ-ДД ЧЧ:ММ` (локальное
  время), затем событие.

## Формат отчёта

Разбор диагноза — свободным текстом в теле, дословный хвост лога — над
блоком. Заверши строками:

```
OK: true|false
JOB: <имя джобы> · #<номер> · <SUCCESS|FAILURE|UNSTABLE|—>
CATEGORY: <категория или пусто>
FIXABLE: true|false
RELATED: task-diff | external | —
CONFIDENCE: high|medium|low
HANDOFF: task | task-tech | human | —
```

## Завершение фазы

Падение fixable — продолжай без остановки фазой фикса: вызови `task`
(fix по диагнозу), после него — перезапуск слота ci под новой 🔒-карточкой.
Не-код — issues.md и стоп. Зелёные фазы до конца плана — финальный
отчёт, предложение архивации прогона (правило `task`: архив
`runs/archive/…`, судьба worktree — выбор человека) и стоп. Одиночный вызов человеком вне плана — без цепочки.

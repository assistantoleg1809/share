# Гейты необратимых действий, транспорт-CI и стенды деплоя — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Поставить под подтверждение человеком все необратимые действия контура (запуски джоб сборки/деплоя, пуши, создание PR), отвязать комплект от Jenkins как единственного CI-транспорта (контракт трёх операций) и добавить стенды деплоя DEV→ST→IFT→PSI (обязательны IFT и PSI).

**Architecture:** Гейт — секция в ролях (jobs/pr/repair), выполняющих необратимое действие: явный вызов роли человеком не должен обходить контроль; `run` фиксирует гейты в плане, останавливается по отклонению, повтор по таймауту наследует подтверждение. Транспорт — контракт операций «запуск/статус/лог» без бренда CI; имена инструментов опционально пинуются в реестре. Стенды — упорядоченный `deploy.stands` в реестре, итерация стендами в `run`, лимит попыток на стенд.

**Tech Stack:** markdown-скиллы ship-kit (`skills/*/SKILL.md`), md-реестр (`ship-kit.projects.md`), python3-валидатор реестра (создаётся планом тестов), моки `mcp/` (e2e-стенд).

**Spec:** решения пользователя из сессии 2026-11-11 (раздел «Решения» ниже), `docs/ship-kit.md`, `skills/adapt-kit/SKILL.md`.

## Решения (утверждены пользователем 2026-11-11)

1. **Гейт-действия — четыре**: запуск джобы сборки; запуск джобы деплоя (каждый стенд отдельно); push ветки (из `repair`, из `pr`, fix-циклы); создание PR. Каждый запуск/пуш — свой гейт. Коммиты — не гейт (локальны и обратимы до пуша). Связка «пуш ветки + создание PR из неё» может закрываться одним вопросом, если оба действия названы в карточке.
2. **Таймауты не переспрашивают**: повторный запуск той же джобы с теми же параметрами/стендом наследует гейт, если предыдущий подтверждённый запуск (а) оборвался по таймауту вызова (итог неизвестен) или (б) упал с категорией таймаута по диагнозу. В плане — `gate=inherited (таймаут #N)`. Изменение параметров/ветки/стенда или фикс между запусками — снова полный гейт.
3. **Механика гейта**: перед действием роль задаёт вопрос (ask_user_question) с карточкой: действие(я), kind, джоба, ветка, стенд (деплой), параметры и их источники, ожидаемая длительность. Отказ → отчёт `ok=false, gate=declined`; `run` останавливает прогон (STOPPED, причина «гейт отклонён»), без молчаливого подбора альтернатив.
4. **Гейт живёт в ролях** (`jobs`, `pr`, `repair`), не только в `run` — явный вызов роли человеком тоже под гейтом.
5. **Закрытие гейта — только явные слова человека**: ответ на вопрос или дословное «подтверждаю …» в задании (путь для headless/e2e-прогонов, где вопрос задать некому; e2e-промпты несут подтверждение). Гейт пишется в план с источником.
6. **Пуш в целевые ветки запрещён**: пуш — только в рабочую ветку шаблона `<X>/<КЛЮЧ>`, созданную в этом прогоне. Целевые ветки — `branchDefault` реестра (main/master/develop/release) и база PR — никогда; изменения попадают туда только merge PR человеком. Роль сверяет ветку пуша с шаблоном и целевой веткой (передана аргументом); несовпадение — отказ до действий. Ужесточение инварианта «push только в рабочие ветки» (сейчас запрещены только main/master).
7. **Режим реализации — входной параметр**: `impl=openspec` (дефолт) | `impl=direct`. `pr` при `openspec` делегирует выполнение tasks.md скиллам OpenSpec (не установлены — честная ошибка, не тихий fallback); при `direct` — выполняет сам по чек-листу. `run` берёт `impl` из задания и передаёт в `pr`. Ступень спеки (openspec) не меняется.
8. **Транспорт CI = контракт, а не бренд**: MCP-контракт трёх операций — **запуск** (джоба+ветка/параметры → номер+URL), **статус** (номер → состояние), **лог** (номер → текст). Имена инструментов не фиксированы: реестр может пиновать `mcp-build.tool.run|.tool.status|.tool.log` (аналогично `mcp-deploy`); не запинковано — роль находит инструмент по описанию на переданном сервере (текущее поведение). Jenkins/GitLab CI/TeamCity — без разницы. adapt-kit §3: проектный скилл нужен, только если контракт не сходится (деплой = параметр сборки, цепочки вызовов), а не просто «не Jenkins».
9. **Стенды**: `deploy.stands: DEV, ST, IFT, PSI` — упорядоченное подмножество канонического порядка; обязателен при наличии `mcp-deploy.*`; **IFT и PSI обязательны в составе**, DEV/ST опциональны. Опционально `mcp-deploy.job.name.<СТЕНД>` — своя джоба на стенд. Стенд уходит в `jobs` параметром запуска + полем отчёта и в карточку гейта.
10. **Деплой в `run`**: задание назвало стенд → только он; «полный прогон» → стенды по порядку, каждый запуск — свой гейт; стенд не назван и не полный прогон → вопрос пользователю (уже есть в цепочке разрешения аргументов). `runLimit.deploy` становится лимитом **на стенд**; `runBudget` — общий предохранитель.

Не трогаются: командные файлы `diagnosis/{build,deploy}.md`, `repair/{build,deploy}.md` (упоминания Jenkins там — контекст конкретной команды, зона владения команды); мок `mcp/jenkins` (id стенда, проверяет alias-механику; параметр `stand` добавляет только план тестов при необходимости).

# Архитектура тестов скилл-контура ship-kit

**Статус: план; реализация и запуск тестов — только после подтверждения
пользователя.** Все тестовые прогоны с моделью — исключительно
`glm-5.3-flash`.

Контур после консолидации 15→9 (2026-11-10): `run` (диспетчер), `jobs`
(запуск/ожидание, kind=build|deploy), `diagnosis` и `repair` (+ командные
файлы build.md/deploy.md), `openspec`, `pr`, `review`, `registry`,
`adapt-kit`; md-реестр, `skill-runs/`.

## Уровень 1 — статические контракты скиллов (без модели, детерминированно)

Скрипт локальной проверки (python3/bash, ноль зависимостей), вход — каталог
`skills/`:

1. **Frontmatter**: `name` = имя каталога, kebab-lowercase; `description`
   непустая, ≤1024 символа, начинается с «Использовать, когда».
2. **Состав**: ровно 9 каталогов — run, jobs, diagnosis, repair, openspec,
   pr, review, registry, adapt-kit; в diagnosis/ и repair/ обязательны
   build.md и deploy.md.
3. **Alias-чистота**: в телах скиллов нет обращений к каноническим id MCP
   (`MCP jenkins`, `jenkins в settings.json`, `mcp__jenkins`); бренд CI в
   значении «джоба/конфиги Jenkins» — разрешён (словарь исключений).
4. **Запрет контекста исполнения**: нет слов «саб-агент», «сабагент»,
   «основной агент» как предписания, где выполнять скилл.
5. **Обязательные секции**: «Шаг 0», «Ограничения», «Формат отчёта»;
   в diagnosis/repair — блок обязательного чтения командного файла своего
   kind; в jobs — оба режима (запуск/ожидание) и оба формата отчёта.
6. **Snapshot форматов отчётов**: поля отчётов скиллов зафиксированы
   в репо; diff при изменении = сознательное изменение контракта
   (потребители — человек и `run`).

## Уровень 2 — схема md-реестра (без модели)

Валидатор `ship-kit.projects.md`: обязательные ключи (`jiraKey`, `repoSsh`,
`ce`), alias-ключи только из фиксированного списка, для
`mcp-build`/`mcp-deploy` — `job.path`+`job.name`, для `mcp-sonar` —
`projectKey`, корректный `[default]`, при `mcp-deploy.*` — `deploy.stands`
(значения DEV/ST/IFT/PSI, канонический порядок, IFT/PSI обязательны). Проверяется
пример (docs/ship-kit.projects.example.md) и тестовые файлы.

## Уровень 3 — baseline-сценарии скиллов (модель = flash)

По методике writing-skills (RED→GREEN): для `run`, `jobs`, `diagnosis`,
`repair`, `pr`, `review`, `registry`, `adapt-kit` — сценарий давления «без
скилла» (зафиксировать дословно: правит реестр мимо схемы, сам вызывает
diagnosis после jobs, смешивает командные инструкции build/deploy, вносит
проектные детали в тело скилла), затем тот же сценарий «со скиллом» —
комплайенс. Отложенная RED-фаза: скиллы написаны до подтверждения
архитектуры (решение пользователя), поэтому RED-сценарий гоняется без
скилла немедленно перед GREEN-прогоном — проверяем против реального
baseline, а не воображаемого. Отдельный негатив: в diagnosis/repair
проверять, что загружен только командный файл своего kind.

## Уровень 4 — e2e скилл-контура на стенде (модель = flash)

Стенд (моки `mcp/`, таргет с багом, bare-репозиторий) + md-реестр стенда
с alias на моки. Сценарии:

1. **Полный прогон `run`**: items-конвейер — спека → PR → красная сборка
   → diagnosis → фикс → PR-2 → зелёная. Проверки: скиллы получали только
   свои alias; `skill-runs/<тег>/plan.md` отмечает items и гейты (раздел
   «Гейты», pre-approved из задания); провал ушёл в `issues.md`; лимиты
   `runLimit.*`/`retryLimit` соблюдены; push только в рабочую ветку.
2. **Негатив «явный вызов ≠ цепочка»**: явный вызов `jobs` (ожидание) на
   упавшей сборке — после отчёта НИКАКОГО diagnosis/фикса (контроль по
   логам вызовов мока).
3. **Наследование аргументов**: `run` без явных параметров взял их из
   предыдущей успешной джобы, переопределил номер; неизвестные — спросил
   и записал в план (контроль по состоянию jenkins-мока и plan.md).
4. **Фикс-PR и ожидание апрува**: стабильное код-падение → фикс → PR из
   fix-ветки (гейт «пуш+PR» закрыт подтверждением из задания) → WAITING
   (прогон остановился, план зафиксировал ожидание, бюджет заморожен) →
   «продолжи прогон» после MERGED → пересборка.
5. **Реестр через `registry`**: добавление проекта/элемента с валидацией
   (уровень 2 ловит битые файлы, включая `deploy.stands`).
6. **Гейт без подтверждения**: задание без слов подтверждения —
   гейт-вопрос в выводе, ноль вызовов trigger по логам мока.
7. **Стенды и деплой-фикс без правки кода**: `deploy.stands: IFT, PSI`;
   деплой-падение категории infra → правки кода нет → PR не создаётся,
   ожидание починки джобы; после «продолжи прогон» — повтор, стенды по
   порядку.

## Порядок внедрения (после подтверждения)

1. Статический скрипт уровней 1–2 + прогон на текущем репо (зелёный или
   реальные отступления — правим).
2. RED-baseline сценариев уровня 3 (flash).
3. GREEN-прогоны уровня 3, правка скиллов по находкам.
4. e2e уровня 4 на стенде (flash), находки — в e2e/e2e-runs.md.
5. Встраивание: статические проверки — в чек-лист коммита эталона
   (adapt-kit §4).

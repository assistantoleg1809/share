# Архитектура тестов скилл-контура ship-kit

**Статус: архитектура предъявлена; реализация и запуск тестов — только после
подтверждения пользователя.** Все тестовые прогоны с моделью — исключительно
`glm-5.3-flash` (дешёвая; без неё агенты уходят на дефолт сессии и сжигают
кредиты — урок прогона 13).

Контекст: агенты/workflows заморожены, тестируется **скилл-контур**
(docs §10): 11 ролей на MCP-alias, мета-скиллы `projects`/`run`/
`adapt-skills`, md-реестр, `skill-runs/`.

## Уровень 1 — статические контракты скиллов (без модели, детерминированно)

Скрипт локальной проверки (python3/bash, ноль зависимостей), вход — каталог
`skills/`:

1. **Frontmatter**: `name` = имя каталога, kebab-lowercase; `description`
   непустая, ≤1024 символа, начинается с «Использовать, когда».
2. **Alias-чистота ролей**: в телах 11 ролей нет канонических id как
   обращений к MCP (`MCP jenkins`, `jenkins в settings.json`, `mcp__jenkins`
   и т.п.); бренд CI в значении «джоба/конфиги Jenkins» — разрешён
   (словарь исключений).
3. **Запрет контекста исполнения**: в ролях нет слов «саб-агент»,
   «сабагент», «основной агент» как предписания, где выполнять скилл.
4. **Обязательные секции роли**: «Шаг 0», «Ограничения», «Формат отчёта»;
   у ролей конвейера — «Соседние шаги» с припиской про явный вызов.
5. **Golden-снимки форматов отчётов**: поля отчётов ролей не изменились
   против замороженных потребителей (schemas build/deploy-autofix) —
   снимок полей в репо, diff при изменении = сигнал остановиться
   (инвариант adapt-skills №4).

## Уровень 2 — схема md-реестра (без модели)

Валидатор `ship-kit.projects.md` (тот же скрипт): обязательные ключи
(`jiraKey`, `repoSsh`, `ce`), alias-ключи только из фиксированного списка,
для `mcp-build`/`mcp-deploy` — `job.path`+`job.name`, для `mcp-sonar` —
`projectKey`, корректный `[default]`. Проверяется пример
(docs/ship-kit.projects.example.md) и тестовые файлы.

## Уровень 3 — baseline-сценарии скиллов (модель = flash)

По методике writing-skills (RED→GREEN): для `projects`, `run`,
`adapt-skills` — сценарий давления «без скилла» (зафиксировать дословно,
что модель делает не так: правит реестр мимо схемы, сам вызывает триаж
после статуса, вносит проектные детали в тело скилла), затем тот же
сценарий «со скиллом» — комплайенс. Отложенная RED-фаза: скиллы уже
написаны доarchitecture-подтверждения (решение пользователя), поэтому
RED-фаза восполняется задним числом: сценарий гоняется без скилла
немедленно перед GREEN-прогоном, чтобы проверять skill против реального
baseline, а не воображаемого.

## Уровень 4 — e2e скилл-контура на стенде (модель = flash)

Существующий стенд (моки `mcp/`, таргет с багом, bare-репозиторий) плюс
md-реестр стенда с alias на моки. Сценарии:

1. **Полный прогон `run`**: спека → реализация → PR → красная сборка →
   триаж → фикс → зелёная. Проверки: роли получали только свои alias;
   `skill-runs/<тег>/plan.md` отмечает выполненные шаги; провал ушёл в
   `issues.md` задачей с фиксированной ошибкой; лимиты `runLimit.*`
   соблюдены; push только в рабочую ветку.
2. **Негатив 7.3**: явный вызов `build-status` на упавшей сборке — после
   отчёта НИКАКОГО triage/фикса (контроль по логам вызовов мока).
3. **Наследование аргументов**: `run` без явных параметров запуска взял
   их из предыдущей успешной джобы, переопределил номер сборки (контроль
   по состоянию jenkins-мока).
4. **Реестр через `projects`**: добавление проекта/элемента с валидацией;
   прямая правка файла мимо скилла — вне теста (дисциплина), но валидатор
   уровня 2 ловит битые файлы.

## Уровень 5 — замороженный контур

Не тестируется новое (заморозка). Существующий e2e build-autofix остаётся
как регресс-прогон при пере-установке расширения; изменения скилл-контура
его не должны ломать (проверка golden-снимками уровня 1).

## Порядок внедрения (после подтверждения)

1. Статический скрипт уровней 1–2 + прогон на текущем репо (должен быть
   зелёным или найти реальные отступления — их правим).
2. RED-baseline сценариев уровня 3 (flash).
3. GREEN-прогоны уровня 3, правка скиллов по находкам.
4. e2e уровня 4 на стенде (flash), находки — в e2e-run.md.
5. Встраивание: статические проверки — в чек-лист коммита эталона
   (adapt-skills §4).

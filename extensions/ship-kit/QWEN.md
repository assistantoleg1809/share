# Ship Kit

Комплект скиллов для конвейера «Jira → OpenSpec → правки → PR → ревью →
сборка → деплой → исправление» на **стадийной модели v2** (2026-11-13).
Полная документация: [docs/ship-kit.md](docs/ship-kit.md).

## Что даёт расширение

- **7 скиллов** (`/ship-kit:<имя>`, «Профессии»):
  - `run` — диспетчер: обход стадий по `pipelineOrder`, переходы
    `nextStageId`/`fixesStageId`/`triggeredBy`, счётчики **по id стадии**,
    loop guard, карточки гейтов, план `skill-runs/<тег>/`, WAIT/resume;
  - `registry` — единственная точка ведения `ship-kit.projects.yaml`
    (стадии, записи знания, `servers:`, `executors:`), валидация, миграции
    `formatVersion`;
  - `analyst` — спека (контекст Jira/Confluence/mmap + OpenSpec-изменение),
    реализация, код-фиксы;
  - `courier` — ветка `<X>/<КЛЮЧ>`, коммиты, PR, цикл замечаний;
  - `operator` — запуск (🔒) и ожидание джоб;
  - `doctor` — режимы `diagnose` (категория/fixable/fixHint/knownIssues;
    только чтение) и `fix` (TDD-фикс, 🔒 карточка пуша); командные файлы
    `build.md`/`deploy.md` по kind;
  - `adapt-kit` — обязательные правила доработки комплекта.
- **Позиции и исполнители**: словарь позиций (analyst, courier, operator,
  detective, mechanic) — манифест `docs/ship-kit.positions.yaml`; набор
  позиций стадии выводится из `kind`; проект подменяет исполнителя в
  `executors:` одной строкой; маршрутизация «категория диагноза → позиция» —
  `fixRouting` манифеста (FIX_BUILD: код→analyst, не-код→mechanic;
  FIX_DEPLOY: любое fixable→mechanic).
- **Реестр** `ship-kit.projects.yaml` (в корне проекта или
  `~/.qwen/ship-kit/projects.yaml`): стадии с kind и ссылками знаний
  (`knowledgeRef`/`diagnosisRef`/`repairRef`, дефолт = `knowledgeRef`),
  записи знания с endpoints (alias → serverId, `runnerKind` JENKINS/CUSTOM,
  джобы, стенды), `servers:` (адреса — только в settings.json), лимиты,
  `errorPolicy`. Ведение — только `registry`; смена формата — через
  `formatVersion` + миграции.
- **Гейт-контракт** (необратимое: запуск джобы / пуш / PR): prepare →
  confirm → apply; карточка = payload с превью и источниками; fail-closed;
  подтверждение привязано к карточке — изменение payload = новый вопрос;
  flaky-повтор идентичной карточки наследует гейт без вопроса.

## Инварианты скилл-контура

Только MCP из аргументов вызова (alias→сервер разрешает вызывающий по
реестру); реестр исполнители не читают; ничего не искать (и исполнителей не
подбирать — trust discovery-only); явный вызов одного скилла не запускает
следующие — цепочку ведёт только `run`; правки репозитория — только через PR;
push только в рабочие ветки `<X>/<КЛЮЧ>`, целевые ветки (branchDefault, база
PR) запрещены; статусы Jira не трогать; **гейты необратимых действий** —
только после явного подтверждения человека, отказ = стоп. Исходы диагноза:
flaky → retry; fixable → позиция по манифесту; not-fixable → issues.md,
кроме `infra`/`devops-known` у деплоя → WAIT (прогон и бюджет заморожены,
«продолжи прогон <тег>»); `errorPolicy.unfixableCategories` — вето на
фикс-стадию. Loop guard: круг «фикс → PR → MERGED → перезапуск» = +1 к
`maxFixAttempts`, новый PR счётчик не сбрасывает.

## История прогонов

`skill-runs/<тег>/` в корне проекта: `plan.md` (фаза = id стадии, позиции,
счётчики, гейты с карточками, аргументы джоб с источниками, журнал) +
`issues.md` (провал = отдельная задача, чинит другой скилл). План — токен
возобновления («продолжи прогон <тег>»).

## Условия работы

- Скиллы MCP-серверы не выбирают: вызывающий (человек или `run`) передаёт
  alias→сервер аргументами из yaml-реестра.
- Транспорт CI — контракт трёх операций (запуск/статус/лог); CI-специфика —
  в командных файлах knowledge-пака, не в скиллах.
- Имена джоб и serverId — в реестре, никогда не хардкодятся.
- Тестовые/e2e-прогоны — только на glm-5.3-flash.
- openspec-слой проекта: `openspec/` в корне расширения (per-project корни
  для мультипроектного репо).

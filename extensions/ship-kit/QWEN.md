# Ship Kit

Комплект скиллов для конвейера
«Jira → OpenSpec → правки → PR → ревью → сборка → деплой → исправление».
Полная документация: [docs/ship-kit.md](docs/ship-kit.md)
(состав, инварианты, items-конвейер со схемами, e2e-стенд, чек-лист
адаптации).

## Статус разработки (2026-11-11)

**9 скиллов**; архитектура — **items-конвейер** (решение по итогам
исследования, 2026-11-11):
конвейер = последовательность `item(action, skill, knowledge, PR)`, дефолт
`openspec → build → deploy`; PR — часть item; у деплоя PR может
отсутствовать, когда правки кода нет (решение — починка джобы). План
задач, исследование и тестовый стенд — в воркспейсе разработки репозитория
(`dev/ship-kit/`; конвенция — `dev/<имя-расширения>/`), в поставку не
входят.

## Что даёт расширение

- **9 скиллов** (`/ship-kit:<имя>`; тела — в `skills/`):
  - `run` — диспетчер items-конвейера: вход «`<тег> [items|скилл] <что
    сделать>`», дефолтный конвейер item1–item3, план `skill-runs/<тег>/`
    (состояние + items + аргументы джоб с источниками + гейты), циклы
    фиксов (код — openspec-скилл по выбору человека; не-код — MCP из
    реестра + knowledge-пак), retry-lazy по flaky/таймауту (`retryLimit`),
    стенды с лимитом на стенд, стоп по отказу гейта, `runBudget` заморожен
    в ожидании;
  - `jobs` — запуск (🔒 гейт с карточкой: kind/джоба/ветка/стенд/
    параметры; один вызов, без ретраев; gate=confirmed/pre-approved/
    inherited/declined) и ожидание (статус/лог/ETA/possiblyStuck);
  - `diagnosis` — разбор падения: категория/fixable/knownIssues;
    командные файлы build.md|deploy.md (knowledge-пак) по kind;
  - `repair` — не-кодовый фикс по диагнозу, TDD (красный → правка →
    зелёный), коммит, 🔒 гейт пуша, push в рабочую ветку PR;
  - `openspec` — контекст (Jira/Confluence/mmap) и оформление изменения
    OpenSpec; реализацию tasks.md делают скиллы OpenSpec;
  - `pr` — обвязка контура: ветка `<X>/<КЛЮЧ>`, 🔒 гейт «пуш+PR» (одна
    карточка), PR — часть item; замечания: фикс openspec-скиллом (точный
    выбирает человек) → 🔒 пуш в тот же PR → resolve;
  - `review` — ревью диффа, только чтение, вне цепочки run;
  - `registry` — единственная точка ведения `ship-kit.projects.md`;
  - `adapt-kit` — обязательные правила доработки комплекта (читать перед
    любой правкой).
- **Инварианты скилл-контура**: только MCP из аргументов вызова
  (alias→сервер разрешает вызывающий); файл проектов роли не читают;
  ничего не искать; явный вызов одного скилла не запускает следующие —
  цепочку ведёт только `run`; push только в рабочие ветки `<X>/<КЛЮЧ>`,
  целевые ветки (branchDefault, база PR) запрещены; статусы Jira не
  трогать; **гейты необратимых действий** — запуск джобы/пуш/создание PR
  только после явного подтверждения человека, отказ = стоп.
- **Реестр проектов** (md): `ship-kit.projects.md` в корне проекта или
  `~/.qwen/ship-kit/projects.md`: jira-ключ, ssh-репо, КЭ, alias MCP
  (`mcp-build`/`mcp-deploy`/`mcp-sonar`/…) → фактический сервер (+опционально
  `<alias>.tool.run|.status|.log`), пути/названия джоб (в т.ч. на стенд),
  `deploy.stands` (DEV, ST, IFT, PSI; IFT/PSI обязательны), `knowledge`
  (пак знаний, дефолт jenkins), лимиты (`runLimit.*`, `retryLimit`,
  `fixRetries`, `runBudget`). Ведение — только скилл `registry`.
- **История прогонов**: `skill-runs/<тег>/` в корне проекта — plan.md
  (состояние, items, аргументы джоб с источниками, гейты, журнал) +
  issues.md (провал = отдельная задача с ошибкой, чинит другой скилл).
  План — токен возобновления («продолжи прогон <тег>»).

## Условия работы

- Скиллы MCP-серверы не выбирают: вызывающий (человек или скилл `run`)
  передаёт alias→сервер аргументами из md-реестра.
- Транспорт CI — контракт трёх операций (запуск/статус/лог), не бренд;
  CI-специфика — в knowledge-паке (командные файлы), не в скиллах.
- Имена джоб (сборка/деплой/стенды) живут в md-реестре или передаются
  args, никогда не хардкодятся.
- Тестовые/e2e-прогоны — только на glm-5.3-flash.

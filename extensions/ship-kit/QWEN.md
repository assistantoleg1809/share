# ship-kit

Три скилла-фазы для цикла «задача → правки → PR → сборка/деплой».
Никакой конфигурации проекта: всё нужное передаётся аргументами вызова.
Полная документация: [docs/ship-kit.md](docs/ship-kit.md).

## Состав

| Скилл | Фаза | Гейт 🔒 |
|---|---|---|
| `task` | контекст → спецификация (опционально) → реализация TDD → коммиты; fix по замечанию/диагнозу | — |
| `pr` | ветка → карточка «пуш+PR» → PR → цикл замечаний → ожидание MERGED | пуш+PR одной карточкой; пуш фикса |
| `ci` | карточка запуска → запуск → ожидание → лог → диагноз падения | каждый запуск джобы |

Вызов: `/ship-kit:<имя> <КЛЮЧ> <задание>, mcp-<роль>=<сервер>, …` —
роли алиасов: **tracker · docs · repo · build · deploy · quality ·
vuln · chat**; одна роль может иметь несколько MCP (через запятую:
чтение по всем, запись — куда названо заданием, иначе вопрос).
Алиасы только аргументами вызова/конвенцией проекта, скиллы сверяют
их с `settings.json → mcpServers` на Шаге-0.

## Инварианты

- Один вызов = одна фаза: один Шаг-0, один контракт отчёта в конце;
  следующая фаза — handoff-строкой в отчёте, без авто-переходов.
- Аргументы вызова и спека — лесенкой: задание > конвенция проекта
  (обычный контекст сессии; формат комплектом не фиксируется;
  несколько источников — каскадом: репо-файл мастер → центральный
  каталог-индекс; запись назвала репозиторий, а cwd не он — task
  клонирует и работает в клоне) > один вопрос; конвенция может
  обязывать спеку и называть инструмент.
- План прогона `runs/<ПРОЕКТ>/<КЛЮЧ>/plan.md` — всегда (без внешних
  скиллов: дефолт task → pr 🔒 → ci 🔒); фазы идут по плану без
  остановки, паузы — только 🔒-гейты и вопросы; одиночный вызов
  человеком вне плана выполняется без цепочки.
- Гейты — три правила: карточка-превью → явное «да» → действие; отказ =
  стоп без перебора; дословное «подтверждаю …» в задании = pre-approved;
  есть в сессии инструмент вопроса с закрытыми опциями — гейт
  спрашивается им (согласие = опция, текст вне опций ≠ подтверждение).
- Пуш — только в рабочие ветки `<X>/<КЛЮЧ>`; целевые ветки
  (main/master/develop/release, база PR) запрещены.
- Статусы задач трекера не меняет никто; «ничего не искать» — джобы и
  пути из задания или вопроса, не сканированием серверов.
- `OK: true` — только с дословными свежими строками прогона/статусов.
- Фикс по диагнозу CI — по связанности: первопричина в диффе задачи →
  тот же PR; посторонняя → тех-ветка от базовой и отдельный PR,
  артефакты спеки не трогать; не-код → issues.md + человек.
- Спецификация — инструментом спекирования проекта, найденным в
  рантайме по списку скиллов сессии (несколько — один вопрос, ни одного
  — мини-дизайн в чате). Имя инструмента в файлах комплекта не
  упоминается.
- Порядок прогона с внешними скиллами: чек-лист из перечня задания →
  одно подтверждение → `runs/<ПРОЕКТ>/<КЛЮЧ>/plan.md`; опциональный макрос
  `ship-kit.workflows.md` разворачивает типовой набор в перечень.

## Состояние прогона

`runs/<ПРОЕКТ>/<КЛЮЧ>/plan.md` — чек-лист фаз (попытки числом в строке),
текущая фаза, журнал (каждая запись — с даты и времени `ГГГГ-ММ-ДД
ЧЧ:ММ`); токен возобновления («продолжи <КЛЮЧ>»): скилл
читает план, сверяется с git/статусами и продолжает (`<ПРОЕКТ>` —
конвенция > имя каталога репо; легаси `skill-runs/` читается).
Провалы — задачами в `runs/<ПРОЕКТ>/<КЛЮЧ>/issues.md` (чинит другой
вызов). Завершённый прогон архивируется в
`runs/archive/<ПРОЕКТ>/<КЛЮЧ>/` (worktree `<ПРОЕКТ>-<КЛЮЧ>`: удалить
по гейту или `git worktree move` в архив). Рекомендация
`.gitignore`: `runs/`.

## Сложные случаи

Полный диспетчерский конвейер v2 — рабочий образец
`examples/conveyor/` в корне репо: не продукт, «оживляется» копированием
скиллов в `.qwen/skills` проекта.

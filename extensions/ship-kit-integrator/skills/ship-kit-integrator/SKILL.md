# Ship Kit Integrator

## Обзор

Сопоставляет фактические MCP-серверы контура с каноническими id, по которым
агенты ship-kit обращаются к серверам. Решения без сомнений принимает по
правилам, сомнения собирает ОДНИМ списком вопросов с рекомендациями.

Скилл исполняется на быстрой модели (qwen 3.8 flash): каждый шаг — правило или
таблица. Никаких «разберись на месте»: если правило не сработало — это вопрос,
а не догадка.

## Канон ship-kit

| Канонический id | Ожидаемые инструменты | Кто использует | Сервера нет → |
|---|---|---|---|
| `jenkins` | trigger_build, get_build_status, get_build_log, trigger_deploy, get_deploy_status, get_deploy_log | build/deploy-trigger, -status, -triage, -fix; probe шага 0 | BLOCKED: конвейер сборки/деплоя невозможен |
| `jira` | поиск и чтение задач | openspec, build/deploy-triage, implementer, скан воркера | деградация: нет тикетов для спеки/триажа/воркера |
| `confluence` | чтение страниц | openspec, build/deploy-triage | деградация: триаж без runbook |
| `sonar` | issues | build/deploy-triage | деградация: триаж без качества |
| `bitbucket` | create_pr, get_pr, list_pr_comments, add_pr_comment, resolve_comment | implementer, triage | деградация: нет PR-цикла, воркер невозможен |
| `mmap` | схемы/знания | openspec | деградация: спека без базы знаний |

## Шаг 1 — собрать факты (только MCP)

1. Прочитать `settings.json → mcpServers` в обоих скоупах:
   проектный `.qwen/settings.json`, пользовательский `~/.qwen/settings.json`.
2. Для каждого id записать: transport (command/httpUrl) и список инструментов
   (из конфигурации сервера; если не видно — из `/mcp` текущей сессии).
3. HTTP-серверы: поле обязано быть `httpUrl` (`url` = легаси-SSE, сервер не
   поднимется) — неверное поле фиксируется как отдельный пункт вопроса.
4. Составить плоскую таблицу: `id | transport | инструменты`.

Смотреть ТОЛЬКО MCP. Агентов, скиллов и прочих настроек это не касается.

Примечание: merge/decline PR в ожидаемые инструменты bitbucket НЕ входят —
сливает человек. Лишние сверх роли инструменты у смапленного сервера и id,
не смапленный ни на один канон, — отдельная строка вопросов и примечание
в итог: в режиме расширения такие серверы достаются всем агентам с
deny-list (утечка лишних операций).

## Шаг 2 — применить правила маппинга

Пройти каноны из таблицы выше по очереди. Для каждого:

| Ситуация | Решение |
|---|---|
| id контура точно равен канону | AUTO — маппинг принят без вопросов |
| id содержит канон как отдельное слово (`jenkins-corp`, `corp-jenkins`, `jenkins_prod`) и инструменты покрывают роль | КАНДИДАТ — идёт в вопрос |
| кандидатов несколько (дубли контуров: `jenkins` и `jenkins-test`) | ВОПРОС: перечислить всех кандидатов |
| кандидатов нет | MISSING — вопрос: добавить сервер или роль не нужна |
| имя похоже, но инструментов роли нет (например, у «jenkins»-кандидата нет trigger) | НЕ кандидат: вернуть в MISSING, в вопросе назвать причину |
| id не подходит ни под один канон (лишний сервер контура) | ВОПРОС: убрать из скоупа сессий с ship-kit или оставить (утечка операций агентам) |

«Отдельное слово» = канон отделён дефисом, подчёркиванием или границей строки
(`myjenkins` — НЕ кандидат, а повод для вопроса отдельным пунктом).

## Шаг 3 — задать вопросы (одним списком)

Собрать ВСЕ вопросы и задать ОДНИМ сообщением. Формат каждого:

1. Что увидел — факты: id, transport, инструменты.
2. Варианты по номерам; вариант 1 — рекомендованный, с пометкой «(рекомендую)».
3. Последствие ошибки — одной строкой.

Запрещено: вопрос без рекомендации; вопрос без последствия; выдавать вопросы
по одному вместо общего списка.

## Шаг 4 — итог

1. Таблица `канон → фактический id → источник решения (auto / ответ) → инструменты`.
2. Вердикт контура: `READY` (все шесть) / `PARTIAL` (список деградаций) /
   `BLOCKED` (нет jenkins).
3. Примечание об утечке: лишние серверы контура и инструменты сверх роли —
   кто их получит в режиме расширения.
4. Готовые правки: какие записи `mcpServers` переименовать в settings.json
   (только id, конфигурацию серверов не трогать).

## Функция B — анализ запусков по ID сессий

Вход: ID сессий Qwen. Транскрипты лежат в `~/.qwen/projects/<slug-проекта>/<id>.jsonl`
(если файла нет — перечислить каталог проекта и уточнить slug).

В каждой сессии искать метки сбоев:

- `❌ MCP <server> недоступен` — сервер не подключён или id не канонический;
- agent failed / null в списке failures — какой шаг упал и чем закончился;
- `TRIGGER_FAILED` / `TRIAGE_FAILED` / `FIX_FAILED` / `WATCH_TIMEOUT` /
  `MCP_UNAVAILABLE` — итоговые статусы workflows;
- `FIX_FAILED` рядом с isolation/worktree — грязное рабочее дерево
  (незакоммиченные файлы; см. run-журналы и .gitignore);
- повторяющиеся retries/watcher'ы — ожидание вне лимита.

Вывод — таблица: `сессия → симптом → чего не хватает → конкретная донастройка`
(запись в settings.json / аргумент запуска / git-действие). Последняя колонка всегда
должна быть выполнимым действием, не наблюдением.

## Частые ошибки

- Собирать что-то кроме MCP — лишняя работа, скилл о серверах.
- Автомаппить кандидата без сверки инструментов — роль упадёт на шаге 0.
- Задавать вопросы без рекомендации и последствия — решение возвращается
  исполнителю вместо владельца.

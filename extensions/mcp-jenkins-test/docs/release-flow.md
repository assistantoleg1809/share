# Карта релисного процесса и точки автоматизации

Источник: транскрипция [about-my-work.md](../../about-my-work.md).

## Процесс (как есть)

1. Тестировщик создаёт баг/задачу в Jira
2. Разработчик читает Jira, открывает IDE, правит в ветке
3. Коммит → push → **job сборки Jenkins** → проверка статуса
4. Успех → передача в тестирование ИЛИ **job деплоя** (EFS-проекты: вторая ступень)
5. Деплой упал → читаем лог → ищем ошибку → ищем открытые тикеты DevOps (массовая ли проблема)
6. Замечания тестировщика → повтор цикла

## Что автоматизирует эталон

| Шаг | Сейчас | Эталон даёт | Осталось человеком |
|---|---|---|---|
| Диагноз упавшей сборки | Открыть лог, найти ошибку | `/build-failure-triage`: классификация + тикеты + массовость | Решение, что делать |
| Исправление | Правка вручную | `/build-fix-loop`: минимальный фикс по TDD в worktree + пересборка | Ревью правки |
| Качество/уязвимости | Отдельные отчёты | sonar-mock/vuln-mock в цикле: критичное — в контексте фикса | Приоритизация |
| Изоляция срочных правок | git stash, захламление | worktree на агента: нет изменений — исчез; есть — ветка | Слияние веток |
| Отключение MCP для задачи | Настройки permissions | `disallowedTools` у отдельного агента workflow | — |

## Что НЕ решает эталон (по qwen-workflows.md §6)

- Реестр задач/проектов между сессиями (это отдельный `assistant`)
- Сам вызов реального Jenkins (permissions/токены — за человеком)
- Полная автоматизация цикла правка→сборка→деплой без человека
